# 应用升级机制完整总结（2026-11-14，v0.1.13 → v0.1.17 四连发实测收口）

本应用升级这一块从「能检查能下载」到「弱网可用、防重复下载、身份核对」的全部演进、防线与注意事项，一页说清。细节出处：`docs/指南对照复核记录.md`（五轮复核记录）、`docs/release-notes/0.1.13–0.1.17.entries`、`docs/操作反馈矩阵.md`。

## 一、流程全景

```
启动（windowReady 后自动检查，不打断不下载）
  └→ CheckForUpdates：真实 GitHub API（8s 超时）→ 版本数值比较（0.10 > 0.9）
      ├─ 已最新 → update:status 事件 → 界面「已是最新」
      └─ 有更新 → 顶栏徽标＋更新屏（版本/大小/可信发布页链接）
          └─ 用户点「下载并安装」
              ├─ 互斥闸 downloadMu.TryLock → 重复触发回 update_busy（独立稳定码）
              ├─ updates 目录按名清理：keep 表只保本版本成品/残片/侧车/清单
              ├─ Download：
              │   ├─ 成品等长命中 → 短路复用（不命中网络；验签闸兜内容）
              │   ├─ .part 残片 → Range ＋ If-Range(ETag 侧车) 身份核对
              │   │     ├─ 206 起点一致 → 断点接着收（进度 200ms 节拍事件）
              │   │     ├─ 200 全量 / 416 越界 / 206 错位 → 删残片整段重来（受控循环≤3）
              │   │     └─ 中断 → 保留残片与侧车，下次接着收
              │   └─ 实收≠声明 → 删残片拒收
              ├─ 双闸：SHA256 对清单 ＋ Ed25519 验签（嵌入公钥）——任一不过当场删包
              └─ 交接 xdg-open → 系统安装器 → dpkg 升级 → 重启自报新版本（启动日志带版本行）
```

## 二、防线清单（每层答一个「会不会」）

| 担心 | 答案 | 防线 |
|---|---|---|
| 跨版本拿旧残片拼新包？ | 结构上不可能 | 残片名含版本号；按名清理先删非本版本残片 |
| 同版本重发布（同名不同内容）？ | If-Range 内容校验器兜住 | 侧车记 ETag，续传核对；变过→200 全量→整段重来 |
| 弱网断线？ | 残片保留 | 重试从断点续；实收不符才删；重发循环≤3 次 |
| 断电/崩溃？ | 最坏退化不出错账 | 原子 rename；侧车写在截断成功后；成品短路读不到半截文件 |
| 坏包装上机器？ | 不会 | 摘要＋验签双闸，任一不过删包作废 |
| 重复点击重复下载？ | 不会 | 成品等长短路＋downloadMu 互斥（update_busy 独立码） |
| 残片收满了再点？ | 死锁已拆 | 等长残片直接改名成品（否则 Range 越界 416 死锁） |
| 升级完还要再升一次？ | 仅元数据时效场景 | 检查与下载之间远端又发新版——启动自动重查自愈（拍板接受） |

## 三、演进史（每个版本贡献了什么）

- **v0.1.13（起点）**：检查/下载/验签/交接已有，但无进度、无续传；弱网下 9MB 包两次下载失败（真机实测暴露）。
- **v0.1.14**：真机升级实测第一轮——检查✔、失败分类✔（update_network 文案正确）、下载弱网失败、续传缺失确认为真实需求。
- **v0.1.15**：下载进度（update:download-progress 事件＋「已收 X/共 Y（N%）」）＋断点续传（.part＋Range）；UI 真界面下载验证（用户亲手把 0.1.14→0.1.15 下载落盘成功）。
- **v0.1.16**：续传身份——If-Range 校验器（防同版本重发布）；响应分支语义表。
- **v0.1.17**：防重复下载——成品等长短路＋按名保留清理（keep 表与续传前提成对）。
- **收尾两轮复核又修 18 处**（416 死锁、Content-Range 错位、fd 泄漏、清单撞车假报错、keep 表漏侧车致加固失效、206 错位静默落坏盘、update_busy 码、percent 钳制、emit 层测试等）。

## 四、注意事项（纪律条目）

1. 残片身份靠**内容校验器**（If-Range/ETag），不靠版本字符串——字符串防不住重发布。
2. keep 表与续传前提**成对维护**：改清理必须同步想「续传前提还在吗」（侧车曾被自己的清扫废掉）。
3. 响应分支每一支都要有明确处理，**盲 O_APPEND 是最危险的一条**（包大小未知时静默落坏盘）。
4. 最终安全由终局双闸负责：续传链路上的任何妥协只损失效率不损失正确性。
5. 重复触发的拒绝用独立稳定码（update_busy），文案绝不与「已作废」混同。
6. 纯标签推送不触发本机重装；release 标签核对步先做 git safe.directory 放行（两次踩坑）。
7. 元数据时效接受自愈：启动自动重查，不做交接前二次确认。

## 五、测试覆盖

- 单测：续传（半包起跑）、If-Range 身份两路径、进度终值、成品短路＋大小不符重下、按名保留（含侧车）、emit 层事件名与终值。
- 真机：v0.1.13→0.1.14 全链实测（含弱网失败分类）、0.1.14→0.1.15 UI 真界面下载（用户亲手）、每版钩子装后三验。
