# 性能与资源基线：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把性能与资源占用从「感觉」变成「数值」：冷启动、首帧可交互、空闲与负载内存、事件分发频率、大 payload 传输、启动路径预算，避免项目中期才发现「越用越卡说不出哪变了」「内存只涨不降找不到来源」「冷启动比别人慢一倍但不知慢在哪一步」。

它不是某个应用的实现说明，也不预设产品名、框架或性能工具。每个项目都应先按自己的 NFR 目标和框架版本核实测量方法，再填写自己的决策。

这类问题的共同名字叫「无基线」。它们几乎从不来自某一个 bug，而来自一个结构：**没有「指标 → 目标值 → 测量方法 → 复测时机」这张表，任何性能讨论都无法收敛**。本方案的目标是让这张表在一档就存在，并随里程碑复测。

主大纲一档的「NFR 数值化基线」只列准入问题；本方案给出完整纪律。内存类问题与《窗口与多窗口技术方案》（一次性窗口、环境策略）和《长任务与后台工作技术方案》（事件风暴）的深水区衔接。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **指标清单与目标值**：冷启动、首帧可交互、空闲内存、负载内存峰值、事件分发频率、包体积、安装体积——各目标值是多少？谁定的、依据什么？
2. **测量方法**：每个指标谁来测、在什么环境测（目标最低配机器？CI？）、用例怎么定义（冷启动是否清缓存、取第几次）？「目标最低配」的机器定义了吗？
3. **启动路径**：首帧前执行了哪些工作（初始化、读盘、网络、窗口创建）？逐项标注「必须 / 可延迟 / 可惰性」，各占总预算多少？
4. **内存构成**：常驻基线由什么构成（WebView 进程组、缓存、数据）？增长的候选来源清单（监听器泄漏、无上限缓存、一次性窗口未销毁、日志）各有什么上限？
5. **事件频率**：哪些信号可能高频？合并 / 节流后的频率预算是多少？实测过分发频率与内存趋势吗？
6. **大 payload**：有无超过数百 KB 的返回值或事件载荷？分块 / 流式 / 分页策略是什么？平台传输限制核实了吗？
7. **复测机制**：每个里程碑复测哪些指标？超标时的处理规则（先归因再继续）？自动化性能回归是否暂缓、触发条件是什么（→ 主大纲五档）？

交付给 AI 的设计结果应包含：一页 NFR 表（指标 / 目标值 / 测量方法 / 复测时机 / 验收阶段）、启动路径分解、内存来源清单与上限、事件频率预算、测试与复测记录格式。

## 一页 NFR 表是唯一的事实

| 指标 | 目标值 | 测量方法 | 复测时机 |
|---|---|---|---|
| 冷启动 | X 秒 | 目标最低配机器、清缓存、N 次取中位 | 每里程碑 |
| 首帧可交互 | X 秒 | 首个可点击元素就绪 | 每里程碑 |
| 空闲内存 | X MB | 启动静置 N 分钟 | 每里程碑 |
| 负载内存峰值 | X MB | 标准负载用例 | 每里程碑 |
| 事件分发频率 | X 条/秒 | 高频场景实测 | 涉及事件改动时 |

表的纪律：
- **目标值必须数值化**，「要快」「不能卡」不是目标值。
- **测量方法先于优化**：同一指标换一种测法就是另一个数；方法定死后不改，要改就连历史数据一起作废重测。
- **复测时机写死**：性能只在被测量时才被守住；「下个大版本再看」等于不测。

## 启动路径预算

- 首帧前的每一项工作登记造册：做什么、耗时实测、能否延迟。
- **必须 / 可延迟 / 可惰性**三档标注；「可延迟」的有明确去向（首帧后空闲时、按需触发时）。
- 启动预算分解到段：把目标值切成「框架启动 + 数据加载 + 窗口呈现 + 首屏渲染」，超标时能定位到段，而不是整体抓瞎。
- 初始化纪律与主大纲「主线程工作早于 `Run`」条目衔接：构造与启动分离，启动阶段不做可延迟的 IO。

## 内存：来源清单 + 每来源上限

- 常驻基线先测出来，再谈增长：不知道基线，一切「好像变多」都无法判断。
- 增长候选来源逐项登记并各配上限：缓存（条数 / 字节上限 + 淘汰策略 →《缓存一致性方案》）、一次性窗口（用后销毁 → 窗口方案）、事件订阅（与生命周期成对 → 同步层）、日志（总量上限 → 可诊断性方案）。
- **台阶式增长的默认嫌疑**：进程组模型下，每多一个独立环境的窗口就多一组进程；窗口体系（共享 / 独立环境）是内存策略的根（→ 窗口方案）。
- 监控点选最低配目标机器：开发机上看不出的泄漏，低配机器上经常一目了然。

## 事件与传输

- 高频信号的节流与合并在同步层统一做（→ 同步层「高频变更」）；本方案要求**实测频率**进 NFR 表，预算超标先归因。
- 大 payload：传输策略（分块 / 流式 / 分页）与平台限制核实绑定；「能跑就行」的 payload 会在真实数据量下变成性能问题。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 越用越卡 | 监听器泄漏、缓存无上限 | 来源清单 + 每来源上限 |
| 内存台阶式上涨 | 一次性窗口未销毁、独立环境窗口累积 | 窗口环境映射（→ 窗口方案） |
| 冷启动超标 | 首帧前做了可延迟的 IO / 初始化 | 启动路径分解 + 预算到段 |
| 界面抽搐 | 事件风暴逐条触发 | 节流合并 + 频率实测 |
| 大数据量下传输卡死 | payload 无上限无分块 | 传输策略 + 平台限制核实 |
| 「新版本变慢了」查不清 | 无复测记录，历史数据缺失 | 每里程碑复测并存档 |
| 低配机器上不可用 | 全部测量在高配开发机 | 目标最低配机器进测量方法 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试与记录格式，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 启动 | 清缓存 / 带缓存、目标最低配机器、N 次取分布 |
| 内存 | 空闲曲线（≥30 分钟）、标准负载峰值、长时运行趋势 |
| 事件 | 高频场景实测频率与内存联动 |
| 传输 | 大 payload 用例（真实数据量级） |
| 复测 | 每里程碑同一方法复测，历史记录可对比 |

每次验收记录：环境（机器 / 版本）、方法、数值、与上次的差值。超标项先归因再继续，归因结论存档。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出一页 NFR 表（指标 / 数值化目标 / 测量方法 / 复测时机）与启动路径分解（逐项标注必须 / 可延迟 / 可惰性）。所有性能相关改动必须能在同一测量方法下复测对比；缓存与常驻结构必须有上限与淘汰策略；高频事件必须节流且实测频率进表；大 payload 必须有分块 / 流式 / 分页策略且平台传输限制核实；测量一律按目标最低配机器的定义进行；超标先归因再继续，归因结论存档。不得以「感觉不慢」替代测量，不得更改测量方法而不作废历史数据。实现后补启动路径与内存来源的实测记录，并明确列出未覆盖的场景。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：一页 NFR 表 + 测量方法（主大纲「NFR 数值化基线」条目）。
- **二档**：启动路径分解、事件分发频率与内存实测（对应主大纲「Go→前端事件内存边界」条目）。
- **五档**：自动化性能回归的暂缓与触发条件（主大纲五档已列）。
