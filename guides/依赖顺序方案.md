# 启动与依赖顺序：Wails3 + Go 专用方案

## 这份方案是做什么的

《后端目录结构方案》定了**编译期**的依赖方向（谁 import 谁）；本方案定**运行期**的依赖顺序：服务按什么拓扑启动、某一环失败怎么办、关停怎么逆序回退。启动与关停是应用中最难重演的两段——顺序错一处，就是「偶发起不来」「关不干净」这类最难排查的缺陷。

**硬性目标**：
1. 启动顺序是**显式声明的拓扑图**，不是注册顺序碰运气；
2. 每个服务登记「必需 / 可降级」，任何一环启动失败有预先选定的应对；
3. 关停严格逆序、可超时、不产生新工作。

**与相邻方案的分工**：构造与启动分离、主线程纪律 → 主大纲「主线程工作早于 `Run`」；目录依赖方向 →《后端目录结构方案》（本方案是其运行期续篇，包落位同源）；迁移在启动链中的位置 →《应用状态与持久化技术方案》；启动预算 →《性能与资源基线技术方案》；启动失败呈现 →《操作反馈方案》。

## 启动链骨架（拓扑参考序）

```
paths（目录与权限）
  → logging（观测先行：此后一切事故有记录）
    → config / state（含 schema 迁移——迁移必在领域服务之前）
      → sync hub（落定枢纽，被所有领域依赖）
        → tasks（任务队列）
          → domains（各领域服务，域间按依赖声明排序）
            → binding / app 装配（暴露层、窗口、托盘、菜单）
              → 窗口与 UI（首帧）
```

- **被依赖者先行**；观测类最先（logging 之后的事故才有现场，→ 可诊断性方案）；
- **两相启动**：先全部**构造**（纯内存、零 IO——主大纲 `Run` 纪律），再按拓扑序逐个 **Startup**（做 IO、起监听）。构造与启动分离让失败定位到「哪一相、哪一个服务」；
- 骨架是参考序，项目按依赖声明生成实际拓扑——**骨架里的相对关系不变**（logging 永远最先、迁移永远在领域前）。

## 依赖显式声明，顺序由声明推导

- 每个服务声明 `DependsOn`（所依赖的其他服务），装配层按声明**拓扑排序**生成启动序——**注册顺序不等于启动顺序**，改注册列表不该改变启动行为；
- **手工组装，不引 DI 框架**：依赖在 `app/` 装配层显式传参（→ 后端结构方案），依赖图肉眼可读；框架自身的 ServiceStartup 排序机制随锁定版本**待验证**，声明式排序以自己的装配层为准；
- **循环依赖的三个解法**（编译期循环被编译器拦，运行期循环要手动解）：接口注入（消费方定义接口）、事件解耦（经 hub 信号替代直接调用）、拆出第三者。解法选定记入装配层注释。

## 启动失败策略（逐服务登记）

| 分类 | 失败时 | 呈现 |
|---|---|---|
| **必需**（logging、state、sync hub、核心领域） | fail-fast：停止启动链、诊断落盘、明确退出 | 启动失败页：人话原因 + 重试 / 查看日志入口（→ 操作反馈失败三件套） |
| **可降级**（可选能力服务：通知、同步、自动更新…） | 跳过并登记降级 | 主功能照常；降级原因在状态表面可见（→ 状态方案就绪分级；系统能力方案降级三档） |

- **禁止裸 panic**：Startup 内 panic 必须被捕获 → 诊断落盘 → 走失败策略（→ 可诊断性方案 panic 纪律）；
- **禁止半死不活**：可降级服务失败后，依赖它的功能呈现明确的受限态，不静默装作正常（「看起来在跑、实际没同步」比崩溃更难查）；
- 迁移失败属于**必需失败**（数据层不健康，→ 状态方案降级守卫）。

## 惰性初始化

- 启动链只装**必需**；「可延迟」服务（→ 性能方案启动路径分解）按需启动——首用时才 Startup；
- **惰性传播**：懒服务的依赖也必须已就绪或随同惰性——首用时的初始化仍按拓扑序，不因懒加载乱序；
- 惰性服务的首次失败走同一失败策略（降级登记）。

## 关停：严格逆序

- `Shutdown` 按启动的**逆拓扑序**执行——后启动的先关，依赖别人的先走，被依赖的最后关；
- 每个关停步骤：接收**可取消的上下文 + 超时**——一个服务关不掉不能拖死整个退出（超时后标记并继续，终态在诊断中可见）；
- 关停期间**不产生新工作**：不接受新命令、不起新任务（→ 任务队列退出策略在此汇合）；
- 关停顺序同样是声明推导的，与启动序共用同一张依赖图。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 拓扑 | 依赖未就绪时服务绝不先行（注入检查）；注册顺序打乱后启动序不变 |
| 失败 | 每服务注入启动失败 → 必需走 fail-fast + 失败页；可降级走受限态呈现 |
| 迁移 | 迁移失败阻断领域服务启动（→ 状态方案矩阵） |
| 关停 | 逆序验证；一个服务关停超时不拖死退出；关停期拒绝新命令 |
| 惰性 | 懒服务首用时依赖已就绪；首用失败走降级 |
| 观测 | logging 之前发生的启动失败仍有诊断可查（构造期失败也要落盘） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 偶发起不来、时好时坏 | 启动顺序隐式（注册顺序决定一切） | 显式 DependsOn + 拓扑排序 |
| 启动失败白屏或裸崩 | 无失败策略、panic 裸奔 | 必需/降级登记 + panic 捕获 |
| 看似正常实际部分功能死了 | 可降级失败静默 | 受限态显式呈现 |
| 退出丢数据 | 关停无逆序、无超时、接受新工作 | 逆序 + 超时 + 关停不接活 |
| 惰性加载首用崩溃 | 依赖未随惰性就绪 | 惰性传播 |
| 最早的事故永远无现场 | logging 不是第一个启动 | 观测先行 |
| 迁移跑了一半服务已开工 | 迁移不在领域之前 | 骨架相对序 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出服务清单与 DependsOn 声明，由装配层拓扑排序生成启动序与关停逆序——不得依赖注册顺序的隐式行为。两相启动：全部纯内存构造后按序 Startup，构造期零 IO。逐服务登记「必需 / 可降级」：必需失败 fail-fast + 诊断落盘 + 启动失败页；可降级失败显式受限态呈现；Startup 内 panic 必须捕获走失败策略。迁移先于领域服务。关停按逆拓扑序、可取消带超时、关停期不接受新命令。惰性服务的依赖随同惰性并保持拓扑序。手工组装不引 DI 框架；框架排序机制随锁定版本待验证。实现后跑测试矩阵（拓扑 / 失败注入 / 关停 / 惰性），并明确列出未覆盖的服务。

方案确认后再改代码；服务生命周期接口细节随锁定的框架版本核实，与本方案冲突时先报告差异再裁决。

## 五档定位

- **一档**：服务清单 + DependsOn 声明 + 必需/降级分类。
- **二档**：拓扑排序落地、失败策略与失败页、关停逆序与超时。
- **三 / 四档**：惰性初始化全量、构造期失败观测、关停组合场景全测。
