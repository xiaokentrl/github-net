# 日志、崩溃与可诊断性：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把日志、错误码、崩溃处理、诊断包放在一起考虑，避免功能做完后才发现：生产环境出了问题只有用户一句「点了没反应」、前端日志只活在 console 里、崩溃没有留下任何现场、同一个错误前后端叫两个名字，或诊断包把用户文件和令牌一起发了出去。

它不是某个应用的实现说明，也不预设产品名、框架或日志库。每个项目都应先按自己的可诊断需求和框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「没有现场」。它们几乎从不来自某一个 bug，而来自一个结构：**可诊断性被当成「出事后再加」的功能，而它恰恰只能在出事前建好**。本方案的目标是把「任何一次故障都留得下现场」作为立项时就成立的约束。

两个边界先说清：
- 日志与诊断里的**脱敏清单**来自《安全边界与权限技术方案》的敏感数据清单；本方案管观测链路本身，脱敏是它的硬约束之一。
- 渲染进程崩溃后的**窗口恢复**在《窗口与多窗口技术方案》；本方案管崩溃的记录与检测。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **分级与去向**：日志分几级？开发与生产的级别、去向差异是什么？生产日志是否确定写入用户可访问的目录？
2. **前端日志接线**：框架是否默认转发前端日志？如无默认通道，是否注册了日志服务并显式传入 logger，让前端日志落盘而非只进 console？
3. **日志内容契约**：每条日志包含什么（时间戳规范、级别、领域、关联 ID、版本）？**排除清单**（令牌、密钥、文件内容、用户路径…）在哪里定义、谁来审？
4. **错误码表**：后端错误码与前端展示的映射表是否单一源生成？有没有双侧一致性（parity）门？
5. **panic 处理**：Go 侧 panic 是否被捕获并落盘诊断文件（含堆栈、版本、近期日志尾部）？哪些调用点被约束「不得 panic，必须返回错误」？
6. **前端崩溃**：未捕获异常上报到哪？渲染进程死亡除恢复外，是否落盘记录？
7. **异常退出检测**：下次启动能否发现上次是异常退出（运行标记 / 心跳）？发现后做什么（提示、标记日志、自检）？
8. **关联 ID**：一次用户操作从点击 → 命令 → 落定 → 界面刷新，能否用一个 ID 串起全部日志？ID 从哪生成、怎么传递？
9. **诊断包**：用户可触发的导出包含什么、排除什么？发送路径与用户确认方式？
10. **磁盘纪律**：日志轮转策略、单文件与总占用上限、写入频率有无预算？

交付给 AI 的设计结果应包含：日志分级与去向表、内容契约与排除清单、错误码单一源与 parity 门、panic 与崩溃处理流程、关联 ID 方案、诊断包内容清单（先审后实现）、测试矩阵。

## 内容契约：先定「写什么」，再定「怎么写」

- 每条日志的最小字段集立项时定：**规范时间戳、级别、领域标识、关联 ID、应用版本**。没有版本号的日志在「用户报障说上周就坏了」时一文不值。
- **排除清单先于日志实现**：敏感值清单来自安全方案；「先记下来以后再脱敏」等于不脱敏——落盘那一刻就决定了泄漏与否。
- **关联 ID 是打通现场的线**：一次操作生成 ID，随命令传入后端、随落定事件返回前端、写入沿途每条日志。没有它，前后端日志是两本对不上的账。
- 级别语义统一：error = 需要行动的失败，warn = 自动恢复的异常，info = 关键路径节点，debug = 仅开发。混用级别等于没有级别。

## 崩溃与异常退出

- **panic 纪律**：跨边界调用点（绑定方法、回调）一律「返回错误、不 panic」；顶层 panic handler 落盘诊断文件（堆栈、版本、日志尾部），随后按框架约定退出或恢复。
- **渲染进程死亡**：恢复流程在窗口方案；本方案要求恢复事件落盘记录，别让「白屏过一次」无据可查。
- **异常退出检测**：运行期维护「正在运行」标记（或心跳），启动时发现标记残留 = 上次异常退出，记入日志并可触发自检（存储完整性 → 状态方案、诊断提示）。没有检测，「偶发打不开」永远无法归因。

## 错误码：两侧一本账

- 错误码单一源定义，前端映射表由它生成；**parity 门**（码表一致性测试）进 CI，杜绝「后端改了码、前端还在翻旧表」。码值结构、登记流程与冻结纪律的实现细则 →《状态码方案》。
- 用户可见文案与内部码分离：内部码稳定用于检索，文案随语言走（→《国际化与输入技术方案》）。

## 诊断包：内容先审，后实现

- 包含：版本与平台信息、分级日志（按清单脱敏）、诊断文件（崩溃记录）、配置的结构化摘要（排除敏感值）、必要的存储统计（不含内容）。
- 排除：用户文件内容、凭据、完整路径中的敏感段、无关数据。
- 发送路径与用户确认方式立项时定；「诊断包里有什么」必须能拿清单向用户解释。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 用户报障无法定位 | 无关联 ID、日志无版本号 | 内容契约最小字段集 |
| 前端错误只有 console | 前端日志未接线 | 显式注册日志服务并落盘 |
| 崩溃原因永远未知 | panic 未捕获、无诊断落盘 | panic 纪律 + 诊断文件 |
| 「偶发打不开」无法归因 | 无异常退出检测 | 运行标记 + 启动自检 |
| 诊断包泄密 | 排除清单后补 | 排除清单先于实现并审查 |
| 错误码对不上 | 双侧手抄无 parity 门 | 单一源生成 + 一致性测试 |
| 磁盘被日志撑满 | 无轮转无上限 | 轮转 + 总量上限 + 写入预算 |
| 日志级别形同虚设 | 级别语义混用 | 级别语义写进契约 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| panic | 注入各层 panic → 诊断文件完整、应用按预期退出或恢复 |
| 崩溃 | 渲染进程崩溃 → 记录落盘 + 恢复联动（→ 窗口方案） |
| 检测 | 强杀后重启 → 异常退出被检出并自检 |
| 脱敏 | 构造含敏感值的操作，逐项审查日志、诊断包内容 |
| parity | 错误码表一致性测试进 CI |
| 磁盘 | 轮转触发、总量上限、长时间运行占用曲线 |

每次验收记录：注入方式、落盘内容审查结果。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出日志分级与去向表、内容契约（最小字段集 + 排除清单）、错误码单一源方案。前端日志显式注册并落盘，不依赖框架默认行为；生产日志确定写入用户可访问目录并带轮转与总量上限；每条日志带规范时间戳、级别、领域、关联 ID 与版本；排除清单来自安全方案的敏感数据清单，先于实现审查；跨边界调用点返回错误不 panic，顶层 handler 落盘诊断文件；错误码由单一源生成并有 parity 门进 CI；诊断包内容清单先审后实现。不得把「以后再加脱敏」作为实现方式。实现后补 panic 注入、脱敏审查与 parity 的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：错误码表与 parity 门（主大纲一档「前端架构纪律」条目）。
- **二档**：前端日志接线、生产落盘与脱敏、崩溃落盘（对应主大纲「生命周期与可诊断」一节）。
- **三档**：诊断支持包、事件订阅清理核对。
