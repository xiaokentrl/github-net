# 操作反馈：通用规划方案

## 这份方案是做什么的

用户每执行一个操作（点击、提交、删除、导出），应用欠他一段反馈。本方案定这段反馈的**契约**：分几段、在哪一层呈现、多久内出现、成功说什么、失败说什么、能不能反悔。

**与相邻方案的分工**：落定后「数据如何一致」→《统一同步层技术方案》；「长任务进度与取消」→《长任务与后台工作技术方案》《任务队列方案》；「离线与失败重试的呈现」→《网络与离线弹性技术方案》；「Toast/Confirm 组件本身」→《多平台一致组件库方案》。本方案管**反馈的交互设计契约**——以上方案都引用它，但「什么操作配什么反馈」的答案只住在这里。

**硬性目标**：每个操作的四段反馈（提交 / 进行中 / 落定 / 可反悔期）在立项时登记进**操作-反馈矩阵**；「这个按钮点了给什么提示」的答案从矩阵里查，不靠每处现想——与同步层「答案从表里查」同一宪法。

## 核心判定：反馈的层级路由

一个反馈出现在哪，按「结果被谁看见」路由：

| 层级 | 适用 | 形态 |
|---|---|---|
| **就地反馈** | 结果就在触发处可见 | 按钮 busy→成功态、行内勾叉、输入框内联校验 |
| **局部反馈** | 结果在附近区域可见 | 表单上方横幅、区块空态切换 |
| **全局反馈** | 结果在别处或不直观 | Toast（克制使用，见下）、页面横幅 |
| **任务中心** | 超过数秒、可取消、可批量的工作 | 进任务队列，中心可见（→ 任务队列方案） |
| **系统通知** | 窗口不可见时完成的重要工作 | 原生通知（→ 系统能力方案，含权限前置） |

**路由规则一句话**：

> **数据自己变对了，就不需要额外说「成功」**——就地能看到结果的操作，成功反馈就是结果本身；Toast 留给「结果不在眼前」的操作（导出到磁盘、发送、后台完成）。

这条「成功克制」原则是反馈噪音的解药：每保存一次就弹「保存成功」的应用，三天后用户对它的所有提示免疫。

## 时效预算（反馈的物理底线）

| 阈值 | 必须发生的事 |
|---|---|
| **100ms** | 操作被确认：按钮 busy/按压态、乐观写入或「已提交」——超过即「点了没反应」体验 |
| **1s** | 进行中指示出现（spinner/进度/百分比），并给出预期（「正在导入…」或接任务中心） |
| **10s** | 长操作必须已进任务中心：可看进度、可取消、切走不丢 |

预算的实现位：100ms 档由前端在途状态保证（→ 同步层在途纪律、乐观更新形状）；1s/10s 档的判定是长任务清单的准入线（→ 长任务方案「预期时长量级」一问）。

## 失败反馈的完整性（失败不许只说「失败」）

每条失败反馈必须三件套齐：

1. **什么失败了**：人话文案（错误码 → 语言包，→ 可诊断性方案 parity 门）；
2. **为什么**：原因分类（网络 / 权限 / 数据冲突 / 程序错误——程序错误也直说「应用内部错误，详情可导出」）；
3. **下一步**：重试入口（幂等才自动给自动重试，→ 网络方案）、查看详情、或帮助链接。

**与诊断的挂钩**：失败反馈提供「复制诊断信息 / 打开日志」入口，携带关联 ID（→ 可诊断性方案）——用户报障时反馈本身就是现场。

**部分失败**：批量操作的成败边界呈现与失败者重试 → 任务队列方案收口规则，反馈层只负责把它们显示出来。

## 破坏性操作：可反悔优先

按「反悔成本」递增选确认模式，**undo 优先于确认弹窗**：

1. **直接执行 + Undo**（默认首选）：删除进可撤销窗口（快照保留 N 秒/条），Toast 带「撤销」——最流畅且最安全；
2. **轻确认**：影响明确但不可逆的（清空回收站）——单次确认，文案写清后果与数量；
3. **强确认**：大面积不可逆（删库、覆盖导出）——输入式确认或明确展示影响范围。

**纪律**：确认弹窗的文案不许恐吓式全大写，必须写「影响什么、多少条」；同一操作在三平台用同一确认模式（→ 组件库方案 Confirm 系列）。

## 在途纪律（与同步层衔接的部分，一句话带过）

在途禁用防连点、乐观占位与已确认的视觉区分、在途取消在途重取——形状全部沿用《统一同步层技术方案》，本方案要求的是**每个可触发写操作的入口都落实这套形状**，在矩阵里逐操作打勾。

## 操作-反馈矩阵（立项填表，代码对表）

| 操作 | 提交（100ms） | 进行中 | 成功 | 失败 | 反悔 |
|---|---|---|---|---|---|
| 保存设置 | 按钮 busy | — | 就地（设置生效，无 Toast） | 就地横幅 + 原因 | — |
| 删除条目 | 乐观移除 | — | 数据已少（无 Toast） | 快照回滚 + Toast + 原因 | Undo 窗口 5s |
| 导出全部 | busy + 入队 | 任务中心进度 | 系统通知 + 打开位置入口 | 任务中心失败 + 重试 | 取消 |
| 远端同步 | 状态标记 | 心跳 | 状态收敛 | 横幅 + 离线降级 | — |

矩阵填法：每操作一行，五列不许留空（留空 = 没设计）；矩阵随新操作登记增长，评审对表。

## 文案纪律

- 成功文案默认**不出现**（成功克制）；必须出现时不带感叹号、不说「操作成功！」这类零信息话。
- 失败文案：主句人话、次句原因、尾句动作（「导出失败——磁盘已满。清理空间后重试」）。
- 全部文案键化走语言包（→ 多语言实现方案）；错误码进日志、人话进界面（→ 可诊断性方案）。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 时效 | 每操作实测 100ms/1s/10s 三档；慢机器（目标最低配）复测 |
| 失败 | 每操作至少一次失败：三件套齐、重试入口可用、诊断入口带关联 ID |
| 反悔 | Undo 窗口内生效 / 窗口外明确不可撤销；强确认覆盖范围核对 |
| 部分 | 批量部分失败的边界呈现 + 失败者重试 |
| 一致 | 同类操作跨界面反馈模式一致（矩阵对表走查） |
| 静默 | 后台完成时窗口隐藏 → 系统通知路径（含通知权限被拒降级） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 点了没反应 | 无 100ms 档在途确认 | 时效预算进矩阵提交列 |
| 「成功」弹窗刷屏 | 成功反馈不克制 | 路由规则：数据自变即成功 |
| 失败只有两个字 | 无三件套要求 | 失败完整性进矩阵失败列 |
| 用户不知道删了还能找回 | Undo 模式未用、文案未说 | 反悔列强制填写 |
| 慢操作把界面卡成假死 | 长操作没进任务中心 | 10s 档判定线 |
| 同类操作反馈五花八门 | 各写各的提示 | 矩阵对表走查 |
| 报障无现场 | 失败反馈无诊断入口 | 关联 ID + 复制详情 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先登记操作-反馈矩阵（提交/进行中/成功/失败/反悔五列全填），矩阵外不实现操作入口。提交反馈 100ms 内出现（在途形状沿用同步层）；超 1s 出现进行中指示，超 10s 进任务中心；成功反馈按路由规则克制（数据自变即成功，Toast 仅用于结果不在眼前的操作）；失败三件套齐（人话 + 原因 + 下一步），带诊断入口与关联 ID；破坏性操作按「undo 优先」分级，确认文案写明影响范围；文案全键化。实现后跑时效实测与矩阵对表走查，并明确列出未覆盖的操作。

方案确认后再改代码；反馈模式与平台习惯冲突时（如某平台确认惯例不同），先报告差异并等待裁决。

## 五档定位

- **一档**：路由规则 + 时效预算 + 操作-反馈矩阵初稿（覆盖一档命令清单）。
- **二档**：矩阵全覆盖写操作；Undo 基础设施（快照窗口）。
- **三 / 四档**：系统通知反馈路径、部分失败呈现、矩阵全量走查。
