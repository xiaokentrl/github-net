# 外部链接与协议回调安全方案：通用规划方案

## 这份方案是做什么的

来源：主大纲一档「自定义协议/外部链接安全」、二档「OAuth / SSO 回调拓扑」、三档「文件关联参数注入」，以及 OWASP 桌面应用安全里「不受信输入来自 OS」这一条。母法方案：《安全边界与权限技术方案》（信任边界与外部输入消毒）、《输入数据验证方案》（四层校验）、《单实例与快速启动方案》（二次启动参数路由）、《登录与权限方案》（会话与授权）、《绑定层契约与生成物方案》（结构化错误）。

它管**从操作系统进入应用的每一条入口**：自定义协议 deep link、文件关联参数、系统通知 action、OAuth 回调、单实例二次启动的 argv、外部链接打开。这些值不是用户输入框里的字符串那么简单——**它们由 OS/浏览器/其他应用传入，位于可信边界之外，且往往在应用启动早期就到达，晚于它的是整个应用状态**。

不预设：协议名、回调端口、参数结构、是否使用系统浏览器。所有具体值由项目决定，未核实的标**待验证**。

## 开始写代码前，先让 AI 回答这些问题

1. 应用注册了哪些自定义协议、文件关联、通知 action、URL scheme？逐条列出，含注册位置与平台差异。
2. 每个入口的参数结构是什么？**是否只接受结构化 ID，还是允许任意路径/URL/命令行文本**？
3. 授权回调用 loopback HTTP（`localhost:端口`）还是自定义协议？端口冲突、用户拒绝授权、系统浏览器回调到已运行实例的路径分别是什么？
4. 二次启动的文件参数与 URL 如何路由到已有实例？唯一 ID 用什么（→《单实例与快速启动方案》）？
5. 关联文件路径在哪里做规范化与目录前缀校验？是否会拼出 `../`、符号链接逃逸、UNC 路径？
6. 打开外部链接前是否做 scheme 白名单？`javascript:`、`file:`、平台特有 scheme 如何处理？
7. deep link 到达时应用处于什么状态（未启动 / 启动中 / 已运行 / 已登录 / 权限已授予）？状态不足时是排队等待还是明确拒绝？
8. OAuth 的 state/PKCE、回调一次性、超时与重放防护在哪一层实现（→《登录与权限方案》）？
9. 参数校验失败时给用户什么反馈？失败是否留下可诊断记录且不含参数原文（→《日志与可诊断性技术方案》）？
10. 目标平台上文件关联/协议参数的编码、长度、转义差异是什么？有没有平台把多个文件参数合并成一次调用？
11. 这些入口的自动化测试能覆盖哪些？哪些必须在打包安装形态下手工验收？

交付给 AI 的设计结果应包含：入口清单、参数契约表、路由状态机、消毒函数位置与用例、失败策略、测试矩阵。未经用户确认，不要擅自决定「收到链接就自动打开」这类会改变用户习惯的行为。

## 核心纪律

### 一、入口清单：一个入口一行

| 入口 | 触发者 | 参数形态 | 到达时机 | 消毒位置 | 最终路由 |
|---|---|---|---|---|---|
| 自定义协议 deep link | 浏览器/其他应用 | 结构化 ID | 冷启动或运行中 | 边界层 | 单实例路由 → 唤回 |
| 文件关联 | 文件管理器/双击 | 路径（可多值） | 冷启动或运行中 | 权威层 | 打开/导入流程 |
| 系统通知 action | 通知中心 | action ID + 可选 ID | 任意 | 边界层 | 统一唤回（→《托盘技术方案》） |
| OAuth 回调 | 系统浏览器 | code + state | 认证流程中 | 边界层 | 会话管理（→《登录与权限方案》） |
| 单实例二次启动 argv | 快捷方式/CLI | 路径或 URL | 已有实例运行时 | 边界层 | 已运行实例 |
| 外部链接打开 | 用户点击 | URL | 运行中 | 边界层 | 系统浏览器 |

清单里出现「同一入口两处注册」就是缺陷（→《托盘技术方案》的回调注册唯一性纪律），不是风格问题。

### 二、结构化 ID，不接受任意路径

- deep link 只携带**类型化 ID + 版本/动作**，例如「打开实体 X」，而不是「打开 /home/user/任意路径」。路径必须由应用在自己的权威数据里查出来，不能由外部直接指定落盘位置。
- 参数先规范化、再校验（→《输入数据验证方案》）：scheme/主机白名单、长度上限、字符范围、枚举动作、ID 格式。**黑名单不算校验**。
- 文件路径：解析成绝对路径后，用目录前缀判定是否落在允许根内；符号链接要用能拒绝逃逸的原语（`os.Root` 一类，→《Go测试与文件系统模式方案》）；`0,0`/空值不得兼职「未记录」。
- 结构化错误输出（码 + 字段 + 关联 ID），不要把原始参数拼进错误文案或日志（→《状态码方案》）。

### 三、回调拓扑与状态机

| 回调方式 | 优点 | 必须处理 |
|---|---|---|
| loopback HTTP | 系统浏览器通用、可带 state | 端口冲突/被占用、随机端口、绑定仅 loopback、超时关闭监听、回调一次性 |
| 自定义协议 | 无需监听端口 | 冷启动排队、参数注入、已运行实例路由、协议被其他应用抢占 |

共同纪律：

- **state / PKCE / 一次性**：回调必须有不可预测的 state 并与本地发起的认证请求绑定；用过即失效；超时有明确终态（→《登录与权限方案》）。
- **冷启动排队**：参数可能在应用还没初始化完时到达。要么先只存「待处理意图」并在依赖就绪后重放（→《依赖顺序方案》），要么明确拒绝并给出可重试入口；禁止在半初始化状态直接执行业务动作。
- **权限前置**：需要账号/授权的动作，在会话就绪后再执行；不得因为「链接里带了 token」就跳过会话校验。
- **二次启动路由**：唯一实例 ID 用反向域名或 GUID；参数路由到已运行实例后，统一走唤回流程，不得各自拼一套 `Show`/`Focus`（→《单实例与快速启动方案》《窗口与多窗口技术方案》）。

### 四、打开外部链接与失败策略

- scheme 白名单（通常只允许 `https:`，产品明确需要才加 `http:`/`mailto:`）；白名单外的请求明确拒绝并留可诊断记录。
- 打开前做一次规范化与目标展示，避免把「看起来像内部链接」的隐藏重定向交给系统浏览器。
- 失败不静默：协议宿主缺失、用户拒绝授权、端口被占、参数非法都要给用户可理解的解释与恢复方式（→《操作反馈方案》）。
- 消毒函数的位置固定在一处，所有入口复用；测试直接打这个函数，而不是只测「点击后有没有反应」。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| deep link 打开任意本地文件 | 参数允许任意路径，未做目录前缀校验 | 结构化 ID + 权威层查路径 + `os.Root` 类原语 |
| 冷启动时链接「偶尔失效」 | 参数到达早于依赖就绪，未排队 | 待处理意图 + 依赖就绪重放（→《依赖顺序方案》） |
| OAuth 回调被重放 | 无 state / 无一次性 / 监听未超时关闭 | state+PKCE+一次性+随机端口与超时 |
| 端口冲突导致登录卡住 | 固定端口、无冲突降级 | 随机端口 + 冲突明确提示 |
| 二次启动打开第二个实例或窗口乱跳 | argv 未走统一单实例路由 | 唯一实例 ID + 统一唤回流程 |
| 日志里出现用户完整路径/授权码 | 原始参数进日志与错误文案 | 消毒后只记关联 ID，字段白名单 |
| 通知点击打开了错误页面 | action 未携带结构化 ID、直接拼 URL | action ID 单源注册 + 路由表 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 参数 | 合法 ID、超长、非法字符、`../`、符号链接、UNC、多个文件参数、空值、未知动作 |
| 状态 | 冷启动 / 启动中 / 已运行 / 已登录 / 未授权 / 应用锁屏，逐格测 |
| 回调 | state 不匹配、重复回调、超时、端口占用、用户拒绝、浏览器未安装 |
| 路由 | 单实例已运行、二次启动、通知点击、系统浏览器回调 → 全部收敛到同一入口 |
| 平台 | Windows / macOS / Ubuntu 26.04 的协议注册、文件关联编码差异 |
| 形态 | dev / server / 打包安装分别重跑；打包形态下协议注册才真实生效 |
| 消毒 | 直接对消毒函数做单元测试，断言日志与错误文案不含原文 |

## 给 AI 的实施约束模板

> 先盘点应用注册的自定义协议、文件关联、通知 action、OAuth 回调与二次启动 argv，给出入口清单（一个入口一行）、参数契约表、路由状态机与消毒函数位置。**协议参数只接受结构化 ID，不接受任意路径或 URL；路径规范化与目录前缀校验放在权威层；打开外部链接前做 scheme 白名单；回调带 state/PKCE、一次性、随机端口与超时；冷启动参数先排队到依赖就绪再重放；所有入口复用同一个消毒函数与统一唤回流程。** 原始参数不得进入日志与错误文案。任何平台编码、协议注册行为以目标系统实测为准，查不到证据的写「待验证」。实现后给出可观察回归测试（非法参数被拒、重复回调失效、冷启动重放、打包形态冒烟），并列出未实测平台。所有协议名、ID 格式、端口策略由当前项目需求决定。

| 二档 | 回调拓扑、state/PKCE、冷启动排队、单实例路由、失败策略 |

| 五档 | 复杂协议族（多 scheme / 批量文件动作）可按产品形态暂缓，须写理由 + 触发条件 |
