# Go 后端目录结构：Wails3 + Go 专用方案

## 这份方案是做什么的

这是 Wails3 + Go 项目的**后端目录结构**规划。目录结构不是审美问题——本方案里每个目录都对应库里一条既有纪律的**物理落点**：唯一写入口、暴露面薄壳、平台代码集中、长任务 ctx、非 UI 冒烟路径。结构立不住，这些纪律就退化为「靠自觉」。

Wails3 工具链对目录有既定约束（模板入口、绑定生成、打包资产），方案的原则是**顺着工具链走，不在结构上跟工具较劲**；模板细节随锁定的框架版本核实，本方案标“待验证”处以项目实测为准。

通用纪律的落点：同步 →《统一同步层技术方案》；状态 →《应用状态与持久化技术方案》；长任务 →《长任务与后台工作技术方案》；暴露面 →《安全边界与权限技术方案》；语言包 →《多语言实现方案》。

## 总览

```
project/
├── main.go                  # 入口：只组装（构造服务 → 注册 → Run），业务与 IO 零容忍
├── app/                     # 装配层：服务清单、窗口/托盘/菜单接线、assets 嵌入（启动/关停的依赖顺序 →《依赖顺序方案》）
├── internal/                # 全部实现（Go 编译器强制外部不可 import）
│   ├── binding/             # 暴露层薄壳：校验 + 分类(只读/写/管理) + 委托，无业务
│   ├── domains/             # 领域层：每领域一目录，与同步层领域切分一一对应
│   │   └── <domain>/
│   │       ├── service.go   #   命令入口、事务边界、经 sync 枢纽落定
│   │       └── store.go     #   该领域的持久化读写
│   ├── sync/                # 统一落定同步枢纽：失效登记、落定三步（唯一出口）
│   ├── state/               # 状态持久化唯一写入口：设置/会话、schema、迁移、损坏降级
│   ├── tasks/               # 长任务：ctx 贯穿、队列上限、进度协议、退出策略
│   ├── net/                 # HTTP 客户端：超时/重试/代理策略显式声明
│   ├── platform/            # 平台特定实现：构建标签分文件，全库唯一允许的 GOOS 分支
│   ├── i18n/                # 语言加载器（go-i18n 封装、回退链）
│   ├── logging/             # 日志服务、panic 落盘、关联 ID
│   └── paths/               # 目录布局与权限：config/data/cache 分离、0700/0600
├── locales/                 # 语言包（模块根，//go:embed）→ 多语言实现方案
├── cmd/
│   └── cli/                 # CLI 入口：迁移、诊断、非 UI 冒烟的事实修改路径
├── core/                    # 高权限进程入口（独立 main；仅当存在高权限操作）
├── bindings/                # wails3 生成物：禁手改，CI generate→diff 门禁
├── frontend/                # 前端（→ 界面体系方案）
└── build/                   # 打包资产：图标、安装器配置、Info.plist 模板 → 分发方案
```

## 顶层规则（每条都有为什么）

1. **`main.go` 只组装**：构造服务（纯内存，不做 IO、不起监听——主大纲「主线程工作早于 Run」条目）→ 注册 → `Run`。装配细节（服务清单、窗口/托盘/菜单接线、assets 嵌入）放 `app/`，main 保持能一眼读完。入口留在根目录以兼容 wails3 工具链（待验证）。
2. **`internal/` 强制**：除入口与生成物外全部实现进 internal——编译器级隔离，不靠口头约定。
3. **`cmd/cli/` 必须存在**：CLI 复用同一套 `domains/` 逻辑，是《统一同步层技术方案》「非 UI 一致性冒烟」的物理前提——**CLI 触达不了全部命令，同步层就不是架构级成立**。同时承载迁移、诊断等无界面任务。
4. **`core/` 独立入口**：存在高权限操作时才有此目录（→ 安全方案：主进程始终普通权限，高权限拆独立进程 + 鉴权 IPC）。它有自己的 main，与主进程零共享状态。
5. **生成物隔离**：`bindings/` 由 `wails3 generate` 产出（目录名待验证），禁手改，CI `generate → git diff --exit-code` 门禁（主大纲「绑定生成物纪律」）。
6. **数据在根，代码在内**：`locales/` 这类被 embed 的数据资产放模块根（embed 无法引用模块外路径，→ 多语言实现方案）；代码不外溢。

## 各目录职责与对应纪律

| 目录 | 职责 | 落点的纪律 |
|---|---|---|
| `binding/` | 暴露给前端的每个方法的**唯一位置**：参数校验（Go 侧再验一次）→ 按「只读/写/管理」分类注册 → 委托领域服务。**薄壳**：一个方法只该有这几行 | 安全方案暴露面纪律；暴露面清单与本目录文件 1:1；绑定类型禁区（struct 只含简单数据容器） |
| `domains/<domain>/` | 领域是**结构的一等切分**：与同步层「领域与实体切分」、前端投影标识一一对应。领域内 service（命令入口、事务边界）+ store（持久化） | 同步方案 Q4；一档「事实源与权威状态归属」——每领域的写操作清单就住在 `service.go` |
| `sync/` | 统一落定同步枢纽：领域服务落定后调它，失效登记与落定三步只在这里实现。业务代码里不允许出现第二个「自己刷界面」的路径 | 同步方案「唯一入口只有一条」 |
| `state/` | 设置/会话等持久状态的**唯一写入口**、schema 与默认值单源、迁移函数、损坏降级 | 状态方案「唯一写入口」「默认值唯一源」 |
| `tasks/` | 长任务管理器：ctx 贯穿、并发上限、进度协议、退出与崩溃恢复策略 | 长任务方案 |
| `net/` | 全部外呼走这里：三层超时、幂等重试、代理策略显式声明 | 网络方案 |
| `platform/` | 托盘、菜单、身份、平台对话框等平台特定实现，**构建标签分文件**（`tray_windows.go` / `tray_darwin.go` / `tray_linux.go`）。全库唯一允许 `GOOS` 分支的地方 | 托盘方案；消灭散落各处的 runtime.GOOS if |
| `logging/` | 日志服务、panic handler、关联 ID、脱敏排除清单的执行点 | 可诊断性方案 |
| `paths/` | 平台标准目录、权限收紧、旧版配置搬家 | 状态方案存储引擎准入核对 |

## 依赖方向（单向，禁止逆行）

```
main/app ──→ binding ──→ domains ──→ sync / state / tasks / net
   │                        │
   └──→ platform            └──→ platform（仅平台能力调用）
cmd/cli ──→ domains（复用同一套领域逻辑，不经 binding）
core     （独立进程，与主进程零共享状态，仅鉴权 IPC）
```

- `domains` **禁止** import `binding`（业务反向依赖暴露层 = 分层倒置，CLI 路径也会断）；
- `binding` **禁止**直接摸 `state`/`store`（必须经领域服务——绕过领域 = 绕过事务边界与落定枢纽）；
- 领域之间**禁止**直接 import 对方内部：跨领域通信走事实层或 `sync` 枢纽的信号，确需接口时接口定义在消费方。

## 命名与禁区

- **禁止垃圾包**：`utils` / `common` / `misc` / `helper` 一律不许出现——放不进任何领域的能力，按「它服务谁」重新归类；真全局的（如 id 生成）给具名包（`ids`、`clock`）。
- 包名与领域清单一一对应，新增领域 = 新增目录 + 登记投影标识（→ 同步方案）。
- 包数量克制：小项目允许 `domains/` 先单包起步，拆分触发条件写明（第二个领域出现即拆；「第二个写入口风险」出现立即拆）——结构为纪律服务，不为对称服务。

## 结构守门清单（验收）

- [ ] `main.go` 无业务、无 IO，装配在 `app/`，一眼能读完
- [ ] `binding/` 每方法只有「校验 + 分类 + 委托」，暴露面清单与本目录 1:1
- [ ] 领域目录与前端投影标识一一对应
- [ ] 全库仅 `sync/` 有落定刷新路径；仅 `state/` 有持久状态写入口（grep 审查）
- [ ] 全库仅 `platform/` 出现 GOOS/GOARCH 分支
- [ ] `cmd/cli/` 能触达全部命令（非 UI 冒烟演练通过）
- [ ] 生成物 diff 门禁在 CI 中生效
- [ ] 无 `utils/common/misc` 包；领域间无直接 import

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 改一个功能要翻五个包 | 按技术分层（models/services/controllers）切，领域被拆散 | 领域是一等切分，技术分层退居包内文件 |
| 绑定方法里长出业务 | 贪快直接在暴露层写逻辑 | 薄壳纪律 + 行数审查 |
| main.go 塞满初始化 | 装配与业务不分 | main 只组装 + `app/` 装配层 |
| 平台 if 散落全库 | 各处 runtime.GOOS 判断 | 集中 `platform/` + 构建标签 |
| 出现第二个状态写入口 | 新功能图方便自己开文件 | `state/` 唯一入口 + grep 审查 |
| CLI 改不了事实 | 领域逻辑绑死在 binding 层 | 依赖方向：CLI → domains |
| 领域间循环依赖 | 领域互相 import 内部 | 跨领域走事实层/信号，接口定义在消费方 |
| 生成物被手改后静默错调 | 图省事直接编辑 | CI generate→diff 门禁 |
| `utils` 包膨胀成垃圾场 | 「放不进任何地方就进 utils」 | 禁垃圾包，按服务对象归类 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 按本结构落位：main 只组装；`binding/` 薄壳（校验 + 分类 + 委托）且与暴露面清单一一对应；业务进 `domains/<领域>`，领域切分与前端投影对齐；一切落定经 `sync/` 枢纽；持久状态唯一写入口在 `state/`；平台代码集中 `platform/` 且带构建标签；长任务、网络、日志、路径各有独立包；`cmd/cli/` 必须能触达全部命令；生成物禁手改。依赖方向单向：domains 不得 import binding，binding 不得直摸 state，领域间不直接 import。禁止 utils/common 垃圾包。新功能先定位目录再写代码，定位不了先报结构问题而不是发明新位置。实现后跑一遍结构守门清单。

方案确认后再改代码；wails3 模板细节（入口位置、绑定生成目录、Service 接口签名）以锁定的框架版本实测为准，与本方案冲突时先报告差异再裁决。

## 与既有指南的关系

- 领域切分与落定枢纽 →《统一同步层技术方案》；状态写入口与迁移 →《应用状态与持久化技术方案》
- 暴露面分类与校验 →《安全边界与权限技术方案》；`core/` 进程边界同上
- 语言包位置 →《多语言实现方案》；打包资产 →《签名打包与更新分发技术方案》
- CLI 非 UI 冒烟 →《统一同步层技术方案》测试矩阵

## 五档定位

- **一档**：结构骨架（总览树）+ 依赖方向决策 + CLI 入口存在性。
- **二档**：结构守门清单全绿（唯一写入口 grep 审查、CLI 触达全部命令、生成物门禁生效）。
- **持续**：新功能先定位目录再写代码；守门清单随 CI 常跑；领域拆分按触发条件执行。
