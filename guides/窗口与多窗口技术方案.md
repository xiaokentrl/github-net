# 窗口与多窗口：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把窗口生命周期（创建、隐藏、销毁、唤回）、几何持久化、焦点、多窗口体系与渲染进程故障恢复放在一起考虑，避免功能分别做完后才发现：各窗口关闭行为不一致、重启后窗口跳到屏幕角落或丢失最大化状态、隐藏后唤不回、渲染进程死了永远白屏，或多窗口把内存拖垮。

它不是某个应用的实现说明，也不预设产品名、框架或窗口管理库。每个项目都应先按目标平台和框架版本核实能力，再填写自己的决策。

两个边界先说清：
- **《托盘技术方案》管窗口的身份、图标与统一唤回入口**（各入口如何复用同一条呈现流程）；本方案管窗口自身——生命周期、几何、焦点、多窗口组织、故障恢复。唤回之后「窗口如何呈现」以本方案为准。
- 窗口几何属于要跨重启恢复的状态，落盘纪律见《应用状态与持久化技术方案》；本方案定 schema 内容与恢复策略。

这类问题的共同名字叫「窗口行为未定义」。它们几乎从不来自某一个 bug，而来自一个结构：**关闭、隐藏、销毁、唤回这些状态转移从未被显式定义，各窗口各写各的**。本方案的目标是让每个窗口的状态机在立项时就被画出来。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标平台和锁定的框架版本，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. **窗口清单**是什么？主窗口、设置、关于、向导、一次性弹窗——逐个标注「常驻 / 一次性」，以及归属哪个 WebView 环境。
2. 每个窗口的**关闭语义**是什么？点关闭按钮、最小化、隐藏、菜单退出，分别对应销毁还是隐藏？语义表逐窗给出，不允许「看默认行为」。
3. **几何持久化 schema** 是什么？是否按「屏幕标识 + DIP 坐标 + 缩放因子」存，而不是裸像素？目标屏幕不存在时如何回退？最大化 / 全屏状态是否单独存？
4. **焦点规则**：启动时谁获得焦点？模态窗口归谁、关闭后焦点归还给谁？Escape 在每类窗口里做什么？
5. **WebView 环境策略**：哪些窗口共享主环境（复用进程），哪些独立环境 + 用后销毁（确定性回收内存）？
6. **渲染进程死亡**的恢复路径是什么？重试上限、恢复期间的用户提示、耗尽后的终态是什么？恢复动作是否可能反过来杀掉宿主？
7. **新建窗口入口**：哪些操作会开新窗口？单实例锁下，二次启动携带的文件 / URL 如何路由到已有实例的正确窗口？
8. **隐藏与唤回**：隐藏后再显示，窗口位置、大小、最大化状态、当前屏幕是否保留？哪些框架调用会重新定位或重新呈现窗口（→ 与《托盘技术方案》的统一唤回流程对接）？
9. **主线程约束**：窗口操作是否都在框架 `Run` 之后、主线程调度？原生对话框是否调度到主线程？
10. **平台差异**：各平台的关闭按钮行为、任务栏 / Dock 分组、虚拟桌面（工作区 / Spaces）归属、混合 DPI 与多显示器行为，哪些已验证、哪些标「待验证」？

交付给 AI 的设计结果应包含：窗口清单与环境决策、每窗状态机、几何 schema、焦点规则、渲染进程故障恢复流程、平台差异验证清单、测试矩阵。

## 每个窗口一张状态机

状态机覆盖：创建 → 显示 → 最小化 / 隐藏 / 失焦 → 销毁，每个转移写明：触发源（用户 / 系统 / 代码）、调用的框架方法、副作用（状态保存、托盘联动、监听器清理）。

三条纪律：

- **关闭语义显式映射**：关闭事件到 hide 还是 destroy，是每窗一条的显式决策；「关闭按钮是退出还是驻留」这类改变用户习惯的行为必须由用户确认，不得擅自决定（与《托盘技术方案》一致）。
- **销毁必须干净**：销毁窗口时订阅、定时器、绑定回调成对清理；「关了还在后台响应」的窗口是最难排查的错乱源。
- **隐藏不是销毁**：隐藏窗口的资源（WebView、页面状态）仍然活着——这是特性（快速唤回）也是成本（内存）；哪些窗口值得隐藏、哪些必须销毁，在窗口清单里定。

## 几何持久化

- schema 按「屏幕标识 + DIP 坐标 + 缩放因子」，不存裸像素——裸像素在跨 DPI 拖动、换主屏、拔显示器后全部失真。
- **目标屏不存在时的回退规则**：回退到主屏可见区域，不允许窗口落在不可见位置。
- 最大化 / 全屏 / 常规三态分开存；恢复时先恢复状态再恢复几何。
- 几何变更的落盘时机沿用状态方案的落盘纪律（变更即写或去抖带上限）。

## 多窗口环境与内存策略

- **常驻窗口共享同一 WebView 环境**：复用浏览器进程，内存与启动成本都省。
- **一次性窗口独立环境 + 用后销毁**：确定性回收，防泄漏累积。
- 窗口 → 环境的映射在立项时逐窗定案，写进窗口清单；运行期不再临时决定。

## 渲染进程故障恢复

恢复流程图必须预先画出：检测（进程退出回调）→ 隔离现场（保存状态）→ 恢复尝试（重载 / 重建）→ 重试上限 → **终态**（明确提示用户 + 重启入口）。配套纪律：

- 恢复动作本身要有重试上限，不能无限循环；
- 恢复失败不得反杀宿主进程；
- 终态必须是「用户能行动的状态」，不是永久白屏。

## 边界场景

设计评审时逐条给出答案；任何一条没有规划，都会在后期表现为「偶发窗口异常」。

- **拔掉外接显示器后重启**：窗口落点按回退规则。
- **混合 DPI / 跨 GPU 环境**：拖拽跨屏的渲染稳定性、适配器切换后的行为——目标硬件上冒烟，未验证项标「待验证」。
- **系统休眠恢复**：窗口状态与网络类任务的联动。
- **焦点跟随鼠标的合成器（Linux）**：弹窗可能因焦点丢失立即收起——目标环境验证，必要时降级为非焦点型呈现。
- **二次启动**：参数路由到已有实例的正确窗口，单实例锁契约（→ 主大纲）。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 恢复后窗口跳到角落 / 不可见 | 裸像素几何、无目标屏缺失回退 | 屏标识 + DIP schema + 回退规则 |
| 不同窗口关闭行为不一致 | 关闭语义未显式映射，各写各的 | 每窗状态机 + 显式语义表 |
| 隐藏后唤不回 | 唤回路径未验证、依赖了会重新定位的调用 | 统一唤回流程（→ 托盘方案）+ 冒烟 |
| 渲染进程死后永久白屏 | 无故障处理或无终态 | 恢复流程图 + 重试上限 + 终态 |
| 内存只涨不降 | 一次性窗口未销毁、环境未隔离、订阅未清理 | 窗口环境映射 + 销毁清理纪律 |
| 弹窗一闪而过 | 焦点型呈现遇上 focus-follows 合成器 | 目标环境验证 + 非焦点降级 |
| 二次启动开了第二个实例 | 单实例锁缺失或路由未接 | 单实例契约 + 参数路由 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 生命周期 | 每窗：打开 → 最小化 / 隐藏 / 关闭 → 唤回 / 重开；正常退出与强杀 |
| 几何 | 跨屏拖拽、混合 DPI、拔显示器、换主屏、最大化 / 全屏恢复 |
| 故障 | 注入渲染进程崩溃 → 恢复流程 → 重试上限 → 终态 |
| 多窗口 | 并发操作同一事实、窗口间焦点转移、模态规则 |
| 平台 | 各目标平台的关闭按钮、任务栏 / Dock、工作区行为 |

每次验收记录：窗口状态机的实际路径、恢复后的几何、内存趋势。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先盘点窗口清单并逐窗给出「常驻 / 一次性」与 WebView 环境决策。开始改代码前，先给出每窗状态机与显式关闭语义表、几何持久化 schema（屏幕标识 + DIP + 缩放因子 + 目标屏缺失回退）、焦点规则、渲染进程故障恢复流程（含重试上限与终态）。不得依赖框架默认关闭行为；不得存裸像素几何；一次性窗口必须独立环境且用后销毁；销毁时订阅与定时器成对清理；窗口操作不得早于框架 `Run` 或绕过主线程调度；平台相关行为先在目标环境验证，未验证一律标注“待验证”。实现后补关闭语义、几何恢复与故障恢复的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：窗口清单 + 环境决策草案。
- **二档**：窗口状态机、几何 schema、故障恢复（对应主大纲「窗口生命周期」「混合 DPI」「多窗口内存策略」等条目）。
- **三档**：焦点规则全量、平台差异验证补全。
