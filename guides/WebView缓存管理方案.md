# WebView 缓存管理：Wails3 + Go 专用方案

## 这份方案是做什么的

三平台的 WebView 引擎各自自带 HTTP / 磁盘缓存（WebView2 用户数据目录、WKWebView 与 WebKitGTK 的网络缓存），**这部分缓存引擎自管，应用不能逐条控制**。本方案回答：引擎缓存住在哪、怎么管住它、前端资产更新后怎么保证不出现「半新半旧」、清理入口怎么把它算进来。

**与相邻方案的分工**：应用自管的落盘缓存 →《磁盘资源缓存管理方案》（分工一句话：**能逐条控制的自己管，管不了的把引擎当黑箱管理其环境**）；数据层的缓存纪律 →《缓存一致性方案》；用户数据目录与权限 → 主大纲「平台标准目录与权限」条目；资产随更新整体替换 →《签名打包与更新分发技术方案》。

**核心立场**：**数据请求不走引擎缓存**。应用数据的一致性由《UI数据一致性实现方案》的落定链负责——引擎 HTTP 缓存是一层应用看不见、控不住、清不准的缓存，让它参与数据一致性就是双层缓存互不对话。数据请求显式禁用缓存或直读（行为随引擎**待验证**），引擎缓存只留给静态资产。

## 用户数据目录（引擎缓存的家）

- **显式指定**，不落系统默认位置：默认位置不可控（路径含框架随意的哈希目录）、可能不加密（主大纲已点名 WebView2）、卸载后残留。指定到 `paths/` 管的应用私有目录、权限收紧。
- **目录里只有引擎的东西**：引擎缓存、存储（localStorage 等）、Service Worker 状态。用户数据零存放——「清引擎目录」因此永远安全。
- **卸载**：随卸载清理决策 → 分发方案；目录可整删重建（首次启动自愈）。
- 多窗口共享主环境 → 缓存共享（→ 窗口方案环境策略）；一次性窗口独立环境 → 独立缓存，用后随环境销毁。

## 资产版本化：防「半新半旧」（本方案最关键的一条）

应用更新后，引擎缓存里可能还躺着**旧版本的 JS/CSS**，而新的 index.html 已经指向新文件名——半新半旧是「更新后界面异常」的头号根因（与《签名打包与更新分发技术方案》的更新原子性衔接：应用二进制与前端资产必须同版本）。

三层防护，逐层核实引擎行为（**待验证**项随锁定版本）：

1. **带 hash 的文件名**：构建产物 `app.3f9c2a.js`——内容变则名变，旧缓存天然无害（L3 内容寻址思想）；
2. **index.html 禁缓存**：入口文件 `Cache-Control: no-cache`（或等价），每次从应用资产直读——版本切换的「指针」永远新鲜；
3. **版本一致性自检**：启动时校验资产指纹（构建期写入的版本号 vs 运行期实际加载的），不一致 → 强制绕过缓存重载并上报（→ 可诊断性方案）。自检失败即「半更新」的检测器。

custom scheme / assetserver 对 Cache-Control 头的透传行为**三引擎有差异，逐引擎核实**后写进引擎基线文档（→ 组件库方案引擎基线）。

## 数据请求：绕开引擎缓存

- 业务 API 调用（若经 webview fetch 真实 HTTP）：请求显式 `no-store`（或响应头禁缓存），数据缓存由应用自管（→ 缓存一致性方案）；
- 若经绑定直调 Go：引擎缓存不参与——这也是「数据走绑定、不走 webview HTTP」的又一理由（→ 前端结构方案 `api/`）。

## 清理入口

- 用户「释放空间」/「重置」时，**引擎缓存计入占用统计**（查询引擎缓存目录大小，API 随引擎**待验证**；无 API 则按目录估算并注明）。
- 清理动作：调引擎清缓存 API，或删除用户数据目录内的缓存子目录后重启 WebView 环境——**不删用户数据目录里引擎的存储部分**（那是应用功能状态，不是缓存），两者的边界按引擎文档核实。
- 「重置应用」= 数据目录整删重建（用户确认后），引擎状态一并归零。

## 验收清单

- [ ] 用户数据目录显式指定、权限收紧、位置可从 `paths/` 查到
- [ ] 更新演练：旧版本 → 新版本，无 stale 资产（版本一致性自检通过，或强制重载触发）
- [ ] 三引擎的 Cache-Control 行为实测记录进引擎基线文档
- [ ] 数据请求无引擎缓存参与（网络面板核验）
- [ ] 清理入口：占用含引擎缓存、清理后自愈、引擎存储（登录态等）不被误删
- [ ] 卸载 → 重装：目录整删重建后应用正常（自愈验证）

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 更新后界面异常、白屏、功能错乱 | stale 资产：hash 文件名 / 入口禁缓存缺失 | 三层版本化防护 + 自检 |
| 数据时新时旧查不清 | 引擎 HTTP 缓存参与了数据一致性 | 数据请求绕开引擎缓存 |
| 引擎目录在系统深处找不到 | 未显式指定用户数据目录 | 显式指定 + paths 统一 |
| 清理后磁盘没变小 | 引擎缓存未计入清理 | 占用统计含引擎缓存 |
| 清理后用户被登出 | 误删引擎存储（非缓存部分） | 边界按引擎文档核实后分层清理 |
| 卸载残留几十 MB | 用户数据目录未随卸载清理 | 分发方案卸载决策 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先核实三引擎的用户数据目录指定方式、缓存目录构成与 Cache-Control 透传行为，结果写进引擎基线文档（未验证项标注待验证）。用户数据目录显式指定至应用私有路径并收紧权限，目录内零用户数据。前端构建产物 hash 文件名 + 入口禁缓存 + 启动版本一致性自检（不一致强制重载并上报）；数据请求禁用引擎缓存，数据一致性只走应用落定链（→《UI数据一致性实现方案》）；业务数据优先走绑定而非 webview HTTP。清理入口的占用统计含引擎缓存，引擎缓存与引擎存储分层清理、边界先核实。实现后跑验收清单，重点补一次旧版本 → 新版本的更新演练，并明确列出未覆盖的引擎差异。

方案确认后再改代码；引擎缓存行为是黑箱，一切「应该」以目标引擎实测为准。

## 五档定位

- **一档**：用户数据目录决策 + 资产版本化方案（hash + 禁缓存）。
- **二档**：三引擎 Cache-Control 行为核实、版本一致性自检、数据请求绕行。
- **三 / 四档**：清理入口含引擎缓存、更新演练、卸载自愈全测。
