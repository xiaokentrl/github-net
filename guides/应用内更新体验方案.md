# 应用内更新体验方案：通用规划方案

## 这份方案是做什么的

来源：主大纲四档「差分更新与回滚路径」「灰度发布」，《签名打包与更新分发技术方案》的更新流水线（那篇管**机制**：签名、原子切换、回滚、通道），《操作反馈方案》的反馈层级与时效预算（那篇管**通用交互**），以及《发布交付流水线方案》的交付链。

本方案补的是**用户在应用里实际看到的更新过程**：什么时候检查、发现新版怎么告知、强制还是可选、下载进度与断点、装完要不要重启、失败怎么回退、企业里能不能关。更新机制正确但体验糟糕，用户会长期停在旧版本，前面所有签名与回滚工作都白做。

不预设：是否强制更新、检查频率、通道数量、重启策略、差分是否启用。所有具体值由产品决定。

## 开始写代码前，先让 AI 回答这些问题

1. 检查时机：启动时、定时、手动、服务端推送？**是否可能在用户正进行长任务时打断**（→《长任务与后台工作技术方案》）？
2. 发现新版后反馈层级：静默后台下载、就地提示、全局横幅、模态？依据是什么（→《操作反馈方案》）？
3. 哪些更新强制、哪些可选？强制的依据（安全修复、契约不兼容、支持窗口到期）写在哪（→《客户端与服务端API契约方案》）？
4. 用户能否推迟？推迟多久、能否无限推迟、到期后行为是什么？
5. 下载：进度是否可观察、能否暂停/续传、大包是否差分/分片（→《分片上传与断点续传方案》《签名打包与更新分发技术方案》）？
6. 磁盘不足、代理/企业 CA、离线、校验失败的提示与恢复入口分别是什么（→《网络与离线弹性技术方案》《生产构建安全基线方案》）？
7. 安装时机：立即重启、下次启动、空闲时？正在编辑的数据如何保存（→《应用状态与持久化技术方案》《原子性提交方案》）？
8. 更新后首次启动：迁移、配置保留、许可状态、窗口几何、单实例锁是否仍正常（→《应用状态与持久化技术方案》《授权与许可方案》《托盘技术方案》）？
9. 回滚：用户侧如何感知？失败后是否自动回退到旧版、保留几次旧版本（→《签名打包与更新分发技术方案》）？
10. 通道（stable/beta）如何切换、用户是否能自助、切换后版本比较规则（→《版本号方案》《企业部署与托管配置方案》）？
11. 企业托管策略能否禁用自动更新、锁定通道？与用户显式设置的仲裁规则（→《企业部署与托管配置方案》《配置文件方案》）？
12. 更新过程的每一步是否留可诊断记录且不含用户数据（→《日志与可诊断性技术方案》）？
13. 发布说明在应用内如何呈现：对用户的影响、需要用户做什么（→《发布交付流水线方案》《用户文档与上手支持方案》）？

交付给 AI 的设计结果应包含：检查时机与打断规则、提示层级与推迟策略、下载/安装/重启状态机、失败与回滚用户路径、通道切换、托管仲裁、发布说明呈现。

## 核心纪律

### 一、状态机：从「发现」到「生效」逐步可观察

| 状态 | 用户看到 | 需要避免 |
|---|---|---|
| 检查中 | 无感或就地轻提示 | 启动时模态挡住主界面 |
| 发现新版 | 说明影响与是否需要操作（→《弹窗按钮文案方案》按钮写结果） | 「有新版本」这种无信息量文案 |
| 下载中 | 进度/可暂停/可推迟，长任务走反馈预算（→《操作反馈方案》） | 假进度、卡在 99% |
| 校验/安装 | 明确阶段与预计影响 | 静默替换正在使用的文件 |
| 待重启 | 明确「保存什么、什么时候生效」 | 不经确认直接杀进程 |
| 已生效 | 更新后首启说明变化 | 升级后什么都没说 |
| 失败/回滚 | 原因、是否保持旧版、重试入口 | 「更新失败」四个字加一个确定 |

**每一步都有可观察判据**（→《托盘技术方案》五层验证纪律）；「代码里写了」不算用户看到了。

### 二、不打断、可推迟、有理由

- 检查与下载避开长任务、模态操作、正在编辑的文档（→《长任务与后台工作技术方案》《原子性提交方案》）。
- 强制更新必须有成文依据：安全修复、服务端契约不兼容、支持窗口到期（→《客户端与服务端API契约方案》《威胁建模与安全响应方案》）；不能因为「想让用户用新版」就强制。
- 推迟策略写明次数/时长上限与到期行为；无限推迟等于没有策略，无提示直接强制等于剥夺用户控制权。
- 重启前保存状态：几何、未提交内容、许可状态；失败时保留旧版可启动（→《应用状态与持久化技术方案》《签名打包与更新分发技术方案》）。

### 三、失败、回滚与通道

| 失败 | 用户路径 |
|---|---|
| 磁盘不足 | 明确需要多少空间 + 清理入口（→《磁盘资源缓存管理方案》） |
| 代理/企业 CA/离线 | 区分「网络问题」与「包损坏」，给重试/离线包路径 |
| 签名或校验失败 | 明确拒绝安装、不静默降级（→《签名打包与更新分发技术方案》） |
| 安装中途失败 | 原子切换回旧版 + 可诊断记录 + 重试入口 |
| 更新后首启异常 | 异常退出检测 + 回滚触发条件（→《日志与可诊断性技术方案》《崩溃上报与符号还原方案》） |

- 通道切换的自助路径与版本比较规则事先定义；从 beta 回 stable 不算「降级」就别显示成降级警告（→《版本号方案》）。
- 企业托管可禁用自动更新/锁定通道；**仅管理员明确锁定的键**优先于用户偏好，被锁定项在 UI 标注「由组织管理」（→《企业部署与托管配置方案》）；未锁定的用户显式设置应用不得覆盖（→《托盘技术方案》）。
- 发布说明结构化生成，写「对我有什么影响」「需要做什么」，而不是提交哈希列表（→《发布交付流水线方案》《用户文档与上手支持方案》）。

### 四、与机制的边界

| 归《签名打包与更新分发技术方案》 | 归本方案 |
|---|---|
| 签名验签、信任根、公钥固定 | 校验失败时用户看到什么 |
| 原子切换、差分、回滚包保留 | 待重启/回滚提示与推迟策略 |
| 通道与灰度分组的服务端机制 | 通道切换 UI 与托管锁定表现 |
| 跨卷更新、安装包格式 | 磁盘/代理/离线失败的用户路径 |

两篇都要在 runbook 里指向对方，避免同一问题两处给出矛盾结论。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 用户长期停在旧版 | 提示无信息量、强制无依据、推迟无上限 | 影响说明 + 成文强制依据 + 推迟策略 |
| 更新打断正在编辑的数据 | 安装时机不看长任务/未提交状态 | 避开长任务 + 重启前保存 |
| 卡在 99%/假进度 | 进度来源与断点状态不清 | 分片/断点以服务端为准（→《分片上传与断点续传方案》） |
| 校验失败仍安装 | 失败降级写成「成功」 | 明确拒绝 + 不静默降级 |
| 升级后设置/窗口位置丢了 | 迁移、几何、许可状态未纳入首启检查 | 更新后首启检查清单 |
| 企业里关不掉自动更新 | 开关只在 UI，未进执行点 | 托管键在执行点统一校验 |
| 「更新失败」无法自救 | 错误未分类、无重试入口 | 失败分类表 + 恢复路径 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 状态 | 检查/发现/下载/暂停/续传/校验/待重启/生效/失败/回滚逐态 |
| 打断 | 长任务中、模态中、编辑未保存、锁屏/休眠 |
| 失败 | 磁盘不足、代理、离线、签名失败、中途断电、跨卷 |
| 首启 | 配置/几何/许可/单实例/托盘唤回逐项核对 |
| 通道 | stable↔beta、版本比较、托管锁定、强制升级到期 |
| 形态 | dev / 打包安装分别跑；安装态才算数（→《生产构建安全基线方案》） |
| 用户 | 提示可读性、按钮写结果、发布说明「对我有什么影响」 |

## 给 AI 的实施约束模板

> 先给出检查时机与打断规则、提示层级与推迟策略、下载/安装/重启状态机、失败分类与用户恢复路径、通道切换与托管仲裁、更新后首启检查清单、发布说明呈现规则，再写更新 UI。**每一步用户可见且可观察；避开长任务与未提交数据；强制更新必须有成文依据且推迟策略有上限；重启前保存状态、失败时保留旧版可启动；签名/校验失败明确拒绝安装、不静默降级；企业托管可禁用自动更新且被锁定项在 UI 标注；仅明确锁定的策略键优先于用户偏好，未锁定的用户显式设置不得覆盖；发布说明写对用户的影响。** 任何「代码里写了」不算验收证据。实现后给出逐态、失败、首启、通道的可观察测试，并在打包安装形态重跑，列出未实测平台。所有时机、时长、通道、阈值由当前产品需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 是否自动更新的决策与强制更新依据原则 |
| 二档 | 状态机、提示层级、推迟策略、失败分类 |
| 三档 | 下载进度与断点、通道切换、发布说明呈现 |
| 四档 | 安装态全流程演练、回滚触发条件、托管锁定表现 |
| 五档 | 差分更新、A/B 式发布说明实验可按产品阶段暂缓（写理由 + 触发条件） |
