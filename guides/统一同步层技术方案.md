# 操作落定与界面同步：统一同步层通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把「用户操作 → 后端落定 → 界面同步」这一整条链放在一起考虑，避免功能分别做完后才发现：操作成功但表格没变、状态闪回旧值、重启后界面空白、批处理只同步了一半，或每加一个功能就要多写一条「这里要不要刷新」的特判。

它不是某个应用的实现说明，也不预设产品名、框架、状态库或刷新间隔。每个项目都应先按自己的命令清单、事实清单和框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「UI 与事实源失去同步」。它们几乎从不来自某一个 bug，而来自一个结构：**刷新规则散落在各处、各带各的条件**——每条规则都可能漏，漏了就是用户报「界面没同步」。本方案的目标是把这类结构在立项阶段就排除掉。

一个定位要先说清：**「事件驱动失效 + 兜底轮询」是有意选择的简化架构，不是对“更高级同步引擎”的妥协。** 桌面单用户场景下，它没有双向绑定、没有自动依赖追踪、没有同步引擎；它的一致性来自一条可以被代码审查强制执行的纪律。本方案的全部内容都是这条纪律的展开。该纪律向全部缓存（不止界面镜像）的推广见《缓存一致性方案》；Wails3 + Go 的具体实现（信号协议、落定枢纽、前端订阅中心）见《UI数据一致性实现方案》。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **权威层在哪里？** 项目的核心数据住在哪个服务/进程里？哪些字段是事实，哪些只是派生？写操作的串行化边界在哪里？
2. **命令清单**是什么？每个命令（保存/删除/执行/还原…）改变哪些后端事实？
3. **事实清单**是什么？哪些界面表面（表格、状态栏、徽标、弹框、别的页签）在读每一份事实？各自通过哪条链路读？
4. **领域与实体如何切分？** 同步信号按领域还是按实体粒度发射？前端的投影标识能否与这个切分一一对应？切分对不上，多窗口和详情视图的一致性就没有落点。
5. **变更的“唯一出口”在代码结构上是什么？** 是一个独立的同步枢纽，还是散落在各业务服务里的发射调用？如果是后者，「唯一入口」纪律将无法被代码审查。
6. 命令的「落定」如何定义？后端写盘、事务提交、外部调用完成与信号发出之间的先后顺序和原子性是什么？
7. 信号投递的保证级别：会丢吗？会乱序吗？会重复吗？接收端断线重连后能否补齐错过的变化？信号是否类型化注册（拼错事件名会在构建期暴露，而不是静默不触发）？
8. 项目里有几层缓存（组件状态、全局 store、内存快照、本地数据库）？每层的失效策略分别是什么，由谁负责？
9. 是否使用乐观更新？落定（settle）策略是什么——成功时是否也从事实源重读？失败时默认重取还是回滚快照？回滚快照在并发下是否可能已失效？
10. 批量操作部分失败时，成功的一半和失败的一半如何各自同步与呈现？前端是否被允许把「部分成功」直接写进镜像而不经过事实源？
11. 是否存在多窗口、多页签、多端同时读写同一份事实源的情形？投影标识的粒度是否与领域/实体切分对齐？
12. 应用重启后，哪些状态住在内存里会丢？丢了之后哪些界面会退回空态或旧值？事件监听器的清理是否与生命周期绑定、是否可审计？

交付给 AI 的设计结果应包含：命令-事实影响表、事实读取登记表、统一同步层规则、乐观更新纪律、失败回执与恢复入口、边界场景清单、测试矩阵。凡是「这个界面要不要刷新」这类问题，答案必须能从表里查出来，而不是靠每处代码现想。

## 先把「事实」「镜像」「意图」分开

界面不同步的病根，几乎都是这三个概念被混成了一个。光下定义不够——立项时要给出**一句话判定规则**，让代码审查能当场判定一段数据属于哪一类。

- **事实**：这段数据如果丢失，重新从权威层读一次就能完整恢复。由权威层持有，跨窗口、跨进程持久。只能通过权威层的写方法改变；写方法必须递增版本标识。
- **镜像**：它存在的唯一理由是「让当前 UI 不必每次同步阻塞地读事实」。住在前端缓存里，可以被随时丢弃并重建。可以被标记失效；可以短暂写入乐观值；**不能被当作任何写操作的输入依据**。
- **意图**：用户表达了「想要某件事发生」，但权威层尚未确认。随请求生命周期存在，可以驱动一次变更请求；在确认之前不进入事实层，也不应长期驻留在镜像中冒充事实。

两个最危险的误用，立项时就要写进纪律：

- **镜像最危险的误用**：把「乐观写入的值」在成功路径上手动“转正”。一旦转正，镜像就变成了第二条事实源。正确做法：乐观写入只是一次可撤销的猜测，成功路径最终仍要经过「失效 → 重新从事实源获取」来收敛，或由落定时的对账覆盖为权威值。
- **意图最危险的误用**：把「用户想要」直接当作「已经发生」来渲染长期状态。意图可以驱动乐观镜像，但镜像的合法性最终由事实源在落定时裁决。

规划原则：

- 每份事实指定**唯一权威读取函数**，全部界面表面从它读；出现第二个读取口，就是未来不同步的种子。
- 每个事实回答三件事：谁写它、谁读它、写完之后哪些读者要更新。答案必须来自登记表，不靠开发者记忆。
- 信号表达「该重新看了」，查询回答「现在是什么」。信号可以丢，查询不会骗人——所以信号永远只是刷新的触发器，不是数据本身。
- 乐观更新是给用户的借据：先显示意图，落定后必须用权威回读对账；对不上就以事实源为准收敛，不许拿本地旧值硬顶。

## 先区分「推」「拉」和「兜底轮询」

三条同步通路各管一段，不能互相代替，也不能只选一条：

- **推（事件/信号）**：落定即刻通知，负责「快」。信号只当触发器，携带领域标识和单调版本号，**不携带完整数据**——带数据的信号会引入「广播值是否最新」的竞态。
- **拉（权威回读）**：收到触发后向事实源重读，负责「准」。数据永远来自查询，不来自信号载荷。
- **兜底（定时/延迟再刷）**：信号丢失、乱序、比落盘晚到时负责「不漏」。低频的兜底轮询或延迟二次刷新，是信号丢失时唯一的保险。

这套「事件管快、查询管准、兜底管不漏」的结构，在桌面单用户场景下是有意选择的简化架构，不是妥协；业界桌面实践（无 WebSocket、无同步引擎、事实源唯一、客户端只重取不合并）与它同构。

**立项时必须把三通路各缺一路的陈旧边界写成一句话**，放进设计文档：

- 只有推、没有拉：接收端不知道「去哪里拿准确值」，只能用信号载荷就地拼凑——载荷不完整或乱序时，镜像停留在错误值且没有恢复入口。
- 只有拉、没有推：感知延迟上限等于轮询间隔；轮询因休眠、失焦、调度暂停时，延迟远超标称值。
- 只有推和拉、没有兜底：一次丢失的信号让镜像无限期陈旧，且无人知晓。
- 三者齐备时，残余陈旧窗口只剩一种：从「信号丢失」到「兜底下一次触发」之间。**写明这个窗口的预期上限**（例如“信号丢失时，镜像陈旧不超过兜底间隔”），而不是假装同步层可以做到零窗口。

## 按命令和事实核对同步需求

不要只看「保存成功了」，就认定所有界面都会自己变好。对项目的每个命令逐项填写：

| 命令 | 改变的事实 | 需要刷新的表面 | 刷新时机 | 失败/部分失败 |
|---|---|---|---|---|
| 保存 X | 事实 A、B | 表格 P、徽标 Q、详情 R | 落定即刻 + 延迟兜底 | 回滚并提示；成功者保留 |
| 执行 Y | 事实 C、状态 S | 队列 Z、状态栏 W | 阶段推进各一次 | 失败原因随事实呈现 |

表格是调查清单。凡是出现「这个命令不用刷 X，因为……」的推理，都必须写成显式规则进统一层，而不是散落在触发它的按钮代码里——散规则就是漏的来源。

## 建立统一落定同步层（核心）

把「命令落定后同步界面」实现为**一个统一入口**。任何命令、任何类型、任何成败，都走同一条路，不各拼各的刷新逻辑。

统一层的固定三步（与乐观更新的落定语义对齐：无论成败都在落定时刻对账，而不是成功时手动写结果、失败时才对账）：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 落定即刻 | 权威刷新：重读全部受影响事实 + 失效对应镜像 | 落定即对账，不依赖成功路径手动写结果 |
| 延迟兜底 | 短暂间隔后再做一轮同样的刷新 | 给失效信号一个「追上来」的窗口；级联变化的后续领域也能覆盖 |
| 失效登记 | 命令声明自己改变了哪些事实/投影标识，只失效这些 | 失效遗漏变成可审计的缺口，而不是悄无声息的陈旧点 |

三条纪律：

- **统一入口只有一条**。所有按钮、弹框、自动化流水线落定后都调它；业务代码里不允许出现第二个「自己刷新自己」的路径。
- **刷新动作幂等**。重复调用不产生副作用、不白涨版本号、不重复入队；落定刷一次、兜底刷一次、焦点恢复再刷一次，都安全。
- **失效条件从宽**。宁可多失效一个相邻查询，也不要为省一次重取漏掉一个可能陈旧的投影——桌面单用户场景下，前者几乎总是更便宜。

## 乐观更新的纪律

乐观更新（先改界面、等后端确认）能显著改善手感，但它的标准形状是固定的：

> 取消在途刷新 → 快照旧值 → 写入乐观值 → 落定时从事实源对账；失败默认**重新获取真实状态**，只有重取本身不可靠时才回滚到快照。

配套纪律：

- 乐观写入的是**意图**，不是事实；界面上必须能区分「已确认」与「乐观占位」。
- **成功路径不手动“转正”乐观值**——等失效信号触发重读，事实源说了算。转正就是制造第二条事实源。
- 失败默认重取事实源，而不是回滚到本地旧值：乐观写入期间事实源可能已被别的路径修改，本地旧值未必是合法回滚点。
- 乐观写入前先取消在途的重取，避免旧响应落地覆盖乐观值；落定时刻统一失效对账。
- 回滚/失败时告诉用户原因和下一步（重试入口或详情入口），不能让界面悄悄退回去就算完。
- 同一事实的并发乐观更新要有先后裁决（如请求序号、版本号），乱序到达的旧响应不许覆盖新响应。

## 生命周期与边界场景

以下场景在设计评审时必须逐条给出答案；任何一条没有规划，都会在后期表现为「偶发不同步」。

- **窗口重新获得焦点**：用户切回窗口看到的不应是旧数据。焦点恢复是一次失效时机。
- **系统从休眠恢复**：休眠期间外部数据可能已变，兜底轮询也可能暂停过；恢复后触发一轮重查，而不是等用户手动刷新。
- **外部进程修改数据**：探测逻辑收进同步枢纽（或统一入口），外部变更产出与内部变更相同的失效信号；不许前端各处自己轮询数据库。
- **高频变更**：同一事实的高频变化在同步入口做合并/节流，防止风暴打爆界面；但节流不能破坏版本标识的单调性。
- **监听器生命周期**：每个信号订阅都必须与组件/窗口生命周期绑定并在销毁时清理。监听器泄漏的表现是「看起来在同步、实际在错乱」，最难排查。
- **服务启停**：所有后台探测、兜底任务挂在启动/关闭生命周期上，具备可取消的上下文；不依赖进程退出来“自然终止”。
- **多窗口并发**：写操作在权威层串行化；信号广播后各窗口以重新获取到的事实为准，前端不做跨窗口的冲突合并。主从窗口的投影标识以实体为锚点。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 操作成功但表格没变 | 刷新规则散落各处且带条件，这一处漏了；或信号名拼错/未注册导致监听器静默不触发 | 统一落定同步层；信号类型化注册进构建，拼错在构建期暴露 |
| 界面先变对又闪回旧值 | 在途的旧响应后到，覆盖了新数据；或失败时回滚到了已过期的本地快照 | 乐观写入前取消在途重取；落定统一从事实源对账 |
| 两个界面显示同一事实的两个值 | 两个读取口各读各的缓存；或一处走乐观、一处走失效，时序不同 | 每份事实唯一权威读取函数；镜像只经失效→重取改变 |
| 重启后某列全部空白 | 该事实只住在内存里，落定刷新救不了重启 | 登记哪些事实会丢；要么落盘要么明示空态 |
| 批量操作只有一半同步 | 逐条落定逐条刷，最后一条落定 ≠ 全批落定 | 按「轮/批」聚合收口，收口才刷一次 |
| 连点后出现重复操作 | 刷新与入队幂等没保障，或按钮未按在途状态禁用 | 幂等键 + 在途禁用，统一进同步层 |
| 弹框里是旧数据，关掉再看是新的 | 弹框快照了打开那一刻的数据，不随后续刷新走 | 弹框读同一权威源，或打开时强制重读 |
| 高频操作后状态反复抽搐 | 事件风暴逐条触发重取，与乐观写入、落定对账互相踩踏 | 同步入口合并/节流；乐观写入前取消在途重取；落定统一收敛 |
| 信号发了界面没动 | 监听器泄漏（旧实例在响应）或绑定到错误的投影标识 | 订阅与生命周期绑定并清理；投影标识与领域/实体对齐 |
| 两个窗口一个变一个不变 | 某窗口的变更没走统一入口；或投影标识粒度与信号粒度不匹配 | 所有变更走同一枢纽；标识按领域/实体对齐 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

自动化测试先覆盖不依赖界面的纯逻辑：失效规则（改 A 只失效 A）、幂等（重复刷新不涨版本）、乱序拒绝（旧响应不覆盖新响应）、统一入口唯一性（不允许旁路刷新路径存在）、一致性冒烟（从**非 UI 路径**修改事实——外部写库、CLI、直接改文件——所有打开的表面应在兜底窗口内自动收敛；这个入口不存在，同步层就只是「UI 操作路径上成立」，不是架构级成立）。

随后制定手工验收矩阵。至少考虑：

| 维度 | 要覆盖的情况 |
|---|---|
| 操作类型 | 每个命令至少一次成功 + 一次失败 + 一次部分失败 |
| 表面 | 每份事实的每一个读者（表格、徽标、弹框、状态栏、别的页签） |
| 时序 | 落定瞬间切页、快速连点、信号与查询赛跑、慢网/断线恢复 |
| 生命周期 | 首次使用、重启后、批量中途失败、多窗口并发、焦点恢复、系统唤醒 |
| 缩放与平台 | 不同缩放档位、不同窗口尺寸（涉及几何的同步） |

每次验收记录：操作前后的界面状态、信号到达顺序、刷新次数。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先盘点仓库的命令清单、事实清单、每个事实的全部读取口和现有刷新调用点。开始改代码前，先给出命令-事实影响表、事实读取登记表和统一同步层规则；不得在各业务代码里散落条件刷新，不得让任何事实存在第二个权威读取口，不得用本地旧值回滚权威数据，不得假设信号必达且有序。所有同步信号必须类型化注册，拼错在构建期暴露。乐观更新遵循「取消在途 → 快照 → 写入 → 落定从事实源对账」的形状，成功路径不手动转正乐观值，失败默认重取事实源。刷新幂等；兜底不可省略，兜底间隔与残余陈旧窗口写入设计说明。事件订阅与后台探测的生命周期清理成对出现。失效条件从宽不从窄。实现后补失效规则、幂等与乱序拒绝的回归测试，补一次非 UI 路径的一致性冒烟，并明确列出未覆盖的时序组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。
