# 发布交付流水线：Wails3 + Go 专用方案

## 附录：Go 破坏性变更判定表（源自 spf13/go-skills 的 go-release 技能，MIT 许可，Steve Francia）

发版即承诺：tag 推送并经模块代理被获取后即不可变。给 Go 模块/应用发版前，按此表判定变更是否破坏：

| 变更 | 破坏？ | 原因 |
|---|---|---|
| 删除/改名任何导出标识符 | **是** | 显然 |
| 改函数/方法签名 | **是** | 加变长参数也算——签名变了 |
| **给导出接口加方法** | **是** | 所有外部实现者不再满足该接口 |
| 给结构体加字段 | 通常否 | **破坏使用非键名复合字面量的调用方**；文档声明只用键名字面量则安全 |
| 新增函数/类型/包 | 否 | minor 版本的职责 |
| 改未类型化常量的值 | **是** | 编译进调用方二进制 |
| 收紧输入校验 | **行为上算** | 原来能跑的现在报错——按破坏对待 |
| 提 go.mod 的 go 指令 | **实际算** | 旧工具链的下游编不过你 |

**机械验证而非目测**：`go run golang.org/x/exp/cmd/gorelease@latest`（对比最近一次发布，报告不兼容并建议正确版本号）；进 CI 对触碰导出标识符的 PR 强制执行。

**弃用是加法逃生门**：`// Deprecated: Use [X] instead.` 段落必须以 `Deprecated:` 开头；v1 上被弃用 API 永远可用；**Go 1.26+ 加 `//go:fix inline` 指令，`go fix ./...` 自动把调用方改写到替代品**——发版说明里写上这条迁移步骤。

**go.mod 卫生**：`go` 指令是对下游的门槛（按需最低，不为一个新 helper 轻提）；`toolchain` 只是本机偏好；**永不 tag 含 replace 指令的版本**（下游构建中被忽略）；tag 前 `go mod tidy`。

**WAILS_MCP 提醒**：本方案「CI」阶段产出的桌面应用，开发期以 `WAILS_MCP=1` 启动可内嵌 MCP 服务器供 AI agent 驱动真实应用做验证（→《Wails3框架版本判别与服务纪律方案》、交付清单项目期验证清单第 8 条）。

## 定位与硬性目标

母法方案：《签名打包与更新分发技术方案》。母法管「从构建产物到用户机器上运行并安全更新」的整条链；本方案管**操作序列**——代码改完之后，按什么顺序做哪几件事、每件事的门禁是什么、失败停在哪、发布文档按什么格式写。

版本号清单、单源注入与平台映射 →《版本号方案》。签名、公证、更新流水线与回滚 → 母法。本方案不重复它们的设计，只规定它们在交付链里的**位置与先后**。

**硬性目标**：

1. 交付链每一步有门禁，门禁红即停，不静默跳过；
2. 本机重装验证在推送之前——推送的代码就是装过的代码；
3. 发布说明从结构化条目生成，格式固定，不手写排版；
4. 版本号、标签、包内版本、Release 标题四处一致（→《版本号方案》三处断言门）。

## 核心设计

### 交付链的固定形状

交付是一条有先后依赖的流水线。顺序不能调——调了等于让未验过的代码到达用户。

| 阶段 | 步骤 | 做什么 | 门禁（红即停） | 失败时 |
|---|---|---|---|---|
| 本地开发 | 1. 编码与测试 | 改代码、跑测试、跑门禁脚本 | 测试全绿 + 门禁全过 | 修到绿再继续 |
| 本地开发 | 2. 提交 | `git commit`，工作区干净 | 无未提交的跟踪文件改动 | 先提交或暂存 |
| 定版 | 3. 递增版本号 | 脚本改权威源（如 `wails.json`）+ 同步打包配置 | 版本号形状合法、两处一致 | 脚本报错即停 |
| 本机出包 | 4. 构建 + 打包 | 门禁 → 测试 → 构建 → 出安装包（deb/rpm/AppImage 或 dmg/exe） | 构建成功 + 产物版本 == 权威源 | 不出包就不往下走 |
| 本机出包 | 5. 还原入库占位 | 构建会覆盖入库的占位文件（如 `dist/index.html`），从备份还原 | 还原后 sha256 == 备份 | 不还原就提交会把构建产物混进源码 |
| 本机重装 | 6. 推送触发 pre-push 钩子 | 验树干净 → 建包 → 关停应用 → 装包 → 验装机版 → 拉回应用 | 每一步失败阻断推送 | 推送被挡，修完再推 |
| 推送 | 7. 推 main | `git push origin main` | 远端 SHA == 本地 HEAD | 冲突先解 |
| 打标签 | 8. 打标签 + 推标签 | `git tag v<版本>` → `git push origin v<版本>` | 标签指向 HEAD；远端无同名标签 | 同名标签已存在则先裁决 |
| CI 出包 | 9. 三平台并行构建 | 标签触发 CI，三个原生 runner 各出各平台的包 | 任一平台构建失败不阻塞其余，但 Release 作业等全部完成 | 失败平台无产物，Release 缺件 |
| CI 签名 | 10. 签名 + 校验 + 清单 | Ed25519 签名 → checksums → manifest → 公钥守卫 | 内嵌公钥 ≠ 签名私钥 → 拒绝发布 | 不发布，修密钥 |
| CI 发布 | 11. 创建 Release | 正文取仓库根的发布说明文件，附件挂全部产物 + 签名 + 校验 | 发布说明文件缺席即红 | 不发布 |

**三条纪律**：

- **本机重装在推送之前**：pre-push 钩子建出来的包就是从 HEAD 构建的，装完验过才放行推送。推送之后 CI 再建一遍是云端验证，不替代本机验证。
- **定版在出包之前**：版本号先递增、先提交，再构建。不允许「先出包再补版本号」——那会让包内版本与标签对不上。
- **发布说明在打标签之前**：说明文件随定版提交一起入库，CI 只读不写。打标签时说明已经定稿。

### 两种仓库、两条流水线

不是所有仓库都需要本机重装。按仓库类型分：

| 仓库类型 | 例子 | 交付链 | 发布文档 |
|---|---|---|---|
| **桌面应用** | Wails3 + Go 产品 | 完整 11 步（含本机重装 + 三平台 CI 出包 + 签名） | 单版净变化文件（如 `release-notes.md`），作为 GitHub Release 正文 |
| **指南 / 组件库** | 本库（guides） | 提交 → 推送（CI 跑门禁 + 打包 + 部署 Pages）→ 打标签（CI 创建 Release） | 累积版本史（如 `RELEASES.md`），CI 从中提取本版段落作为 Release 正文 |

桌面应用多了「定版 → 本机出包 → 本机重装」三步，因为用户装的是二进制包，必须在推送前验证「装上去能跑」。指南库没有安装步骤，推送即部署。

### 发布文档的两种格式

#### 格式 A：单版净变化（桌面应用用）

每次发版写一份独立文件，只写**本版相对上一版改了什么**，不写历史累积。由脚本从结构化条目生成，格式固定：

```
## English

### <产品名> <版本号> What's Changed from <上一版本> to <版本号>

**Version type: Stable**

**Added**

- 一条一行，动词开头

**Changed**

- …

**Fixed**

- …

**Removed**

- …

## 中文

### <版本号> 相比 <上一版本> 更新内容

**版本类型：稳定版**

**新增**

- …

**修改**

- …

**修复**

- …

**删除**

- …
```

**规则**：

- 英文在前、中文在后；两种语言各收在自己那一段里，顶部不放中英混排行。
- 四类固定标题：Added / Changed / Fixed / Removed（新增 / 修改 / 修复 / 删除）。某类为空则整类不出现。
- 每条一行、动词开头、说人话。不写验真过程、不写冻结数字、不写「未提交」「未推送」。
- 预览版把 `Stable` 换成 `Preview`、`稳定版` 换成 `预览版`。
- 条目文件每行 `分类|语言|内容`（如 `added|zh|加一颗 AppImage 安装包`），脚本排标题与空行，人只写条目。
- 上一版本从本地标签按版本序取，不手写。

#### 格式 B：累积版本史（指南 / 组件库用）

所有版本记在同一份文件里，最新版本在最上。CI 打标签时从中提取本版段落作为 Release 正文。

```
### vX.Y.Z — YYYY-MM-DD

**【新增 / Added】**

        1. 条目一

        2. 条目二

**【修复 / Fixed】**

        1. …

**【更新 / Updated】**

        （无 / none）

**【其他 / Other】**

        1. …
```

**规则**：

- 四类固定标题：【新增】【修复】【更新】【其他】（Added / Fixed / Updated / Other）。
- 编号条目（1. 2. 3. …），每条起始处缩进 8 个空格（以 8 个 `&nbsp;` 实现），编号手写以保证双语一致。
- 某类无内容时放一行 8 空格缩进的「（无）/ (none)」。
- 双语镜像：English 段与中文段互为镜像，任一语言新增条目时另一语言同步（含编号）。
- 顶部语言切换锚点跳转。

#### 两种格式不混用

格式 A 是**一次性文件**，发完版就留在那儿当历史存档，下一版写新的。格式 B 是**累积文件**，每次发版往最上面加一节。桌面应用用 A（Release 正文只需要本版净变化）；指南库用 B（仓库本身就是版本史的载体）。

### 本机重装钩子的设计

pre-push 钩子是交付链里最容易出错的一环。它的设计纪律：

1. **快速失败在前，动用户应用在后**：先验树干净、验安装类型、验路径归属，全部通过才关停应用。树不干净时不动用户正在跑的程序。
2. **装完验三件事**：包状态是 `install ok installed`、可执行文件在预期路径、用户数据目录没丢。
3. **关停与拉回对称**：只有关停过的才拉回；本来没跑的不越权启动。拉回失败只提醒不挡推送——包已装好，推送该放行。
4. **占位文件有 trap 还原**：构建会覆盖入库占位文件，钩子用 `trap … EXIT` 保证无论成败都还原。
5. **免密优先、交互兜底**：有 sudoers NOPASSWD 规则就走免密，没有就回退到交互式输密码。两条路装的包一样，只是授权方式不同。
6. **跳过开关**：环境变量（如 `PHPO_PRE_PUSH_DRY_RUN=1`）只打印计划不执行，供调试。

### CI 出包的版本裁决

CI 不信任标签名或手动输入的版本号——它从权威源（如 `wails.json`）现读，与标签剥掉预发布后缀后比对，不一致即拒绝发布。这保证：

- 手动 dispatch 时不会拿分支名当标签；
- 标签与包内版本不会对不上；
- 预览版后缀只认 `-beta.N`，别的形状一律拒。

标签已存在但指向别的提交时同样拒绝——构件与 Release 必须挂在同一个提交上。

## 验收清单

| # | 检查项 | 怎么验 |
|---|---|---|
| 1 | 交付链 11 步顺序不可调 | 走查脚本 / 钩子代码：定版在出包前、重装在推送前、说明在标签前 |
| 2 | 门禁红即停 | 注入一个失败（如测试红），确认后续步骤不执行 |
| 3 | 本机重装验三件事 | 装完后断言包状态 + 可执行文件 + 数据目录 |
| 4 | 占位文件还原 | 构建前后 sha256 一致；钩子失败后也一致 |
| 5 | 版本号四处一致 | 权威源 == 包内版本 == 标签（剥后缀）== Release 标题 |
| 6 | 发布说明格式 | 格式 A：四类标题、英前中后、空类不出现；格式 B：编号 + 8 空格 + 双语镜像 |
| 7 | 发布说明缺席即红 | 删掉说明文件，CI 拒绝创建 Release |
| 8 | 公钥守卫 | 内嵌公钥 ≠ 签名私钥时拒绝发布 |
| 9 | 标签指向 HEAD | 标签指向别的提交时 CI 拒绝 |
| 10 | 钩子跳过开关 | dry-run 只打印不执行 |

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出交付链的步骤表（每步：做什么 / 门禁 / 失败时停在哪），顺序必须是「提交 → 定版 → 本机出包 → 本机重装 → 推送 → 打标签 → CI 出包 → 签名 → 发布」。本机重装在推送之前，由 pre-push 钩子执行：验树干净 → 建包 → 关停应用 → 装包 → 验装机版与数据目录 → 拉回应用；任一步失败阻断推送。定版用脚本改权威源并同步打包配置，不允许手工抄版本号。发布说明从结构化条目（`分类|语言|内容`）由脚本生成，格式固定（英前中后、四类标题、空类不出现），随定版提交入库；CI 只读不写，缺席即红。CI 版本裁决从权威源现读，与标签剥后缀比对，不一致拒绝发布；公钥守卫在签名前执行。指南 / 组件库仓库无本机重装步骤，发布文档用累积版本史格式（编号 + 8 空格缩进 + 双语镜像）。实现后跑验收清单，未覆盖的步骤标为未验。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位

- **二档**：交付链步骤表 + 本机重装钩子 + 占位文件还原（对应主大纲「本地重装门禁」与「CI 基础门禁」）。
- **四档**：发布说明格式与生成脚本、CI 版本裁决、公钥守卫、三平台并行出包（对应主大纲四档发布链条目）。
- 母法《签名打包与更新分发技术方案》管更新流水线与回滚；本方案管「从代码到 Release」的操作序列，两者在「CI 出包」一步衔接。
