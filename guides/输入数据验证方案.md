# 输入数据验证：通用规划方案

## 这份方案是做什么的

库里已有两块验证相关的碎片：《安全边界与权限技术方案》定了「前端传入皆不可信、校验在 Go 侧」的边界纪律；《多平台一致组件库方案》定了表单校验的 UX 时机（组合态不校验、blur / 提交校验）。缺的是把所有输入点串起来的**验证架构**：分几层、每层管什么、规则定义在哪、错误怎么输出。

**硬性目标**：
1. 每个输入点（不止表单——导入、粘贴、拖放、deep link、CLI、同步下行全是输入）都登记**验证层与规则来源**；
2. 校验规则**定义一次**，双端共用，parity 门防漂移；
3. 错误输出**结构化**（字段 + 码 + 参数），文案由码表出——验证层不产文案。

## 四层校验职责（每层有存在理由，不互相替代）

| 层 | 校验什么 | 为什么存在 |
|---|---|---|
| **展示层**（前端组件） | 格式提示、必填、即时反馈 | 纯体验优化——**不算数**，可被绕过（API 直调、CLI、同步） |
| **入口边界**（Go `binding/`） | 类型、取值范围、归属、权限、路径合法性 | 不可信输入的**强制门**（→ 安全方案：绑定类型不算校验） |
| **领域层** | 业务不变式（余额非负、状态机转移合法、唯一性） | **唯一权威**——任何入口（UI / CLI / 同步 / 导入）都必经，不得因「前端已验」省略 |
| **存储层** | 约束兜底（not null / unique / FK / check） | 最后一道防线，防的是代码 bug 不是用户 |

判定规则一句话：

> **上层校验为体验，下层校验为正确性。** 判断一段校验该放哪层：绕过 UI 的路径（CLI、同步、导入）还能绕过它吗？能 → 它不配做正确性校验，正确性版本必须同时在领域层。

## 规则单源：定义一次，双端生效

- 校验规则（必填 / 长度 / 范围 / 格式 / 枚举）定义在 **Go 的数据模型上**（struct tag 或 schema，与《配置文件方案》的 schema 单源同哲学），**生成或投影**给前端做展示层提示（JSON Schema / 生成的校验模块，生成方式随锁定版本待验证；无生成则手维护 + parity 测试门）。
- **规则 ID 即错误码**：每条规则一个稳定 ID，进错误码表（→《日志与可诊断性技术方案》parity 门），文案键化（→《多语言实现方案》）。
- 领域不变式**不住 tag 里**：跨字段、需查库、涉及状态机的规则放领域服务——tag 只承载无状态结构性规则。混在一起是「验证散落」的开始。

## 规范化先于校验

校验一个未规范化的值，结果必然漂移：

- **入口边界一次性规范化**：去首尾空白、Unicode NFC、路径清理、邮箱/域名小写、全半角归一（CJK 场景必坑）；
- **展示格式永不入库**：日期存 ISO、数字存原始值（→ 国际化方案「数据归数据」）；用户按 zh-CN 输入的「2026/11/4」在入口转为规范值再校验；
- 规范化只做一次、集中一处（入口边界），不散落在各领域重复实现——两处规范化不一样宽，就是新的不一致源。

## 错误输出协议

- 结构化错误：`{field, code, params}`——`code` 指向码表，`params` 填充文案占位（「长度需在 {min}–{max} 之间」）；**验证层绝不拼接人话文案**，更不回传原始异常（内部信息泄漏，→ 安全方案）。
- **一次报完**：收集全部错误一次性返回，不逢错即停（与《配置文件方案》逐键降级同一哲学）；表单逐字段呈现（→ 组件库 FieldLabel / 错误呈现）。
- 领域层错误同样走码表——「余额不足」与「格式错误」在 UI 上呈现方式一致，只是码不同。

## 全部输入点（表单之外勿漏）

| 输入点 | 易漏的校验 |
|---|---|
| 文件导入 / 拖放 | 文件大小、类型嗅探（不信扩展名）、编码、行数上限 |
| 粘贴 | 富文本消毒（→ 安全方案）、长度、格式 |
| deep link / 文件关联 | 已是安全方案重点：结构化 ID + 路径规范化 |
| CLI 参数 / 配置文件 | 走同一领域层校验（CLI 是绕过 UI 的合法路径——它必须被验证而不是被信任） |
| **同步下行数据** | 他端设备也是不可信对端：下行变更过领域层不变式（→《多端数据同步方案》——裁决后的合并值同样要验） |
| 剪贴板 / 外部 URL | scheme 白名单 |

**登记表**：全部输入点 × 各自验证层 × 规则来源，一张表管完——有登记才有审计，散落即漂移。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 分层 | 绕过 UI 的每条路径（CLI / API 直调 / 同步下行）触发领域层校验 |
| 规则 | 双端 parity：同一非法值前端提示且后端拒绝；规则改动两侧同步 |
| 边界 | 每字段：空、超长、极值、类型混淆、全半角、前后空白、Unicode 组合字符 |
| 规范化 | 「 2026/11/4 」与「2026-11-04」等价入库；NFC/NFD 视为同串 |
| 错误 | 结构化输出、码表命中、多错误一次报完、文案键化无硬编码 |
| 攻击 | 超长嵌套、特殊字符、注入向量（→ 安全方案恶意用例矩阵） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 直调 API / CLI 能写入脏数据 | 只有展示层校验 | 四层职责表 + 绕过路径审查 |
| 两处提示规则不一样 | 规则双端手抄 | 规则单源 + parity 门 |
| 错误文案五花八门 | 验证层拼人话 | 结构化错误协议 |
| 搜不到刚存的记录 | 未规范化（空格 / 全半角 / NFD） | 入口一次性规范化 |
| 领域不变式被导入绕过 | 不变式写在 UI 或边界层 | 不变式只住领域层 |
| 打字时校验打断输入法 | 组合态即校验 | 组件库校验时机纪律 |
| 日期按机器区域漂移 | 格式化字符串入库 | 规范化 + 规范值入库 |
| 新输入点忘了验证 | 无输入点登记表 | 登记表 + 评审对照 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出输入点登记表（输入点 × 验证层 × 规则来源）。校验规则定义在 Go 数据模型单源并投影/生成到前端展示层，parity 门进 CI；结构性规则用 tag、领域不变式只住领域服务，任何入口（UI / CLI / 同步 / 导入）必经；入口边界一次性规范化（空白 / NFC / 路径 / 全半角 / 日期数字规范值），展示格式永不入库；错误输出 `{field, code, params}` 结构化、一次报完、文案走码表键化，绝不回传原始异常。不得在展示层做正确性校验、不得在领域层省略已在前端出现的规则。实现后补绕过路径、边界值、规范化与 parity 的回归测试，并明确列出未覆盖的输入点。

方案确认后再改代码；生成投影的机制随锁定的框架版本核实，与安全方案的边界纪律冲突时以安全方案裁决。

## 五档定位

- **一档**：输入点登记表初稿 + 分层职责决策 + 规则单源选型。
- **二档**：边界与领域层校验落地、错误协议与码表接线、规范化模块。
- **三 / 四档**：全部输入点覆盖、攻击矩阵、双端 parity 全量验证。
