# 版本号：Wails3 + Go 专用方案

## 这份方案是做什么的

主大纲一档「版本号单一源」只列了准入问题；《签名打包与更新分发技术方案》引用它。本方案给出**版本号的完整设计**：一个应用不止一个版本号——每个版本号列清单（内容 / 权威源 / 消费者）、定构成规则、做单源实现与校验门、处理三平台打包格式映射与版本比较。

**硬性目标**：
1. 每类版本号**一个权威源**，产物版本从源自动推导；
2. 任何日志、诊断包、崩溃报告都能回答「这是哪个版本、哪次构建」；
3. 版本比较交给库，不手写字符串比较。

## 版本号清单（一个应用不止一个版本号）

| 版本 | 内容 | 权威源 | 消费者 |
|---|---|---|---|
| **应用版本** | semver，用户可见 | 仓库根 `version` 文件（或单一常量包） | 关于页、日志、更新判断、打包 |
| **构建元数据** | commit 哈希、构建时间、构建号 | CI 注入 | 诊断包、崩溃还原 |
| **数据 schema 版本** | 每类持久文件独立 | 各 schema 定义（→ 状态方案） | 迁移与降级守卫 |
| **码 / 枚举版本** | 引入版本登记 | 码表登记表（→ 状态码方案） | 弃用与兼容判断 |
| **插件 apiVersion** | 扩展契约大版本 | 插件 API 定义（→ 插件扩展方案） | 握手拒载 |
| **平台打包版本** | 各平台格式 | 由应用版本**推导生成** | 安装器 / 商店 |
| **引擎基线版本** | 三引擎能力基线 | 引擎基线文档（→ 组件库方案） | 兼容性核查 |

**纪律**：清单上的每个版本号**独立演进、互不混写**——「把数据 schema 版本号当应用版本用」是版本混写事故的开端。新增版本号先进清单再进代码。

## 应用版本的构成与语义纪律

- **semver**：`MAJOR.MINOR.PATCH` + 预发布（`-beta.1`）+ 构建元数据（`+build.123`，不参与比较）；
- **语义判定规则**（立项写明）：MAJOR = 数据或契约破坏性变更（配置不可迁移、同步协议不兼容）；MINOR = 新功能；PATCH = 修复。「感觉差不多就升 PATCH」的随意性由规则拦住；
- **预发布 = 通道**：beta 通道即预发布标签（→ 分发方案灰度）；正式通道永不收到预发布版本（比较规则保证）；
- 构建元数据解决「版本相同内容不同」：同 semver 的两次构建以构建号区分，产物可追溯到 commit。

## 单源实现与校验门

- **源**：仓库根单一 `version` 文件（或 `internal/version/` 单常量包）——**禁止第二处定义**（grep 审查零例外）；
- **注入**：构建期经 ldflags / 生成代码写入二进制（wails3 构建任务的具体机制**待验证**）；打包配置由构建流程**从源读取**，不手工抄（主大纲准入问题的答案）；
- **校验门**：CI 断言「构建产物内嵌版本 == 源版本 == 打包配置版本」三处一致——不一致明确失败（主大纲「一致性校验门」模式）；
- **运行期可查**：关于页、日志（每条日志的最小字段集含版本 → 可诊断性方案）、诊断包三处读同一注入值。

## 三平台打包格式映射

| 平台 | 字段 | 约束 |
|---|---|---|
| Windows | `FILEVERSION`（四段数值）与 `ProductVersion`（semver） | 四段数值由 semver + 构建号推导映射 |
| macOS | `CFBundleShortVersionString`（用户可见 semver）与 `CFBundleVersion`（单调构建号） | **构建号只增不减**——倒退会被系统/商店拒绝 |
| Linux | deb/rpm 包版本 | 遵循发行版字符集与比较规则 |

- 映射**由源自动生成**，映射规则随打包矩阵登记（→ 分发方案）；生成器三平台产物逐个验证（各平台格式约束不同，映射 bug 只在产物上现形）。

## 版本比较与更新决策

- **semver 库比较**，禁止手写字符串比较（`"0.10" > "0.9"` 这类事故）；预发布排序按 semver 规范（`beta.2 > beta.1`、正式版 > 同版本预发布）；
- **更新判断** → 分发方案更新流水线（清单比较用同一比较库）；
- **降级不靠版本号**：回滚是分发方案的机制（保留旧版 + 原子切换），不是「装个更小的版本号」——版本号只描述，不执行；
- 同版本不同内容：以构建元数据区分，比较规则只认 semver 部分。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 单源 | 全库 grep 第二处定义零命中 |
| 注入 | 产物内嵌版本 == 源 == 打包配置（三处断言） |
| 映射 | 三平台打包产物版本字段逐个验证（含 FILEVERSION 四段推导） |
| 比较 | 预发布排序、跨通道判断、回退场景不误判 |
| 可观测 | 关于页 / 日志 / 诊断包三处版本一致 |
| 通道 | beta ↔ stable 转换的版本判断（→ 分发方案矩阵） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 关于页与安装包版本不一致 | 多处定义、手工抄 | 单源 + 三处断言门 |
| beta 用户永远收不到正式版（或反之） | 手写字符串比较、预发布规则错 | semver 库 + 比较测试 |
| 用户报障说不出版本 | 运行期版本未接线 | 三处可观测 |
| macOS 构建被拒 | `CFBundleVersion` 倒退 | 构建号单调规则 |
| 升级后数据迁移没跑 / 跑错 | schema 版本与应用版本混写 | 版本清单分治 |
| 同版本重装行为不同 | 无构建元数据 | 构建号 + commit 注入 |
| 更新清单把旧版当新版 | 自写比较逻辑 | 统一比较库 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出版本号清单（每类：内容 / 权威源 / 消费者）。应用版本单一源（version 文件或常量包，禁止第二处），构建期注入，CI 断言源 / 产物 / 打包配置三处一致；平台打包格式由源自动生成映射，`CFBundleVersion` 单调递增；semver 比较一律用库，预发布排序按规范；schema 版本、码表版本、apiVersion 独立演进不与应用版本混写；关于页 / 日志 / 诊断包三处接同一运行期值。构建注入机制随锁定的框架版本待验证。实现后跑测试矩阵，并明确列出未覆盖的平台与场景。

方案确认后再改代码；版本方案属发布契约，AI 给结构与映射推演，最终版本策略由用户裁决。

## 五档定位

- **一档**：版本号清单 + 单源选型 + 语义规则（对应主大纲「版本号单一源」准入）。
- **二档**：注入与校验门、三平台映射生成器。
- **四档**：通道比较、灰度与回滚中的版本判断全量（→ 分发方案矩阵）。
