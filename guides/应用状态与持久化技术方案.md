# 应用状态与持久化：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把「应用的状态住在哪里、谁是权威、活多久、怎么落盘、坏了怎么活下来」放在一起考虑，避免功能分别做完后才发现：重启后设置丢失、界面闪回默认值、配置文件损坏后白屏、升级后旧数据读不出来，或同一份偏好存了两处、改哪处看运气。

它不是某个应用的实现说明，也不预设产品名、框架、存储引擎或序列化格式。每个项目都应先按自己的状态清单和框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「状态无家」。它们几乎从不来自某一个 bug，而来自一个结构：**同一份状态住在多处——内存一份、前端 store 一份、配置文件一份——各写各的、各存各的，没有一处被指定为权威**。本方案的目标是把这类结构在立项阶段就排除掉。

一个边界要先说清：**《统一同步层技术方案》管「事实变了，界面如何知道」（一致性纪律）；本方案管「状态本身的生命周期」（住哪、活多久、怎么存、怎么恢复）。** 两者在「镜像」处交接：同步层问「这个镜像谁负责失效」，本方案问「这个副本有没有资格存在」。主大纲「本地存储」一节只列准入问题（驱动、目录权限），状态与落盘的完整纪律以本方案为准。设置类状态的文件载体（格式、schema 单源、手编辑支持）另见《配置文件方案》。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **状态清单**是什么？全部状态逐条列出，每条标注四类之一（权威事实 / 派生 / 设置 / 瞬态），并写明权威住址和生命周期（进程内 / 会话 / 永久）。
2. 每条状态的**唯一权威**是谁？前端 store 里的同名副本是登记过的镜像，还是越权的第二事实源？
3. 哪些状态要落盘？落到哪类目录（配置 / 数据 / 缓存）？路径是否按平台标准放置？目录与文件权限是否收紧？
4. 落盘是否**原子**（临时文件 + 改名）？写一半崩溃后旧文件是否完好？半成品是否可能被下一次启动读到？
5. 首次启动、文件缺失、文件损坏三条路径分别怎么走？**默认值**定义在哪一份 schema 里？是否保证全部默认值只有这一处定义？
6. **schema 版本与迁移**：版本号是否写进文件？迁移函数谁写、怎么测？用户从新版本降级，旧版本能否识别并明确拒绝，而非静默损坏？
7. **启动顺序**：哪些状态必须首帧前就绪？哪些可以懒加载？未就绪时对应界面显示什么？
8. **写入纪律**：谁有权写？是否收敛到唯一写入口？校验发生在哪一层？
9. **多窗口 / 多实例**：有单实例锁吗？两个窗口同时改同一设置，谁赢、另一方如何感知？
10. **敏感状态**（令牌、密钥、凭据）存在哪？是否与普通配置分离、权限是否收紧、是否被排除在日志与诊断之外？
11. **重启恢复清单**：窗口几何、页签、滚动位置、未提交草稿，各恢复什么？「有意不恢复」清单是否也写下来了？
12. **测试矩阵**：进程强杀、文件损坏、跨版本升级、全新安装、双窗口并发，各有没有自动化或手工用例？

交付给 AI 的设计结果应包含：状态登记表（四类 + 权威 + 生命周期 + 落盘策略）、落盘 schema 与默认值唯一源、迁移清单、恢复清单与有意不恢复清单、损坏降级路径、测试矩阵。

## 先把状态分四类，并给出一句话判定规则

状态混类是落盘混乱的病根。立项时给出**一句话判定规则**，让代码审查能当场判定一段数据属于哪一类：

> **丢了能不能重建？** 能重建 → 派生或瞬态；是用户的显式决定 → 设置；其余 → 权威事实。

- **权威事实**：丢失后无法从其他状态重建（或重建代价不可接受）。落盘；唯一权威在存储层；只经唯一写入口改变。
- **派生**：可由事实 + 规则重建。不落盘——落了也只是缓存，必须登记失效责任（→《统一同步层技术方案》的镜像纪律）。
- **设置**：用户显式改变的偏好。必须落盘、必须跨版本可读、必须可重置。
- **瞬态**：选中项、滚动位置、临时光标。默认不落盘；确要「记住」的（如上次页签），在登记表里**显式升级为会话状态**，而不是顺手写进设置文件。

三个最危险的误用，立项时就要写进纪律：

- **把瞬态写进设置**：用户改一次主题，顺带把半截表单永久记住。瞬态进设置必须走显式升级，不走顺手保存。
- **把事实当设置**：随使用漂移的「最近路径」被当成用户决定，下次启动行为悄悄变了。
- **把派生落盘后忘记失效**：升级后新旧两份派生值对不上，谁也不认谁。

## 生命周期与落盘时机

| 生命周期 | 含义 | 落盘策略 |
|---|---|---|
| 进程内 | 跟进程走，退出即丢 | 不落盘；登记「会丢什么」，对应界面要有空态预期 |
| 会话 / 窗口 | 跟窗口生命周期走 | 关闭时可存快照；几何与状态的恢复 →《窗口与多窗口技术方案》 |
| 永久 | 跨重启必须还在 | 落盘，且落盘时机必须显式决策 |

**落盘时机是崩溃安全的分界**：退出时才写 = 任何异常退出丢掉全部未存变更；变更即写（或去抖写、去抖须有上限）才有崩溃安全。「去抖上限」要写成数值（如最迟 N 秒落盘一次），不能是「攒够了再写」。

## 落盘纪律

- **每份持久状态一个权威模块、一个唯一写入口**。出现第二个写入口（某功能自己改配置文件）就是未来数据互相覆盖的种子。
- **原子写**：写临时文件 → 刷盘 → 原子改名覆盖。半成品任何时刻不可见。命令级与跨资源的原子提交（事务边界、收据、补偿）→《原子性提交方案》。
- **默认值唯一源**：全部默认值定义在 schema 一处；使用点只引用，不复制字面量。
- **读取收敛**：每份持久状态一个权威读取口；缓存它的地方是镜像，走同步层的失效纪律。
- **去抖落盘的实现**：去抖窗口、maxWait 与冲刷时机的统一实现 →《防抖与节流方案》（判定表 + lib 钩子）。
- **滚动备份**：覆盖写入前保留上一版（固定保留 N 份，轮换替换最旧）——损坏降级「从备份恢复」路径的物资基础；升级迁移前的预迁移备份同规执行（→ 主大纲「数据迁移与降级保护」「数据备份与恢复」）。
- **存储引擎准入核对**（与主大纲「本地存储」表对应）：驱动与并发模型、连接池配置、超时参数、预迁移备份、降级守卫、目录分离与权限，逐项核对后才选型定案。

## 启动与恢复

- **就绪分级**：首帧必须 / 首屏可后 / 惰性加载，逐条标注；未就绪的表面显示「加载中」或显式空态，不显示默认值冒充已加载。
- **损坏降级三选一**（每种持久文件预先选定并写进设计）：重命名保留坏文件 + 用默认值继续并提示；从备份恢复；明确失败并给出修复入口。**不允许的行为**是静默吞掉异常后当空文件用，或白屏。
- **恢复清单与有意不恢复清单成对出现**：恢复什么（窗口几何、页签、草稿）逐条登记；明确不恢复什么（敏感凭据的会话、临时选择）也逐条登记。没有「无意中恢复」，也没有「无意中丢失」。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 重启后设置丢失 | 退出时才落盘，异常退出没走到 | 变更即写或去抖写 + 上限 |
| 设置改了又弹回旧值 | 两个写入口各存各的；或读取缓存未失效 | 唯一写入口 + 唯一读取口；缓存走镜像纪律 |
| 配置损坏后白屏或无提示回默认 | 损坏路径从未设计 | 三选一降级路径预先选定 |
| 升级后旧数据读不出或被清空 | 文件无版本号、无迁移；或降级静默损坏 | schema 版本守卫 + 迁移函数带测试 + 降级明确拒绝 |
| 两窗口改设置互相覆盖 | 无单实例锁、无并发裁决 | 单实例锁 + 最后写入裁决 + 变更信号（→ 同步层） |
| 令牌进了日志或诊断包 | 敏感状态与普通配置同路径 | 分类分离 + 排除清单（→《日志与可诊断性技术方案》） |
| 半截表单被永久记住 | 瞬态顺手写进了设置文件 | 四类判定规则 + 显式升级才落盘 |
| 新装机器行为异常 | 默认值散落在使用点，漏了环境差异 | 默认值唯一源（schema） |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 写入时机 | 正常退出、进程强杀（kill -9）、写入中途断电模拟 |
| 文件状态 | 缺失、空文件、截断、损坏、旧版本 schema、未来版本 schema |
| 升级 | 从首个版本起逐级迁移的整条链；降级被明确拒绝 |
| 并发 | 双窗口同时改同一设置；多实例同时启动 |
| 恢复 | 按恢复清单逐项重启验证；按有意不恢复清单验证确已丢弃 |
| 备份 | 滚动备份的轮换与保留份数；从备份恢复演练；迁移前备份存在性 |

每次验收记录：写入时机、损坏注入方式、恢复后的实际状态。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先盘点状态清单，逐条按「权威事实 / 派生 / 设置 / 瞬态」标注并给出权威住址与生命周期。开始改代码前，先给出状态登记表、落盘 schema 与默认值唯一源、迁移清单、损坏降级路径。不得存在第二个写入口；不得在使用点复制默认值；所有持久化必须原子写；缺失、损坏、旧版本三条启动路径必须实现并有测试；迁移函数必须带测试且降级明确拒绝；敏感状态分离存储并排除出一切日志与诊断。瞬态进设置必须显式升级登记。实现后补损坏恢复与跨版本迁移的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：状态清单 + 四类标注 + 权威归属。
- **二档**：落盘策略、原子写、损坏路径、迁移与降级守卫（对应主大纲「本地存储」一节）。
- **三档**：多窗口并发裁决、敏感状态隔离、恢复清单全量。
- 具体准入问题以主大纲为准；本方案提供深水区的完整纪律。
