# 签名、打包与更新分发：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把「从构建产物到用户机器上运行、并安全地更新」整条链放在一起考虑：签名与公证、打包格式、首次安装、自动更新、回滚与灰度、杀软兼容、供应链（SBOM、依赖锁定、混淆与符号），避免发布前才发现：公证只在某台机器上能跑、更新到一半断电应用损坏、旧版本降级把数据写坏、杀软在发布日拦下全部用户，或出了问题无法回滚。

它不是某个应用的实现说明，也不预设产品名、框架、打包工具或更新服务。每个项目都应先按目标平台和分发渠道核实能力，再填写自己的决策。

这类问题的共同名字叫「发布链上没有失败路径」。它们几乎从不来自某一个 bug，而来自一个结构：**更新流程只写成功了怎么走，每一步失败怎么办从未被回答**。本方案的目标是让发布链每一环的失败路径在立项时就写下来。

两个边界先说清：
- 产品身份单一源、版本号单一源、macOS Info.plist 合规等准入问题在主大纲一档，以主大纲为准；本方案引用不重复。版本号的清单、单源实现与平台映射细则 →《版本号方案》。
- 降级对本地数据的影响（新 schema 旧版本打不开）按《应用状态与持久化技术方案》的迁移与降级守卫处理；本方案管「应用自身的更新」，数据迁移在更新流程中的位置见其「提交后」一步。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标平台和分发渠道，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. **签名矩阵**：三平台各用什么证书？私钥存哪、CI 如何取用？macOS 公证流程能否在新机器上从零重复执行（有记录）？
2. **打包格式**：每平台选什么（安装器 / MSIX / dmg / deb…）？未签名或半签名包在目标环境的实际行为验证过吗？
3. **运行时契约**：WebView 运行时（Evergreen / Fixed / 系统自带）选哪种？离线与企业环境如何保证「装完就能跑」？
4. **更新拓扑**：更新源在哪、清单格式是什么？签名校验发生在哪一步？版本比较规则是什么（预发布、回退版本号）？
5. **更新流程的失败路径**：下载失败、校验失败、落盘失败、切换失败、提交失败，各显示什么、留什么状态？
6. **原子性**：从下载到切换提交，哪一步是原子边界？中途断电后应用能否完好回旧版？
7. **回滚**：旧版本保留几份？回滚由谁触发（自动 / 用户）、验证流程是什么？
8. **差分更新**：是否支持 patch？失败率与体积收益评估过吗？patch 失败回退全量的路径？
9. **跨卷问题**：安装卷与临时目录不同卷时改名失败的处理？
10. **杀软 / EDR**：白名单申请的提前量？UPX 等压缩是否验证过不误报？
11. **供应链**：SBOM 生成、依赖哈希固定、漏洞扫描、混淆对绑定 ID 与调试的影响、符号剥离后的堆栈还原——各是什么决策？
12. **灰度**：通道（stable / beta）怎么分？问题出现时能否只影响一小部分用户？发布说明如何生成与存档？

交付给 AI 的设计结果应包含：签名矩阵与 CI 密钥说明、打包格式决策、更新流程图（含每步失败路径）、回滚与灰度策略、供应链门禁清单、测试矩阵。

## 更新流程的固定形状

更新是一条有原子边界的流水线，每步都有失败出口：

| 步骤 | 动作 | 失败时 |
|---|---|---|
| 发现 | 拉取清单、比较版本 | 保持当前版本，静默或提示，无副作用 |
| 下载 | 取包到临时区（校验大小 / 断点） | 丢弃临时区，下次重来 |
| 校验 | 验签名 / 哈希（公钥内置） | 拒绝并记录，绝不落盘生效 |
| 落盘 | 写入新版本目录（保留旧版） | 丢弃新目录，旧版完好 |
| 切换 | 原子地改「当前版本」指针 / 提交 | 指针未动 = 旧版照常运行 |
| 提交后 | 数据迁移（→ 状态方案）、清理旧版（按保留策略） | 迁移失败按降级守卫明确拒绝 |

三条纪律：
- **切换是原子边界**：切换之前一切失败都无副作用；切换之后才允许动用户数据。
- **公钥固定在二进制内**：更新源被劫持时，校验仍然成立。
- **旧版本是回滚的本钱**：保留策略（几份、多久）立项时定，不许「更新成功顺手删旧版」。

## 降级与数据

用户装回旧版本是会发生的（回滚、企业环境）。应用对「未来的数据 schema」必须明确拒绝并说明，而不是静默读错或写坏（→《应用状态与持久化技术方案》的降级守卫）。更新流程的「提交后」一步要和迁移守卫对接：迁移失败时应用保持可用，而不是起不来。

## 供应链与构建纪律

- **可追溯**：版本号从单一源自动同步（→ 主大纲）；构建产物可追溯到源码与依赖清单。
- **依赖锁定**：依赖按哈希固定；`go mod verify`、漏洞扫描进门禁；SBOM 随发布生成存档。
- **混淆与符号**：混淆前确认绑定 ID 稳定路径与调试代价；剥离符号前确认崩溃堆栈的还原方案（独立符号文件），否则诊断链断在发布那天（→《日志与可诊断性技术方案》）。
- **杀软提前量**：签名不等于不拦截；启发式误报、UPX 兼容性要在发布前足够早地验证与申请，写明提前量周数。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 更新后起不来 | 无原子切换、校验缺步 | 流水线六步 + 原子边界 |
| 更新中断应用损坏 | 切换不原子、无旧版保留 | 原子边界 + 保留策略 |
| 降级后数据损坏 | 无 schema 守卫 | 降级明确拒绝（→ 状态方案） |
| 公证时好时坏 | 凭据 / 环境不可重复 | 从零执行记录 + CI 化 |
| 发布日被杀软拦 | 无提前量、UPX 未验证 | 提前量周数 + 目标环境扫描 |
| 出事无法回滚 | 旧版已删、无通道隔离 | 保留策略 + 灰度通道 |
| 崩溃堆栈不可读 | 符号剥离无还原方案 | 符号文件随版本存档 |
| 差分更新失败率升高 | patch 失败无全量回退 | patch 失败 → 全量路径 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 安装 | 三平台从零安装（在线 / 离线）、覆盖安装、卸载残留 |
| 升级 | 跨多个版本的升级链；每次升级后的数据可用性 |
| 失败 | 下载中断、校验失败、落盘失败、切换中断电模拟——每步失败后应用可用 |
| 回滚 | 自动与手动回滚演练；回滚后数据守卫生效 |
| 通道 | 灰度命中与未命中、beta ↔ stable 互转 |
| 环境 | 杀软扫描、无代理 / 有代理下载（→ 主大纲代理策略） |

每次验收记录：步骤、失败注入点、应用最终状态。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出签名矩阵、打包格式决策与更新流程图（六步各带失败路径）。更新必须实现「发现 → 下载 → 校验 → 落盘 → 原子切换 → 提交后迁移」的形状，切换前任何失败无副作用；公钥固定于二进制；旧版本按保留策略留存；降级时对未来的数据 schema 明确拒绝。依赖按哈希固定，`go mod verify` 与漏洞扫描、SBOM 生成进门禁；符号文件随版本存档。杀软验证与白名单申请排在发布计划内并写明提前量。发布走灰度通道，发布说明从结构化条目生成。不得依赖「框架默认的更新行为」；平台与渠道相关行为先验证，未验证标注“待验证”。实现后补升级、失败注入与回滚的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：签名矩阵、信任根、版本单一源（主大纲一档对应条目）。
- **二档**：打包格式与运行时契约、更新拓扑。
- **四档**：SBOM、CVE、杀软、MSIX、差分更新、回滚、灰度全量（对应主大纲四档各条）。
