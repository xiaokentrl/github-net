# 托盘、应用图标与桌面身份：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把系统托盘、应用图标、程序身份、窗口隐藏与唤回放在一起考虑，避免功能分别做完后才发现：改名要改很多处、图标对不上、托盘开关实际无效、关闭后进程找不回来，或唤回时窗口跳到屏幕角落。

它还要挡住另一类更隐蔽的失败：**代码看着改对了、发布说明也写了「已修复」，实际一次都没生效**。这类失败有固定来源——同一个回调被注册两次而后一次覆盖前一次、某个手势在该平台根本没有回调、恢复位置的调用早于框架初始化因而是空操作、框架随后又按自己的默认策略重新摆位、落盘文件被退出流程写进一份坏值。它们的共同点是「只读自己的代码看不出来」，必须把框架源码、协议语义和实机判据一起摆上桌。

它不是某个应用的实现说明，也不预设产品名、标识符、资源路径、默认开关、平台策略或防抖时长。每个新项目都应先按目标平台和框架版本核实能力，再填写自己的决策。

边界先说清：本方案管**入口**（谁触发唤回、触发几次、触发后走哪条流程）与**身份图标**；唤回之后窗口自身的几何 schema、屏幕回退、焦点与故障恢复 →《窗口与多窗口技术方案》；几何落盘的通用纪律 →《应用状态与持久化技术方案》；托盘菜单的定义与本地化 →《菜单方案》。带源码证据的完整案例与验收记录模板见《[托盘唤回位置 实证复盘](./托盘唤回位置_实证复盘.md)》。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标平台和锁定的框架版本，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. 产品有哪些面向用户的名字和机器身份？哪些平台要用应用 ID、Bundle ID、桌面文件名、窗口类名、Dock 归组键或通知类别？
2. 每个平台的应用图标、托盘图标、Dock/任务栏图标、安装包图标分别从哪里来？是否复用同一源文件，是否需要尺寸、格式、模板图标或多分辨率版本？
3. 项目所用框架版本中，托盘的创建、显示、隐藏、点击、双击、右键菜单和销毁在每个平台分别怎么实现？是否有空操作、部分支持、异步行为或宿主依赖？
4. Linux 目标桌面是否使用 StatusNotifier、传统 XEmbed 或其他托盘机制？没有宿主时，用户还能从哪里恢复应用？
5. 窗口关闭、最小化、隐藏、退出分别有什么含义？用户选择后台驻留时，是否始终存在可见且可用的恢复入口？
6. 从托盘点击、托盘菜单、系统通知、Dock/任务栏、再次启动快捷方式等入口唤回时，是否全部复用同一个窗口呈现流程？
7. 隐藏或最小化再恢复时，框架和窗口管理器是否保留窗口位置、大小、最大化状态和当前屏幕？哪些调用会重新定位或重新呈现窗口？
8. 双击在目标平台上究竟是两个单击回调、独立双击回调，还是由托盘宿主合并？是否会与单击切换逻辑重复执行？
9. 设置项之间有什么依赖？能力检测失败、托盘宿主退出、图标被用户关闭时，后端如何阻止“进程留在后台但没有唤回入口”？
10. 自动化测试能覆盖哪些行为？哪些必须在目标桌面、登录会话和打包安装形态下手工验收？
11. **回调注册是赋值还是追加？** 框架的 `OnClick`／`OnRightClick`／`OnDoubleClick` 一类接口，重复注册时是覆盖、追加还是报错？仓库里同一个入口是否被注册了不止一次（含历史遗留、不同文件、条件分支各注册一次）？最终生效的是哪一处，证据是什么？
12. **每个手势在每个平台落到哪个回调？** 把「用户手势 → 托盘协议事件 → 框架回调」三层逐个对上：左键单击、左键双击、右键单击、右键双击、中键、滚轮。哪些手势在该平台**根本没有对应回调**？哪些事件名与实际鼠标键不符（例如协议里的“次要激活”其实是中键）？菜单是框架弹还是宿主弹？
13. **框架调用的时序契约是什么？** 逐个列出唤回与几何恢复要用的调用，标明：在框架 `Run` 之前调用是生效、空操作还是被记进初始选项；有没有“初始选项”这条兜底路径；框架在窗口首次显示前后是否会再按自己的默认策略摆位一次，从而覆盖应用刚设好的位置。
14. **几何是谁在写、写进去的可不可信？** 列出所有写入点（收托盘、菜单退出、关闭钩子、退出回调、信号处理），确认退出回调执行时窗口是否已销毁；销毁后读尺寸／位置会返回什么；写入前有没有有效性门；多个写入点冲突时谁最后赢。
15. **“修好了”凭什么算数？** 这次修复的可观察判据是什么（唤回前后坐标、尺寸、最大化状态、落盘文件内容、进程数、触发来源日志）？谁在什么会话／安装形态下实测？没有实测记录时，发布说明允许怎么写？
16. **同一入口的注册次数有没有静态门？** 赋值语义的注册接口一旦被注册两次，前一次就是死代码；仓库里有没有一条能在提交前拦住「同一入口两行」的检查？没有的话，靠什么保证修复提交不会只新增、不删旧？
17. **开发态与安装态是否等价？** 浏览器预览、server 模式、dev 构建、打包安装四种形态里，托盘协议、窗口后端、几何读写是否走同一套实现？在 dev 下验过的结论，凭什么推广到发布包？

交付给 AI 的设计结果应包含：平台能力表、**手势三层映射表**、**回调注册清单（一个入口一行）**、**框架调用时序表**、用户行为表、身份与图标映射、统一唤回流程、**几何写入点清单与有效性门**、**修复生效判据与验收记录**、失败策略和测试矩阵。未经用户确认，不要擅自决定“关闭按钮是退出还是驻留”这类会改变用户习惯的行为。

统一唤回的入口清单包含**系统通知点击**（后台完成的工作以系统通知提醒用户，点击即唤回主窗口并跳转）——其路由实现见组件库 `NotificationRouter`（权限前置与降级 →《系统能力与平台集成技术方案》）。

## 先把名字和身份分开规划

“改名”通常涉及多种值，不能靠全仓库查找替换维护。先列出身份清单，并指定唯一权威来源。

| 身份或名称 | 用途 | 规划时要确认 |
|---|---|---|
| 产品显示名 | 窗口标题、菜单、安装界面、用户可见文字 | 是否允许本地化；不要拿显示名代替机器身份 |
| 稳定应用 ID | 单实例、桌面环境识别、设置和通知归属等 | 格式要求、生命周期、改名后是否保持稳定 |
| 平台原生身份 | Bundle ID、桌面文件 ID、窗口类名、程序名等 | 哪些值必须彼此匹配，哪些只用于平台展示 |
| 托盘可访问名称 | 托盘宿主显示、辅助功能、菜单标题 | 平台是否展示，长度和本地化规则 |
| 资源名 | 图标文件名、资源目录名、安装包名 | 是否由构建流程从权威身份生成 |

规划原则：

- 先定义不可混用的概念，再给每个平台建立明确映射；不要把“产品名”“应用 ID”“图标名”写成同一个未定义概念。
- 稳定身份集中在单一源中；桌面项、打包配置、运行时初始化和测试从该源读取或校验。
- 改显示名不应意外改变单实例锁、用户数据目录、升级识别或桌面归组。若确实要迁移稳定 ID，先定义旧身份兼容、快捷方式迁移和数据保留策略。
- 为每个衍生值提供自动检查：构建配置和安装桌面项与权威值不一致时，让 CI 或测试明确失败。
- 代码中的示例值只能是占位符；正式方案不得把示例产品名、域名或 ID 复制成新项目事实。

## 把“图标”拆成资源与显示位置

用户说“图标不对”时，先确认具体是哪一个图标，不要只替换一张图片就认为完成。

至少分别检查：

- 应用窗口标题栏图标；
- 系统托盘图标；
- Dock、任务栏或桌面启动器图标；
- 安装包、文件管理器和应用列表图标；
- 通知使用的图标。

提前确定唯一的原始品牌资源和资源生成流程，再按平台要求生成目标格式、尺寸和变体。托盘图标可能需要透明背景、单色模板、浅色/深色版本或多尺寸资源，不能默认把窗口图标原样缩小就会正确显示。

为每个显示位置记录资源来源、生成工具、打包位置和运行时加载位置。测试应检查最终安装包和正在运行的应用，而不只看源码目录里是否有图片。

## 先区分托盘、Dock 和通知

这三者是不同入口，不能互相代替：

- **系统托盘**：桌面状态区里的应用图标，通常用于快速操作或恢复后台应用。
- **Dock/任务栏/应用启动器**：应用启动、归组和窗口切换入口；它不是系统托盘。
- **系统通知**：短暂展示的消息；用户点击通知可能触发操作，但通知不保证一直存在，不能默认当作后台应用唯一的恢复入口。

产品需求应逐个说明每个入口承担什么行为。不要用“点右上角图标”这类无法区分托盘、标题栏和 Dock 的描述。

## 按平台和框架版本核对能力

不要只看框架 API 名称相同，就认定各平台行为相同。对项目锁定的精确版本逐项查源码、官方文档和实际运行结果。

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 创建和显示托盘图标 | 核对原生实现、资源格式与通知区域行为 | 核对状态栏项、模板图标规则及菜单行为 | 核对协议、桌面宿主、会话总线和打包依赖 |
| 动态隐藏/显示 | 核对调用结果和失败反馈 | 核对原生状态项的创建/移除语义 | 核对框架是否实现；明确区分“宿主不存在”和“框架 API 不支持” |
| 点击/双击/右键 | 核对原生回调顺序和系统约定 | 核对状态项回调及菜单约定 | 核对托盘协议与宿主实际发送的激活事件 |
| 窗口隐藏/最小化/恢复 | 核对恢复后位置、焦点和任务栏状态 | 核对 Dock、窗口和应用激活语义 | 分别核对 X11、Wayland 及所用 GTK/框架后端 |
| 后台进程恢复入口 | 快捷方式、托盘、任务栏等 | Dock、托盘、应用菜单等 | 托盘宿主、桌面项再次启动、窗口列表等 |

表格是调查清单，不代表任何平台一定支持某项能力。记录验证所用的框架版本、操作系统、桌面环境、显示会话、安装方式和实际结果。框架升级后重新核对，不沿用旧版本结论。

能力检测要有明确结果，例如“可用”“不支持”“暂时无法确认”；不要把探测报错静默改写成“没有托盘”，也不要把 API 空操作报告成成功。

## 定义清楚用户行为与依赖

用行为表确定关闭、托盘和后台驻留的组合。以下是规划模板，具体选项须由产品决定：

| 托盘入口 | 关闭时驻留 | 关闭窗口后 | 用户如何恢复 | 是否允许该组合 |
|---|---|---|---|---|
| 可用且显示 | 开启 | 隐藏或最小化，进程继续运行 | 托盘菜单/图标等 | 按产品决定 |
| 用户关闭或平台不支持 | 开启 | 不得无提示地进入不可见后台 | 明确替代入口，或退出 | 必须定义 |
| 可用且显示 | 关闭 | 正常关闭或退出 | 再次启动 | 按产品决定 |
| 能力正在检测或检测失败 | 未确认 | 不得假设恢复入口存在 | 等待重试、显示原因或安全退出 | 必须定义 |

如果提供“显示托盘图标”和“关闭时驻留”两个设置，先定义依赖：关闭图标时如何处理驻留设置；平台不支持动态显隐时如何呈现；能力未知时是否禁用；后端如何再次校验。UI 禁用只是即时提示，不能作为进程生命周期的唯一保护。

为每种失败给用户可理解的解释和恢复方式。特别测试托盘宿主在应用运行期间退出、重启或暂时不可用的情形。

## 建立唯一、幂等的窗口唤回流程

将“让主窗口回到前台”实现为一个统一操作。托盘单击、托盘菜单、系统通知点击、Dock/任务栏激活和单实例二次启动都应调用该操作，不各自拼一套 `Show`、`Restore`、`Focus`、`Present` 或居中逻辑。

统一流程先读取真实窗口状态，再只做必要操作：

| 当前窗口状态 | 目标行为 | 需要避免 |
|---|---|---|
| 已最小化 | 恢复原窗口 | 恢复后又额外触发一次显示/呈现 |
| 已隐藏 | 显示原窗口 | 调用会自动居中或按托盘位置重新定位的辅助 API |
| 已显示 | 只聚焦或置前 | 重复 present、restore 或切换成隐藏 |
| 已显示且最大化 | 只置前，保留最大化 | 顺手调用“还原”把最大化状态抹掉 |
| 从未显示过（启动即后台） | 首次显示 + 按几何落盘摆位 | 把“启动即隐藏”当成“启动即最小化”，首次映射时位置交给合成器 |
| 已销毁 | 重建窗口并恢复几何，或明确告知无法唤回 | 对已销毁窗口读几何（常返回零值）或调用呈现 |
| 状态不可确认 | 使用平台验证过的安全路径 | 依据过时缓存状态反向切换窗口 |

恢复的默认目标是保留用户最后看到的位置、尺寸、最大化状态和屏幕归属；只有产品明确要求窗口跟随托盘弹出时，才使用托盘定位功能。唤回流程不应悄悄把普通主窗口改成托盘弹出窗口。

**“收进托盘”用隐藏还是最小化，要按平台实测选，不要按名字选。** 两者在不同合成器下的差别很大：有的平台隐藏会销毁窗口映射、再显示时由合成器重新摆位；最小化保留映射、唤回时原位恢复。有的平台两者都保位置，有的平台两者都保不住（此时只能换显示后端或接受限制并如实告知用户）。选定之后，**所有收起入口必须走同一种**——关闭钩子、托盘菜单、标题栏按钮各走一种，等于位置时好时坏。

**“启动后进入后台”也有两种实现，语义不同。** “创建时不显示”与“创建后立即最小化”在窗口管理器眼里是两件事：前者是首次映射还没发生，后者已经映射过。框架的初始选项里这两项通常是独立字段，只设其中一个不会自动带上另一个。方案里要写明选哪种，以及首次唤回时位置由谁决定。

**换显示后端是有代价的产品决策。** 为了让位置可恢复而强制应用走某个兼容后端（例如在原生会话里改走兼容层），可能带来渲染发虚、输入法或无障碍行为变化、缩放异常。这属于改变用户可感知行为，要由用户确认，并把已知代价写进方案与发布说明；用户显式设置的后端选择不应被应用覆盖。

## 将激活事件当作事件，不猜用户手势

不同托盘协议和桌面宿主对单击、双击的定义可能不同。两个快速激活事件不一定表示“隐藏再显示”，也不保证框架会提供单独的双击事件。

- 先查清平台实际回调语义，再决定是否使用框架的单击/双击 API。
- “打开主界面”应是幂等操作：重复调用不会再次定位、切换或关闭窗口。
- 如确需合并重复事件，先有目标平台的实测或框架契约作为依据，再选择防抖策略；防抖间隔不能作为跨平台常量照搬。
- 分清“托盘激活”“菜单命令”“通知点击”“快捷方式再次启动”等事件来源，再统一路由到窗口唤回流程。
- 菜单项和通知操作应直接表达意图，例如“显示主界面”；不要借用含义模糊的托盘双击来实现菜单功能。

### 手势要过三层才算落地

「用户做了什么」和「代码里哪个函数被调用」之间隔着两层翻译，每层都可能断。规划时逐格填表（列：用户手势 → 托盘协议事件 → 框架回调 → 决定它做什么 → 核实依据），填不出来的格子标“待验证”，不要留空当成支持。

一次核实到源码行号粒度的完整样例（Wails v3.0.0 的 Linux StatusNotifier 实现，GNOME/Wayland 会话 + XWayland）见《[托盘唤回位置 实证复盘](./托盘唤回位置_实证复盘.md)》第二节；换框架、换版本、换桌面必须重新核实，不能照抄结论。

这类表填完通常立刻暴露两件事：**事件名不等于鼠标键**（右键回调可能挂在中键的「次要激活」上，右键菜单其实由宿主弹），以及**双击可能压根没有回调**。因此「左键双击、右键双击」这类需求不能靠注册 `OnDoubleClick` 交付，只能靠单击幂等与明确的不支持声明。

三条容易翻错的地方：

- **事件名不等于鼠标键。** 协议里的“主激活／次要激活／上下文菜单”是三个独立方法，哪个键触发哪个由协议和宿主决定，不能按字面猜。有的框架把“右键回调”接在“次要激活”上，而次要激活实际是中键 ⇒ 右键永远进不了那个回调。
- **菜单可能是宿主弹的，不经过应用回调。** 应用只通过桌面总线导出菜单结构，宿主自己绘制和点击。这时“右键单击”在应用侧可能只有一个空实现的事件方法，任何写在右键回调里的逻辑都不会执行。
- **双击可能压根没有回调。** 某些平台实现里双击回调只在其中一个操作系统被触发，另两个平台注册了也永不执行。此时“双击唤回”只能靠单击幂等来兜住，不能在方案里写成“已支持双击”。

### 回调注册：一个入口只能有一个主人

框架的事件注册接口有两种语义：**赋值**（后一次覆盖前一次）和**追加**（多次都执行）。必须先查清是哪一种，再据此约束代码。

- 赋值语义下，同一个入口注册两次＝前一次是死代码。修复时新增了一处注册却没删旧的那处，等于没修，而且比没修更难发现：代码里能搜到“正确的那段”，发布说明也写了，实际生效的是旧行为。
- 追加语义下，同一个入口注册两次＝一次点击执行两套逻辑，可能出现“先隐藏再显示”或“先显示再隐藏”。
- 规划产物里要有一张**回调注册清单**：一个入口一行，写明注册位置、语义、最终生效的是哪一处。清单里出现同一入口两行，就是缺陷，不是风格问题。
- 自动化门要能抓住它：静态检查同一入口的注册次数，或用一个可观察判据（点一次之后窗口状态只按预期变一次）锁住行为。只测“回调函数本身做对了什么”抓不到覆盖问题。
- 框架的“智能默认值”也要进清单：未注册时框架可能自动挂上切换显隐、按托盘位置摆窗一类默认行为。默认行为与应用意图冲突时，必须显式注册覆盖，而不是假设没有默认。

### 框架调用的时序契约：谁最后摆位

位置恢复失败最常见的原因不是“调用写错了”，而是**调用发生在它还不生效的时刻，或者生效之后又被框架覆盖**。逐个调用填这张表，列要覆盖：在框架 `Run` 之前调用是生效、空操作还是被记进初始选项；有没有“初始选项”兜底；框架在窗口首次显示前后是否会再按自己的默认策略摆位一次，覆盖应用刚设好的位置。

同一族 API 的兜底路径可能完全不同——这正是「尺寸和最大化恢复了、位置没恢复」会同时发生的原因。一次填到源码行号粒度的样例（Wails v3.0.0 + GTK4 Linux：位置类调用的提前返回分支、`options.StartState` 兜底、`applyScreenPlacement()` 的两个调用点）见《[托盘唤回位置 实证复盘](./托盘唤回位置_实证复盘.md)》第三节。

四条纪律：

- **空操作不等于成功。** 很多框架在窗口实现尚未创建时直接返回，不报错也不记录。这类调用必须挪到框架初始化之后，或改用能写进初始选项的字段。判断依据是源码里那条提前返回的分支，不是“调用没报错”。
- **同一个能力可能两条路，只有一条有兜底。** 例如状态类调用（最大化／最小化）在未初始化时被记进初始选项，而位置类调用没有这条兜底 ⇒ 尺寸和最大化恢复了、位置没恢复。不要把同一族 API 当成同一种时序。
- **查清框架自己的默认摆位。** 初始位置选项常有默认值（例如“居中”就是零值），框架可能在首次显示前和显示后各摆一次。应用设好的位置会被这两次覆盖。正确做法通常是把位置写进初始选项，而不是建窗后再调一次设位置。
- **公开 API 与私有实现可能不一致。** 私有实现是空操作，不代表公开 API 无效——公开层可能先判状态再转调另一个真正干活的方法。读源码要读到实际那一条路径，注释和函数名都不算证据；反过来，代码注释里写的“某调用在本平台是空实现”也要按同样标准复核。

### 回调注册清单：一个入口一行

规划产物里要有一张回调注册清单：一个入口一行，写明注册位置、赋值/追加语义、最终生效的是哪一处——**包括未注册入口的框架默认行为**（未注册 ≠ 没行为，默认可能是切换显隐、按托盘位置摆窗一类，与应用意图冲突时必须显式注册覆盖）。清单里出现同一入口两行，不是风格问题而是缺陷；修复的正确形态是**删掉旧注册**、让一个入口只有一个主人，而不是再加一处「看起来正确」的注册。一份把缺陷本身拍进清单的样例（同一入口两行、生效的恰好是旧行为）见《[托盘唤回位置 实证复盘](./托盘唤回位置_实证复盘.md)》第二节。

### 坐标口径：绝对、显示器相对、DIP

- 读回来的坐标和设进去的坐标必须是同一口径。有的框架读位置返回**屏幕绝对坐标**，而初始选项里的 X/Y 是**相对当前显示器工作区原点**；单屏时两者看着一样，多屏时直接错位。
- 落盘 schema 与回退规则以《窗口与多窗口技术方案》为准（屏幕标识 + DIP + 缩放因子 + 目标屏缺失回退）。本方案只额外要求：**唤回流程不得引入第二套坐标口径**，也不要在唤回时临时做居中或跟随托盘定位。
- “位置为 0,0”要区分两种含义：用户真的把窗口放在原点，还是根本没读到位置。schema 里要能表达“未记录”，不要用零值兼职当哨兵。

## 几何落盘的写入侧纪律

读侧有兜底不够，**坏值一旦写进去，读侧兜底只能把它当“没记录”，用户看到的就是位置丢失**。写入侧要单独立规矩：

- **列全写入点。** 收托盘、托盘菜单退出、关闭钩子、应用退出回调、信号处理、崩溃前钩子——逐个列出，并标明各自执行时窗口处于什么状态（正常、最小化、隐藏、已销毁）。
- **退出回调里窗口可能已经销毁。** 销毁后读尺寸／位置，框架常返回零值而不是报错。退出流程里“再存一次以防万一”的那一次，往往就是把好值覆盖成坏值的那一次。要么在销毁前存，要么在写入前判有效性。
- **写入前必须过有效性门。** 尺寸小于合理下限、坐标明显越界、状态读回来全零——一律不写，保留上一次的好值。门要写在写入函数里，不能只写在读取函数里。
- **单一写入者。** 多个入口写同一个文件时，定义谁优先、谁不许写。最后一个写的人赢是默认结果，不是设计。
- **写失败要说出来。** 落盘失败静默忽略，会让“位置偶尔丢”变成无法排查的偶发问题。至少留一条可诊断记录（→《日志与可诊断性技术方案》）。
- **高频变更不逐次写。** 拖动过程中逐次写盘没必要；但“只在退出时写”会漏掉崩溃与强杀。落盘时机沿用《应用状态与持久化技术方案》的纪律（变更去抖带上限，或明确的离开眼前时机 + 退出前补一次）。

### 有效性门缺位时会发生什么

读侧兜底只能把坏值当「没记录」：退出回调在窗口销毁后读到全零并覆盖了好值，而读取侧兜底把坐标一并归零，于是「只有非零坐标才恢复位置」的判断永远不成立——位置依旧丢失。带源码证据与落盘实测的完整失效链（五个写入点、无有效性门、全零 `window.json`）见《[托盘唤回位置 实证复盘](./托盘唤回位置_实证复盘.md)》第三节。

由此得出写入侧必须写死的四条判据：尺寸下限、坐标合理性（含「全零」这个明确的坏值签名）、状态可信标志、以及**坏值一律不覆盖上一次的好值**。另外 `0,0` 不能兼职当「未记录」哨兵：用户真的把窗口放在屏幕原点也是合法几何，schema 里要有独立的 `hasPosition` 一类字段（→《窗口与多窗口技术方案》）。

## 修复之后：怎么证明它真的生效了

「代码改对了」和「用户看到的行为变了」之间隔着**编译产物、运行中的旧进程、打包形态、桌面会话、协议宿主**五层。历史修复最常见不是改错，而是改完之后没有任何一层被验证到，于是同一个问题被反复「修复」。方案里要把验证闭环写进交付物，而不是留给发布说明里的一句「已修复」。

### 五层验证，每层都要有可观察判据

| 层 | 要确认什么 | 可观察判据（不能用「代码里写了」代替） |
|---|---|---|
| 源码层 | 修复代码是最终生效的那一份，不是被覆盖／被跳过的死代码 | 同一入口注册次数为 1；静态门输出「入口 → 唯一注册位置」清单 |
| 编译层 | 跑起来的二进制包含这次改动 | 构建产物时间戳／版本、构建日志里该步骤通过 |
| 进程层 | 用户操作的是新进程，不是后台驻留的旧进程 | 进程数与 PID、启动时间；驻留类应用必须显式重启或走升级替换 |
| 会话层 | 目标桌面／协议宿主／显示后端与修复假设一致 | 会话类型、后端、托盘宿主是否存在；与该修复的实测环境逐项对照 |
| 行为层 | 用户动作之后窗口位置、尺寸、状态真的没变 | 唤回前后 X/Y/W/H、最大化状态、当前屏幕、落盘文件内容的快照对比 |

**发布说明纪律**：没有行为层记录，不得写「已修复」「所有路径一致恢复」这类完成式结论；只能写「已调整 X，待在 A/B/C 会话下实测」。修复条目要带上验证方法与未验范围，否则下一次复盘无法判断当时到底验了什么。

### 三道自动化门（提交前必须能跑）

1. **回调注册唯一性门**：静态扫描所有托盘回调注册点，同一入口出现两处即失败，输出文件与行号。赋值语义下这一条直接拦住「修复提交只新增、不删旧」；追加语义下拦住「一次点击跑两套逻辑」。框架的智能默认值也要进清单——未注册时框架可能自动挂切换显隐或按托盘位置摆窗。
2. **几何写入有效性门**：纯函数单测覆盖「尺寸小于下限／坐标为负或越界／全零／读回状态不可信」四类坏值，断言**不写盘、保留上一次好值**；再覆盖「退出回调读到零值」这一条，断言它不能覆盖有效几何。只测「好值能写进去」抓不到覆盖问题。
3. **唤回状态机幂等门**：把「窗口状态 → 动作序列」抽成可测的纯决策，断言已显示时**不调用**隐藏／定位／重复呈现，已最小化时只做必要的那一次恢复，连续多次激活产出的动作序列完全相同。不要只测「某个辅助函数被调用了」。

这三道门都不依赖桌面环境，属于每次提交都能跑的净收益；实机矩阵才需要人工，两者不能互相替代。

### 四类手势的验收判据

用户说的「单击／双击」在网络上常被当成一件事，验收必须拆成独立用例，每个用例都记录唤回前后的几何快照：

| 用例 | 操作前窗口状态 | 期望 | 必须记录 |
|---|---|---|---|
| 左键单击 | 普通 / 最小化 / 隐藏 / 最大化 | 幂等唤回，位置尺寸不变 | 前后 X/Y/W/H、最大化标志、落盘文件 |
| 左键双击 | 同上 | 与单击同一结果，不得出现「隐藏再显示」的抖动 | 连续两次激活实际触发了几个回调、窗口是否闪两次 |
| 右键单击 | 同上 | 按产品定义：弹菜单，或唤回；两者不得同时发生 | 菜单由谁弹出（宿主／框架）、应用侧收到哪些事件 |
| 右键双击 | 同上 | 明确定义或明确标注不支持，不能「看起来偶尔有用」 | 宿主是否发出独立事件；没有就写「不支持」 |
| 快速连续点击 | 同上 | 不移位、不切换显隐、不重复建窗 | 激活次数、进程数、窗口数 |
| 关闭／收托盘后再唤回 | 关闭到托盘、最小化到托盘 | 位置与关闭前一致 | 落盘写入点是谁触发的、写入内容 |
| 退出后重新启动 | 应用重启 | 位置与退出前一致 | 读取侧是否真的用上了落盘值（而不是只走了兜底） |

「位置没变」是相对判据：先把窗口拖到一个非默认、非居中的位置再开始，否则默认居中和恢复原位看起来一样，测不出差别。每一条都要在**打包安装形态**下重跑一遍，dev 与浏览器预览里托盘／窗口后端常常根本不是同一套实现。

## 图标与窗口问题的常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 改名后 Dock 出现两个应用图标 | 显示名、应用 ID、桌面文件身份、窗口类名不一致，或启动器仍收藏旧身份 | 建立身份映射表和迁移方案；安装后检查运行窗口是否归到预期启动器 |
| 托盘图标与程序图标不一致 | 托盘与窗口使用了不同资源、遗漏平台资源格式或打包没带资源 | 逐个列出显示位置和资源链路；检查最终安装包 |
| 设置显示“已隐藏”，托盘图标仍在 | 当前框架平台实现是 no-op，且公共 API 不返回结果 | 源码核对平台实现；能力不支持时禁用或明示，不做成功形回退 |
| 点关闭后进程消失，托盘也不在 | 系统托盘与 Dock 被当成同一入口，或没有考虑宿主缺失 | 定义后台驻留条件和至少一个持续可用的恢复入口 |
| 双击托盘后窗口跳到角落或托盘附近 | 双击拆成多个激活；回调重复 present；框架切换函数会定位窗口 | 激活路径幂等；核查框架默认 Toggle/Position 行为；测试连续激活 |
| 从通知恢复正常、从托盘恢复异常 | 不同入口各自实现窗口恢复，调用顺序不一致 | 所有入口共用窗口唤回操作，记录触发来源 |
| Wayland 下隐藏后位置丢失 | 合成器控制窗口位置；重新映射会按自身策略放置 | 分别验证隐藏与最小化，按实际桌面行为选择方案，不假设 X11 与 Wayland 相同 |
| 关掉托盘后留下无法恢复的后台进程 | 前端偏好与后端关闭钩子不一致，或能力发生变化 | 后端在关闭时复核有效恢复入口；托盘不可用时采取明确安全行为 |
| 通知点击没有唤回或打开了第二个窗口 | 通知 action 未进入统一激活路径，或单实例身份未规划 | 通知 action、单实例激活和窗口创建一起设计并测试 |
| 发布说明写了「已修复」，用户操作仍和以前一样 | 新注册被旧注册覆盖成死代码；或修复只改了「正确那段」，生效的是另一段 | 回调注册清单 + 注册次数静态门 + 行为层快照对比 |
| 双击「支持了」却没反应 | 该平台根本没有双击回调，只有两次单击；或右键回调挂在中键的「次要激活」上 | 手势三层映射表逐格核实；无回调的手势明确标「不支持」 |
| 尺寸／最大化恢复了，位置没恢复 | 位置类调用在框架初始化前是空操作，且没有初始选项兜底；框架显示时又按默认摆位一次 | 把位置写进初始选项；核对 `applyScreenPlacement` 一类调用点 |
| 几何落盘文件全是 0，之后每次都丢位置 | 退出回调在窗口销毁后读几何并覆盖了好值；写入侧没有有效性门 | 写入侧有效性门 + 单一写入者；坏值不写盘 |
| 只在打包版复现、dev 版正常 | 会话后端、托盘宿主、显示协议与 dev／浏览器预览不是同一套实现 | 四类手势在打包安装形态下重跑一遍 |

以上是常见原因与预防方向，具体根因必须依据项目代码、框架版本和目标桌面复现确认。

## 先设计测试矩阵，再开始实现

自动化测试先覆盖不依赖桌面的纯逻辑：偏好依赖、能力归类、关闭裁决、窗口状态到动作的映射、重复激活幂等、稳定身份一致性。不要只测某个辅助函数被调用，而要锁定“重复唤回不能移动窗口”“无恢复入口不得驻留”等可观察行为。

随后制定桌面手工验收矩阵。至少考虑：

| 维度 | 要覆盖的情况 |
|---|---|
| 操作系统与后端 | 项目实际支持的平台及各自窗口/托盘实现 |
| Linux 会话 | 目标发行版、主要桌面环境、X11、Wayland；有无托盘宿主 |
| 窗口状态 | 普通、最大化、最小化、隐藏；主屏与副屏 |
| 激活入口 | 托盘单击、快速连续点击、右键菜单、菜单命令、通知点击、Dock/任务栏、二次启动 |
| 生命周期 | 首次启动、隐藏后恢复、最小化后恢复、托盘宿主退出、应用退出、升级后从旧快捷方式启动 |
| 资源和身份 | 开发运行、打包安装、桌面收藏项、窗口图标、托盘图标和通知图标 |
| 四类手势 | 左键单击、左键双击、右键单击、右键双击、中键、滚轮；每个都过「普通／最小化／隐藏／最大化」四种窗口状态 |
| 连续激活 | 快速两次点击、双击被拆成两次单击、菜单弹出期间再次点击 |
| 几何写入 | 正常收起、直接退出、退出回调读到零值、强杀、落盘文件损坏、目标屏被拔掉 |
| 修复有效性 | 发布包形态下重跑；确认运行的是新进程；确认落盘值被读取侧真正用上 |

每次唤回测试都记录操作前后窗口位置、尺寸、最大化状态、进程数量和图标归组；同时保留 OS、桌面环境、会话类型、托盘宿主和框架版本。未测试的平台标为未验，不用某个平台的结果替其他平台背书。**位置类用例必须先把窗口拖到非默认、非居中的位置再开始**，否则「恢复原位」与「走到默认居中」看起来一样，测不出差别（见「修复之后」的四类手势验收判据）。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先盘点仓库中的应用身份、图标资源、托盘安装、关闭事件、所有唤回入口和当前锁定的 GUI 框架版本。逐平台核实托盘 API 的实现与事件语义，标出源码依据和需要实机验证的部分。开始改代码前，先给出产品身份映射、行为/依赖表、统一唤回状态机和测试矩阵；不得假设 API 跨平台等价，不得把托盘、Dock 和系统通知混为一谈，不得重复硬编码身份或图标路径，不得在已显示窗口上重复定位或呈现。**修复类改动先查同一个入口是否被注册过不止一次：赋值语义下新增一处注册而不删旧的那处，等于没修。**实现后增加可观察行为的回归测试（重复唤回不移动窗口、坏几何不覆盖好值、同一入口注册次数为 1），并明确列出未实测平台和安装形态。**没有行为层实测记录，不得在提交信息或发布说明里写「已修复」；只能写「已调整 X，待在 A/B/C 会话下实测」。**所有名称、ID、资源路径和默认策略由当前项目需求决定，不得从其他项目照抄。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。
