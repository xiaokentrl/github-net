# 托盘、应用图标与桌面身份：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把系统托盘、应用图标、程序身份、窗口隐藏与唤回放在一起考虑，避免功能分别做完后才发现：改名要改很多处、图标对不上、托盘开关实际无效、关闭后进程找不回来，或唤回时窗口跳到屏幕角落。

它不是某个应用的实现说明，也不预设产品名、标识符、资源路径、默认开关、平台策略或防抖时长。每个新项目都应先按目标平台和框架版本核实能力，再填写自己的决策。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标平台和锁定的框架版本，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. 产品有哪些面向用户的名字和机器身份？哪些平台要用应用 ID、Bundle ID、桌面文件名、窗口类名、Dock 归组键或通知类别？
2. 每个平台的应用图标、托盘图标、Dock/任务栏图标、安装包图标分别从哪里来？是否复用同一源文件，是否需要尺寸、格式、模板图标或多分辨率版本？
3. 项目所用框架版本中，托盘的创建、显示、隐藏、点击、双击、右键菜单和销毁在每个平台分别怎么实现？是否有空操作、部分支持、异步行为或宿主依赖？
4. Linux 目标桌面是否使用 StatusNotifier、传统 XEmbed 或其他托盘机制？没有宿主时，用户还能从哪里恢复应用？
5. 窗口关闭、最小化、隐藏、退出分别有什么含义？用户选择后台驻留时，是否始终存在可见且可用的恢复入口？
6. 从托盘点击、托盘菜单、系统通知、Dock/任务栏、再次启动快捷方式等入口唤回时，是否全部复用同一个窗口呈现流程？
7. 隐藏或最小化再恢复时，框架和窗口管理器是否保留窗口位置、大小、最大化状态和当前屏幕？哪些调用会重新定位或重新呈现窗口？
8. 双击在目标平台上究竟是两个单击回调、独立双击回调，还是由托盘宿主合并？是否会与单击切换逻辑重复执行？
9. 设置项之间有什么依赖？能力检测失败、托盘宿主退出、图标被用户关闭时，后端如何阻止“进程留在后台但没有唤回入口”？
10. 自动化测试能覆盖哪些行为？哪些必须在目标桌面、登录会话和打包安装形态下手工验收？

交付给 AI 的设计结果应包含：平台能力表、用户行为表、身份与图标映射、统一唤回流程、失败策略和测试矩阵。未经用户确认，不要擅自决定“关闭按钮是退出还是驻留”这类会改变用户习惯的行为。

## 先把名字和身份分开规划

“改名”通常涉及多种值，不能靠全仓库查找替换维护。先列出身份清单，并指定唯一权威来源。

| 身份或名称 | 用途 | 规划时要确认 |
|---|---|---|
| 产品显示名 | 窗口标题、菜单、安装界面、用户可见文字 | 是否允许本地化；不要拿显示名代替机器身份 |
| 稳定应用 ID | 单实例、桌面环境识别、设置和通知归属等 | 格式要求、生命周期、改名后是否保持稳定 |
| 平台原生身份 | Bundle ID、桌面文件 ID、窗口类名、程序名等 | 哪些值必须彼此匹配，哪些只用于平台展示 |
| 托盘可访问名称 | 托盘宿主显示、辅助功能、菜单标题 | 平台是否展示，长度和本地化规则 |
| 资源名 | 图标文件名、资源目录名、安装包名 | 是否由构建流程从权威身份生成 |

规划原则：

- 先定义不可混用的概念，再给每个平台建立明确映射；不要把“产品名”“应用 ID”“图标名”写成同一个未定义概念。
- 稳定身份集中在单一源中；桌面项、打包配置、运行时初始化和测试从该源读取或校验。
- 改显示名不应意外改变单实例锁、用户数据目录、升级识别或桌面归组。若确实要迁移稳定 ID，先定义旧身份兼容、快捷方式迁移和数据保留策略。
- 为每个衍生值提供自动检查：构建配置和安装桌面项与权威值不一致时，让 CI 或测试明确失败。
- 代码中的示例值只能是占位符；正式方案不得把示例产品名、域名或 ID 复制成新项目事实。

## 把“图标”拆成资源与显示位置

用户说“图标不对”时，先确认具体是哪一个图标，不要只替换一张图片就认为完成。

至少分别检查：

- 应用窗口标题栏图标；
- 系统托盘图标；
- Dock、任务栏或桌面启动器图标；
- 安装包、文件管理器和应用列表图标；
- 通知使用的图标。

提前确定唯一的原始品牌资源和资源生成流程，再按平台要求生成目标格式、尺寸和变体。托盘图标可能需要透明背景、单色模板、浅色/深色版本或多尺寸资源，不能默认把窗口图标原样缩小就会正确显示。

为每个显示位置记录资源来源、生成工具、打包位置和运行时加载位置。测试应检查最终安装包和正在运行的应用，而不只看源码目录里是否有图片。

## 先区分托盘、Dock 和通知

这三者是不同入口，不能互相代替：

- **系统托盘**：桌面状态区里的应用图标，通常用于快速操作或恢复后台应用。
- **Dock/任务栏/应用启动器**：应用启动、归组和窗口切换入口；它不是系统托盘。
- **系统通知**：短暂展示的消息；用户点击通知可能触发操作，但通知不保证一直存在，不能默认当作后台应用唯一的恢复入口。

产品需求应逐个说明每个入口承担什么行为。不要用“点右上角图标”这类无法区分托盘、标题栏和 Dock 的描述。

## 按平台和框架版本核对能力

不要只看框架 API 名称相同，就认定各平台行为相同。对项目锁定的精确版本逐项查源码、官方文档和实际运行结果。

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 创建和显示托盘图标 | 核对原生实现、资源格式与通知区域行为 | 核对状态栏项、模板图标规则及菜单行为 | 核对协议、桌面宿主、会话总线和打包依赖 |
| 动态隐藏/显示 | 核对调用结果和失败反馈 | 核对原生状态项的创建/移除语义 | 核对框架是否实现；明确区分“宿主不存在”和“框架 API 不支持” |
| 点击/双击/右键 | 核对原生回调顺序和系统约定 | 核对状态项回调及菜单约定 | 核对托盘协议与宿主实际发送的激活事件 |
| 窗口隐藏/最小化/恢复 | 核对恢复后位置、焦点和任务栏状态 | 核对 Dock、窗口和应用激活语义 | 分别核对 X11、Wayland 及所用 GTK/框架后端 |
| 后台进程恢复入口 | 快捷方式、托盘、任务栏等 | Dock、托盘、应用菜单等 | 托盘宿主、桌面项再次启动、窗口列表等 |

表格是调查清单，不代表任何平台一定支持某项能力。记录验证所用的框架版本、操作系统、桌面环境、显示会话、安装方式和实际结果。框架升级后重新核对，不沿用旧版本结论。

能力检测要有明确结果，例如“可用”“不支持”“暂时无法确认”；不要把探测报错静默改写成“没有托盘”，也不要把 API 空操作报告成成功。

## 定义清楚用户行为与依赖

用行为表确定关闭、托盘和后台驻留的组合。以下是规划模板，具体选项须由产品决定：

| 托盘入口 | 关闭时驻留 | 关闭窗口后 | 用户如何恢复 | 是否允许该组合 |
|---|---|---|---|---|
| 可用且显示 | 开启 | 隐藏或最小化，进程继续运行 | 托盘菜单/图标等 | 按产品决定 |
| 用户关闭或平台不支持 | 开启 | 不得无提示地进入不可见后台 | 明确替代入口，或退出 | 必须定义 |
| 可用且显示 | 关闭 | 正常关闭或退出 | 再次启动 | 按产品决定 |
| 能力正在检测或检测失败 | 未确认 | 不得假设恢复入口存在 | 等待重试、显示原因或安全退出 | 必须定义 |

如果提供“显示托盘图标”和“关闭时驻留”两个设置，先定义依赖：关闭图标时如何处理驻留设置；平台不支持动态显隐时如何呈现；能力未知时是否禁用；后端如何再次校验。UI 禁用只是即时提示，不能作为进程生命周期的唯一保护。

为每种失败给用户可理解的解释和恢复方式。特别测试托盘宿主在应用运行期间退出、重启或暂时不可用的情形。

## 建立唯一、幂等的窗口唤回流程

将“让主窗口回到前台”实现为一个统一操作。托盘单击、托盘菜单、系统通知点击、Dock/任务栏激活和单实例二次启动都应调用该操作，不各自拼一套 `Show`、`Restore`、`Focus`、`Present` 或居中逻辑。

统一流程先读取真实窗口状态，再只做必要操作：

| 当前窗口状态 | 目标行为 | 需要避免 |
|---|---|---|
| 已最小化 | 恢复原窗口 | 恢复后又额外触发一次显示/呈现 |
| 已隐藏 | 显示原窗口 | 调用会自动居中或按托盘位置重新定位的辅助 API |
| 已显示 | 只聚焦或置前 | 重复 present、restore 或切换成隐藏 |
| 状态不可确认 | 使用平台验证过的安全路径 | 依据过时缓存状态反向切换窗口 |

恢复的默认目标是保留用户最后看到的位置、尺寸、最大化状态和屏幕归属；只有产品明确要求窗口跟随托盘弹出时，才使用托盘定位功能。唤回流程不应悄悄把普通主窗口改成托盘弹出窗口。

## 将激活事件当作事件，不猜用户手势

不同托盘协议和桌面宿主对单击、双击的定义可能不同。两个快速激活事件不一定表示“隐藏再显示”，也不保证框架会提供单独的双击事件。

- 先查清平台实际回调语义，再决定是否使用框架的单击/双击 API。
- “打开主界面”应是幂等操作：重复调用不会再次定位、切换或关闭窗口。
- 如确需合并重复事件，先有目标平台的实测或框架契约作为依据，再选择防抖策略；防抖间隔不能作为跨平台常量照搬。
- 分清“托盘激活”“菜单命令”“通知点击”“快捷方式再次启动”等事件来源，再统一路由到窗口唤回流程。
- 菜单项和通知操作应直接表达意图，例如“显示主界面”；不要借用含义模糊的托盘双击来实现菜单功能。

## 图标与窗口问题的常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 改名后 Dock 出现两个应用图标 | 显示名、应用 ID、桌面文件身份、窗口类名不一致，或启动器仍收藏旧身份 | 建立身份映射表和迁移方案；安装后检查运行窗口是否归到预期启动器 |
| 托盘图标与程序图标不一致 | 托盘与窗口使用了不同资源、遗漏平台资源格式或打包没带资源 | 逐个列出显示位置和资源链路；检查最终安装包 |
| 设置显示“已隐藏”，托盘图标仍在 | 当前框架平台实现是 no-op，且公共 API 不返回结果 | 源码核对平台实现；能力不支持时禁用或明示，不做成功形回退 |
| 点关闭后进程消失，托盘也不在 | 系统托盘与 Dock 被当成同一入口，或没有考虑宿主缺失 | 定义后台驻留条件和至少一个持续可用的恢复入口 |
| 双击托盘后窗口跳到角落或托盘附近 | 双击拆成多个激活；回调重复 present；框架切换函数会定位窗口 | 激活路径幂等；核查框架默认 Toggle/Position 行为；测试连续激活 |
| 从通知恢复正常、从托盘恢复异常 | 不同入口各自实现窗口恢复，调用顺序不一致 | 所有入口共用窗口唤回操作，记录触发来源 |
| Wayland 下隐藏后位置丢失 | 合成器控制窗口位置；重新映射会按自身策略放置 | 分别验证隐藏与最小化，按实际桌面行为选择方案，不假设 X11 与 Wayland 相同 |
| 关掉托盘后留下无法恢复的后台进程 | 前端偏好与后端关闭钩子不一致，或能力发生变化 | 后端在关闭时复核有效恢复入口；托盘不可用时采取明确安全行为 |
| 通知点击没有唤回或打开了第二个窗口 | 通知 action 未进入统一激活路径，或单实例身份未规划 | 通知 action、单实例激活和窗口创建一起设计并测试 |

以上是常见原因与预防方向，具体根因必须依据项目代码、框架版本和目标桌面复现确认。

## 先设计测试矩阵，再开始实现

自动化测试先覆盖不依赖桌面的纯逻辑：偏好依赖、能力归类、关闭裁决、窗口状态到动作的映射、重复激活幂等、稳定身份一致性。不要只测某个辅助函数被调用，而要锁定“重复唤回不能移动窗口”“无恢复入口不得驻留”等可观察行为。

随后制定桌面手工验收矩阵。至少考虑：

| 维度 | 要覆盖的情况 |
|---|---|
| 操作系统与后端 | 项目实际支持的平台及各自窗口/托盘实现 |
| Linux 会话 | 目标发行版、主要桌面环境、X11、Wayland；有无托盘宿主 |
| 窗口状态 | 普通、最大化、最小化、隐藏；主屏与副屏 |
| 激活入口 | 托盘单击、快速连续点击、右键菜单、菜单命令、通知点击、Dock/任务栏、二次启动 |
| 生命周期 | 首次启动、隐藏后恢复、最小化后恢复、托盘宿主退出、应用退出、升级后从旧快捷方式启动 |
| 资源和身份 | 开发运行、打包安装、桌面收藏项、窗口图标、托盘图标和通知图标 |

每次唤回测试都记录操作前后窗口位置、尺寸、最大化状态、进程数量和图标归组；同时保留 OS、桌面环境、会话类型和框架版本。未测试的平台标为未验，不用某个平台的结果替其他平台背书。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先盘点仓库中的应用身份、图标资源、托盘安装、关闭事件、所有唤回入口和当前锁定的 GUI 框架版本。逐平台核实托盘 API 的实现与事件语义，标出源码依据和需要实机验证的部分。开始改代码前，先给出产品身份映射、行为/依赖表、统一唤回状态机和测试矩阵；不得假设 API 跨平台等价，不得把托盘、Dock 和系统通知混为一谈，不得重复硬编码身份或图标路径，不得在已显示窗口上重复定位或呈现。实现后增加可观察行为的回归测试，并明确列出未实测平台和安装形态。所有名称、ID、资源路径和默认策略由当前项目需求决定，不得从其他项目照抄。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。
