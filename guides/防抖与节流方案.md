# 防抖与节流：延迟家族通用方案

## 这份方案是做什么的

库里已有五处「延迟/合并」的局部纪律，但从未统一判定：同步层的高频事件节流、缓存方案的单飞、状态方案的去抖落盘、操作反馈的延迟显示、任务队列的在途去重。本方案把这一家子收进**一张判定表**——回答「这段逻辑该用哪种延迟机制、参数是什么、共享哪些不变式」。

**硬性目标**：
1. 每段延迟逻辑可归入五类之一，登记处可查（机制、参数、清理责任）；
2. **数据会丢的防抖必须有上限**（maxWait）——防抖与崩溃安全的冲突在此裁决；
3. 全部定时器**卸载可清理、假时钟可测**。

**与相邻方案的分工**：单飞（同 key 在途合并）→《缓存一致性方案》；在途禁用与乐观对账 →《统一同步层技术方案》；落盘去抖 + 上限 →《应用状态与持久化技术方案》；任务在途去重 →《任务队列方案》；IME 组合态 →《国际化与输入技术方案》。本方案给**判定表与共同不变式**，各方案引用不重复。

## 先把五类分开（一句话判定规则）

| 机制 | 语义 | 适用 | 典型参数 |
|---|---|---|---|
| **防抖**（debounce） | 等「停」再执行，只要最终态 | 搜索输入、自动保存、resize 后重算、表单草稿 | 200–500ms；**有数据丢失风险必须加 maxWait** |
| **节流**（throttle） | 限频执行，要过程反馈 | scroll / mousemove / 拖拽跟随 / 进度渲染 | 16ms（帧）–200ms |
| **单飞**（in-flight merge） | 相同 key 的并发请求合并为一次 | 数据重取、同实体的并发读 | 无延迟，只合并在途 |
| **在途禁用**（状态锁） | 写操作不可重入 | 提交按钮、删除、支付 | 无延迟，状态锁 |
| **延迟显示**（意图确认） | 等「意图稳定」再出现 | Tooltip / HoverCard / 下拉展开 | 200–300ms |

**判定规则**：

> **要最终态 → 防抖；要过程 → 节流；要并发不重复 → 单飞；要不可重入 → 在途禁用；要意图确认 → 延迟显示。**

**边界说明**：倒计时（剩余时间展示，如重发冷却）不是延迟机制，属展示件——其判定与实现 →《验证码方案》`useCountdownUntil`；本判定表只管「延迟执行」的五类。

最常见的错配：**该节流的地方用了防抖**（拖拽跟随在停止前毫无反馈），**该在途禁用的地方用了防抖**（提交按钮连点变成「每 500ms 提交一次」——防抖永远不防重入）。

## 数据防抖：上限是硬约束

凡是**延迟会丢数据**的防抖（自动保存、草稿、配置写入），必须三件套齐：

1. **maxWait 上限**：最迟 N 毫秒必写一次盘——「用户一直在打字」不能成为永不落盘的理由（→ 状态方案落盘时机「去抖须有上限，写成数值」）；
2. **卸载 / 退出冲刷**：组件卸载、页面隐藏（visibilitychange）、应用退出前，pending 的写入**立即冲刷**；
3. **崩溃安全**：冲刷依赖退出流程不可靠（kill -9 不走）——所以上限冲刷之外，关键数据走「变更即写」而非防抖（→ 状态方案崩溃安全分界）。

纯 UI 场景（搜索联想、resize 重算）不丢数据，无需 maxWait。

## 共同不变式（五类全适用）

- **可取消**：组件卸载时 pending 的定时器与在途动作必须清理——「卸载后 setState」是最难查的警告源；
- **竞态裁决**：延迟期间事实可能已变——迟到响应以版本/时间裁决（→ 缓存方案 key 纪律、同步层乱序拒绝），不许旧值覆盖新值；
- **组合态不触发**：CJK 输入的搜索联想在组合结束前不发请求（→ 国际化方案组合态纪律）；
- **假时钟可测**：全部延迟逻辑必须能在 `vi.useFakeTimers()` 下测试——依赖真实时间的设计不可测即不可验收；
- **被合并的事件有迹可查**：节流/防抖丢弃的中间态至少 debug 级可见（→ 可诊断性方案），排查「为什么没触发」时不靠猜。

## 生命周期与边界场景

- **焦点切换 / 页面隐藏**：输入防抖在失焦时立即冲刷一次（用户的心智是「我填完了」）；
- **休眠恢复**：节流的进度类定时器在休眠期间暂停——恢复后补一发（→ 同步层休眠恢复纪律）；
- **批量落定的合并**：前端延迟逻辑复用 `lib/timing.ts` 钩子，不各写各的 setTimeout；Go 侧落定枢纽的节流在 hub 内实现（→《UI数据一致性实现方案》），两侧判定表一致、实现各自归位；
- **首次立即**：搜索首字符通常应立即响应（leading）还是等待（trailing）？逐场景登记，不全局一刀切。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 防抖 | 窗口内连续触发只执行末次；maxWait 到点强制执行；卸载后不执行 |
| 节流 | 高频触发的执行频率 ≤ 间隔；首尾触发不丢 |
| 单飞 | 并发同 key 合并为一次；不同 key 不合并 |
| 冲刷 | 卸载 / 失焦 / visibilitychange 各冲刷一次且不重复 |
| 竞态 | 延迟期间事实变更 → 迟到的旧响应被拒 |
| IME | 组合态输入不触发搜索 |
| 时钟 | 全部用例在假时钟下通过 |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 搜索每键一请求 | 无防抖 | 判定表 + lib 钩子 |
| 自动保存丢数据 | 防抖无 maxWait + 崩溃 | 数据防抖三件套 |
| 拖拽跟随毫无反馈 | 该节流用了防抖 | 判定表 |
| 提交按钮防抖后仍重复提交 | 防抖不是重入锁 | 在途禁用 |
| 控制台刷「卸载后更新」警告 | 定时器未清理 | 可取消不变式 |
| 中文打字疯狂触发搜索 | 组合态未拦 | 组合态不触发 |
| 切换页面后旧结果覆盖新结果 | 无版本裁决 | 竞态裁决不变式 |
| 测试只能 sleep 等真实时间 | 依赖真实时钟 | 假时钟可测 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出延迟逻辑清单，逐条按判定表归类（防抖 / 节流 / 单飞 / 在途禁用 / 延迟显示）并登记参数。全部延迟逻辑复用 `lib/timing.ts` 的钩子，不自写 setTimeout 散落各处；数据会丢的防抖必须 maxWait + 卸载/失焦/隐藏冲刷；卸载清理与假时钟可测是不变式；组合态不触发；竞态以版本裁决。禁止用防抖替代在途禁用。实现后补假时钟下的防抖窗口、maxWait、冲刷、竞态测试，并明确列出未覆盖的场景。

方案确认后再改代码；判定拿不准（防抖还是节流）时，先报告场景再裁决。

## 五档定位

- **一档**：延迟逻辑清单 + 判定归类。
- **二档**：lib 钩子落地 + 数据防抖三件套。
- **持续**：新延迟逻辑先进判定表再写代码。
