# 原子性提交：命令与事务通用方案

## 这份方案是做什么的

库里已有多处原子性的局部规则：文件的原子写 →《应用状态与持久化技术方案》；更新的原子切换 →《签名打包与更新分发技术方案》；oplog 与业务写同事务 →《多端数据同步方案》。本方案补上总纲：**命令级与跨资源的原子提交**——一个操作要么全部生效、要么全部不生效，以及做不到全有全无时，怎么让失败可恢复。

**病根一句话**：部分提交——命令做三件事，第二件失败，第一件已生效、第三件没做，用户面对一个谁也没预期过的中间状态，且没有恢复入口。这类事故几乎从不来自某一个 bug，而来自一个结构：**事务边界从未被画出来，步骤顺序随手写**。本方案的目标是让每个命令的原子性在立项时就是显式决策。

**判定规则先行**：

> **每个命令登记三件事**：事务边界在哪、涉及哪些资源（DB / 文件 / 外部服务）、失败时用户看到什么。三问无答案的命令不许开工。

## 事务边界纪律（单资源内）

- **事务住领域层**：领域服务的命令方法 = 事务边界；store 不自行开事务（→ 后端结构方案：`service.go` 是命令入口、事务边界）。
- **单命令单事务**：一个命令一个事务，不跨命令、不被 UI 步骤切分；「先建实体再弹第二个框填详情」是两个命令，各有各的原子性，中间态是合法状态而非事故。
- **事务短小**：事务内**禁止网络调用、外部命令、用户交互、引擎操作**——锁与不确定等待都在事务外。需要外部结果的，见下文多资源模式。
- **长任务不分一个长事务**：耗时工作按阶段提交 + 检查点（每阶段原子、可续跑）——一个导入占住事务十分钟，等于把并发和崩溃恢复全部锁死（→ 任务队列方案）。
- **oplog 同事务**：接入多端同步后，业务写与变更日志同事务（→ 多端方案），保证「数据变了日志必在」。

## 多资源原子性：三种模式，按成本递增选

跨 DB / 文件系统 / 外部服务没有共享事务，原子性靠**结构**而非机制：

### 模式一：顺序规则（最便宜，默认首选）

排列步骤，使**任何一步失败都落在可恢复的位置**：

- **先建后删**：新文件写完并落盘（fsync）才删旧文件；新记录先入库，旧资源后清理；
- **悬空引用好过数据丢失**：必须在「留下指向不存在资源的引用」与「丢失数据」之间选时，选前者，并给出修复路径（空态 + 重建入口，→ 状态方案损坏降级）；
- 顺序规则登记在命令的原子性登记表里，不靠口头约定。

### 模式二：意图先行（收据 / outbox）

有外部动作（发通知、调外部服务、移动大量文件）时：

1. 同一事务内先写**收据记录**（命令 ID、动作参数、状态 = 待执行）；
2. 事务提交后执行外部动作；
3. 完成后回写收据为已完成；
4. **启动时扫描未完结收据** → 重试或补偿（与长任务崩溃恢复、日志方案的异常退出检测同形状——在途标记 + 启动扫描是全库统一的恢复模式）。

收据让「提交了但外部动作没做成」从幽灵状态变成可枚举、可恢复的显式状态。

### 模式三：补偿（saga）

多步外部流程必须整体回滚时：

- 每步登记**逆操作**，失败沿链补偿；
- 补偿本身可能失败——补偿失败是**显式状态**（任务中心可见 + 人工处理入口），不许静默吞（→ 操作反馈失败三件套）；
- 补偿链只用于**确有必要的**外部流程；能在模式一、二解决的，不引入补偿——补偿是三模式中最贵的。

选型规则：**先排顺序（一），不行加收据（二），最后才补偿（三）**。

## 与既有体系的衔接

- **批量命令**：批量的原子性 = 收口规则（全部子操作终态后父命令落定；部分失败的成败边界呈现 + 失败者重试 → 任务队列方案）。
- **导入导出**：导入 = 「解析（无副作用）→ 校验 → 单事务入库（或检查点分批）→ 收据收尾」；解析失败零副作用，入库失败按检查点续跑或整体回滚（登记选择）。
- **恢复入口**：启动时发现未完结收据 → 操作反馈矩阵登记「上次操作未完成，恢复 / 放弃」——中间态对用户永远有出口（→ 操作反馈方案）。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 步骤失败 | 每命令在第 N 步注入失败（N = 1..总步数），断言终态与恢复入口 |
| 进程死亡 | 事务提交前 / 后、外部动作执行中 kill -9 → 收据扫描恢复 |
| 多资源 | DB 成功 + 文件失败；文件成功 + DB 失败；两种悬空各按顺序规则的预期 |
| 补偿 | 补偿链各步失败；补偿失败显式呈现 |
| 批量 | 部分失败收口、失败者重试不重复生效（幂等） |
| 并发 | 同实体两命令并发的事务串行化；长任务与短命令不互锁 |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 界面出现半成品状态 | 事务边界未定义、步骤随手写 | 命令三问登记表 |
| 悬空文件 / 孤儿记录 | 顺序反了（先删后建） | 先建后删 + 顺序登记 |
| 事务卡死、并发全部超时 | 事务内有网络 / 用户交互 | 事务短小纪律 |
| 导入失败残留半库 | 长事务一把梭或无检查点 | 阶段提交 + 收据 |
| 外部动作悄悄丢了 | 无收据、失败无人知 | 意图先行 + 启动扫描 |
| 补偿后数据更乱 | 补偿无逆操作登记、失败静默 | 补偿链登记 + 显式失败态 |
| 重试导致重复生效 | 命令不幂等 | 幂等键（→ 网络方案重试纪律） |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 每个命令先答三问（事务边界 / 涉及资源 / 失败呈现）并登记。事务住领域层、单命令单事务、事务内零外呼零交互；跨资源按「顺序规则 → 收据 → 补偿」递增选型并登记理由，先建后删、悬空引用优于丢数据；外部动作一律意图先行（同事务写收据）+ 启动扫描恢复；补偿链显式登记逆操作，补偿失败显式呈现不静默；批量按收口规则，重试幂等。长任务按阶段提交带检查点，不占长事务。实现后补步骤失败注入、进程死亡恢复与并发串行化的测试，并明确列出未覆盖的命令。

方案确认后再改代码；事务语义与框架生命周期冲突时先报告差异再裁决。

## 五档定位

- **一档**：命令三问登记表（事务边界 / 资源 / 失败呈现）+ 模式选型原则。
- **二档**：事务边界落地、顺序规则与收据机制、启动扫描恢复。
- **三 / 四档**：补偿链全量、批量收口全测、恢复入口进操作-反馈矩阵。
