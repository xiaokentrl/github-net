# 长任务与后台工作：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把「耗时超过一次点击预期的工作」——扫描、导入导出、批处理、同步、网络请求、外部命令——放在一起考虑，避免功能分别做完后才发现：界面卡在等一个没有取消入口的调用、窗口关了任务还在跑、批量只成功一半却无回执、同一任务被连点触发了三次，或崩溃重启后任务留在幽灵状态。

它不是某个应用的实现说明，也不预设产品名、框架或任务队列实现。每个项目都应先按自己的长任务清单和框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「任务失控」。它们几乎从不来自某一个 bug，而来自一个结构：**任务发起后与发起它的界面解绑——既没有贯通的取消链，也没有约定的收口点**。本方案的目标是把这类结构在立项阶段就排除掉。

两个边界先说清：
- **《统一同步层技术方案》管任务落定之后界面如何刷新**（落定三步、失效、对账）；本方案管任务本身——取消、并发、进度、生命周期。
- 任务产生的持久结果按《应用状态与持久化技术方案》落盘；本方案只管「任务跑到落定为止」。
- 任务系统的**具体实现设计**（状态机、通道互斥、去重、批量收口、持久化档位）见《任务队列方案》。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **长任务清单**是什么？哪些绑定调用可能超过数秒？各自的预期时长量级（秒级 / 分钟级 / 小时级）？
2. **取消语义**：Go 侧签名是否首参接受 `ctx` 并在循环内设检查点？前端能否拿到可取消句柄并有取消入口？取消后资源（文件句柄、临时文件、子进程）如何清理？
3. **并发模型**：任务排队还是并行？并发上限是多少？同一实体的两个任务是否互斥？
4. **进度协议**：进度事件多久发一次？是否节流合并？进度允许倒退吗（阶段化任务）？长时间无进度的段落有没有心跳？
5. **部分失败**：批量任务的成败边界如何呈现？失败者可单独重试吗？成功者会不会被失败者拖着重跑？
6. **生命周期**：应用退出时在途任务怎么办——等待、取消还是丢弃？后台常驻任务挂在哪个生命周期上、是否可取消？
7. **重复入队**：同一任务在途时再次触发怎么办？幂等键或在途禁用在哪里强制？
8. **结果落点**：任务结果如何进入事实源？是否复用统一落定同步层，而不是任务自己刷界面？
9. **崩溃恢复**：任务状态有没有落盘？重启后是续跑、放弃还是清理残留？残留状态由谁扫？
10. **可观测**：任务的排队 / 运行 / 进度 / 失败在哪些界面表面可见？有没有地方能看「现在都在跑什么」？

交付给 AI 的设计结果应包含：长任务清单、取消链路图、并发与互斥规则、进度协议、退出策略、崩溃恢复策略、测试矩阵。

## 取消必须是一条贯通的链

取消不是「界面上放个按钮」，而是一条从用户意图贯穿到最内层循环的链：

- **入口**：前端保存可取消句柄；取消入口在任务可见的每一处（进度条、任务列表）都可触达。
- **贯通**：Go 侧首参 `ctx`，逐层下传；循环体和 IO 处设检查点；子调用接收并传播同一 `ctx`。
- **清理**：取消后临时文件、句柄、子进程有明确归宿；「取消成功」的定义（状态、回执）写进设计。
- **标注不可取消段**：确实无法中断的外部调用（外部命令、第三方库）必须设超时并在长任务清单里标注「不可取消，超时 X」；任务里全是这种段时，取消入口要明示「将于当前步骤结束后停止」。

## 并发与互斥

- **串行边界**：哪些任务对同一实体必须互斥（同一文件的两次导出）、哪些可并行，逐条写成规则而非默认。
- **上限与排队**：并发上限定数值；排队任务可取消；队列不无界增长。
- **有界并发用现成件**：Go 侧批量并发用 `errgroup.WithContext` + `g.SetLimit(n)`——不手搓信号量 channel、不写静态 worker pool；无错误传播需求时 `sync.WaitGroup.Go`（Go 1.25+）省掉 Add/Done 样板。
- **每个 goroutine 有已知退出条件**：每一处 `go func()` 必须能回答「它怎么停」——退出条件通常是 ctx 取消或 channel 关闭，写不出来就不许启动；Go 1.27+ 可用 `goroutineleak` profile（`runtime/pprof`）在验收时实证无泄漏（profile 干净是证据不是证明——经由全局变量阻塞的泄漏它看不见）。
- **防重复入队**：与同步层「连点」纪律一致——在途禁用或幂等键，统一收口，不靠每处按钮自觉。

## 进度与心跳

- 进度事件**节流合并**（→ 同步层的高频事件纪律），频率有预算。
- 阶段化任务的进度协议（阶段名 + 阶段内比例）在立项时定，避免「进度从 90% 跳回 30%」被当成 bug。
- 长段无进度的任务要有**心跳**（活性信号），否则「在慢慢跑」和「已经死了」无法区分；超时阈值写明。

## 退出与崩溃

- **退出策略三选一显式化**：等待完成 / 取消全部 / 明示丢弃，写进设计文档；不许「看框架默认行为」。
- **崩溃恢复二选一**：任务状态落盘可续跑，或不落盘则启动时必须清扫残留（临时目录、半成品文件、在途标记）。两样都不做，就是幽灵状态。
- 常驻后台任务（监听、轮询、同步）全部挂启动 / 关闭生命周期，具备可取消上下文，不依赖进程退出来「自然终止」（与同步层的服务启停纪律一致）。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 界面卡死 | 长调用无超时无取消，且在 UI 线程等待 | 长任务清单 + 全调用首参 `ctx` + 超时兜底 |
| 点了取消停不下来 | `ctx` 未贯通到循环，或某段不可取消且未标注 | 取消链路图逐层核对；不可取消段显式标注并设超时 |
| 任务被执行多次 | 在途未禁用、无幂等键 | 在途禁用 / 幂等键统一收口 |
| 批量一半失败用户不知情 | 部分失败无回执、无重试入口 | 成败边界呈现规则 + 失败者单独重试 |
| 重启后任务幽灵复活或永久残留 | 状态未落盘且启动不清扫 | 落盘续跑或启动清扫，二选一 |
| 进度条反复横跳 | 进度未节流、无阶段协议 | 节流 + 阶段化协议 |
| 关了窗口任务还在写文件 | 退出策略未定义，依赖默认行为 | 退出策略显式化 |
| 越跑越慢 | 任务无并发上限，互相争抢 | 上限与排队规则 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 取消时机 | 启动瞬间、进行中、收尾阶段；取消后立即重发 |
| 生命周期 | 正常退出、强杀、崩溃后重启的残留清扫 / 续跑 |
| 并发 | 上限验证、同实体互斥、跨实体并行 |
| 失败 | 每类任务至少一次失败 + 一次部分失败 + 失败者重试 |
| 进度 | 阶段推进、心跳、慢任务的取消入口可达性 |

每次验收记录：取消时任务所处的段、资源清理结果、落定后的界面状态。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先盘点长任务清单并标注预期时长与可取消性。所有长调用首参接受 `ctx` 且循环内设检查点；前端保存可取消句柄并在任务可见处提供取消入口；任何无取消能力的外部调用必须设超时并在清单标注；进度事件节流并有阶段协议；任务在途幂等或在途禁用；并发上限与互斥规则写成显式配置；退出策略与崩溃恢复策略（落盘续跑或启动清扫）二选一写进设计；任务落定一律走统一落定同步层，不得自行刷界面。实现后补取消、崩溃恢复与部分失败的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：长任务清单 + 取消链路设计。
- **二档**：`ctx` 贯穿路径、前端取消入口、退出策略（对应主大纲「长任务取消通道」条目）。
- **三档**：崩溃恢复、部分失败回执、常驻任务生命周期全量。
