# 网络与离线弹性：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。对会访问网络（API、更新、同步、外部资源）的桌面应用，它把超时、重试、离线、代理、时钟放在一起考虑，避免功能分别做完后才发现：网络一卡界面跟着卡、弱网下重复提交、离线时一片空白或假死、企业代理下更新和 API 全部失联、断网期间的操作与远端状态对不上。

**纯本地应用**：只需回答第 1 问（确认无网络依赖）后即可跳过本方案。

它不是某个应用的实现说明，也不预设产品名、框架或网络库。每个项目都应先按自己的网络依赖清单核实能力，再填写自己的决策。

这类问题的共同名字叫「网络被当成可用前提」。它们几乎从不来自某一个 bug，而来自一个结构：**代码写成像本地调用一样永不失败、永不慢、永不经过代理**。本方案的目标是把「网络随时会没、会慢、会绕路」作为立项时的默认假设。

三个边界先说清：
- 更新流水线的下载与校验 →《签名打包与更新分发技术方案》；本方案管一般网络路径的弹性。
- 任务级取消 →《长任务与后台工作技术方案》；落定后的界面同步对账 →《统一同步层技术方案》。
- 代理策略的准入问题在主大纲二档（Go 侧 HTTP 客户端与系统代理/PAC）；本方案给出完整纪律。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **网络依赖清单**是什么？哪些功能依赖网络？离线时各功能的预期行为是哪一档（完整可用 / 只读 / 明确禁用）？
2. **超时策略**：每类请求的连接 / 响应 / 总超时各是多少？有没有无超时的调用？
3. **重试与幂等**：哪些操作可安全重试？重试间隔与上限？非幂等操作如何防重复提交？
4. **离线检测与呈现**：怎么判断离线？离线时各界面显示什么（缓存数据 + 标记？空态？）？恢复后触发什么？
5. **操作排队**：离线期间的用户操作是排队还是拒绝？队列持久吗（→《应用状态与持久化技术方案》）？重放的顺序与冲突如何裁决？
6. **代理与防火墙**：目标环境（尤其企业）的系统代理 / PAC 策略？Go 侧 HTTP 客户端是否遵循——遵循与否都必须显式声明？企业 TLS 拦截（自签根证书）怎么办？
7. **TLS**：证书校验策略是什么？允许任何形式的降级吗（不允许）？
8. **DNS / IPv6 / 重定向**：目标环境有没有已知限制（待验证）？
9. **时钟**：依赖本地时钟的逻辑（令牌过期、授权窗口）在时钟偏差下怎么办？
10. **带宽与流量**：大文件与同步的流量预算？按量计费网络的处理？
11. **测试**：弱网、断网、半断（连接正常请求全挂）、代理、强制门户的用例在哪？

交付给 AI 的设计结果应包含：网络依赖清单与离线预期、超时 / 重试矩阵、离线呈现与排队设计、代理策略声明、测试矩阵。

## 超时与重试纪律

- **一切外呼必须有超时**（连接 / 响应 / 总超时三层）；无超时的调用是缺陷，不是默认。超时的请求要有「它还在转吗」的明确答案——在途请求与界面状态绑定（与《长任务与后台工作技术方案》的在途纪律、同步层的乐观更新纪律衔接）。
- **重试只对幂等操作自动进行**：非幂等操作要么带幂等键，要么交给用户显式重试；「网络组件自动帮你再试一次下单」是最贵的 bug。
- 退避 + 抖动 + 重试上限；**上限到达后给用户明确状态与手动重试入口**，不许静默放弃也不许无限转圈。

## 离线是一等状态

- **离线不是错误，是常态**：每个依赖网络的功能预先定义离线行为，三档——完整可用（本地优先）/ 只读（缓存）/ 明确禁用（说明原因与恢复条件）。
- **离线检测不可靠**：连接状态指示只是信号，最终以请求实际结果为准；必须处理「检测在线但请求全挂」的半离线态——它是用户最困惑的状态。
- **恢复后的收敛**：恢复在线触发一轮重查（→ 同步层兜底通路）；离线期间排队的操作按序重放，重放冲突以事实源裁决，前端不做本地合并（与同步层多窗口纪律同理）。多设备场景的同步与冲突裁决 →《多端数据同步方案》。
- **缓存呈现必须带「这是缓存」的标记**，不许冒充实时数据；缓存的新鲜度标准（多旧算旧）写进设计。

## 代理与企业环境

- **Go 侧 HTTP 客户端不会自动继承 WebView 的系统代理**（主大纲已列）。显式声明策略：遵循（读取系统 / 环境配置）或不遵循并写明理由；更新、API、遥测的代理策略可以不同，但每条都必须显式。
- **企业 TLS 拦截**（自签根证书替换流量证书）在目标环境验证；校验策略不降级，例外走显式配置而非关闭校验。
- 代理不可用时各网络功能的降级档位进入能力矩阵（→《系统能力与平台集成技术方案》）。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 网一慢界面全卡 | 外呼无超时且在关键路径同步等待 | 超时矩阵 + 异步化 + 在途状态呈现 |
| 弱网重复提交 | 非幂等操作被自动重试 | 幂等键 + 用户显式重试 |
| 离线白屏或假死 | 离线行为未定义 | 离线三档预定义 |
| 企业环境全部失联 | 代理未处理、TLS 拦截未验证 | 代理策略显式声明 + 目标环境验证 |
| 恢复网络后数据错乱 | 排队操作乱序重放、本地合并 | 有序重放 + 事实源裁决 |
| 显示在线但什么都失败 | 半离线态无呈现 | 以请求结果为准 + 明确状态 |
| 令牌频繁失效 | 依赖本地时钟 | 服务器时间 / 宽松有效期窗口 |
| 重试上限到达后转圈不止 | 无终态 | 明确状态 + 手动重试入口 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 网络 | 正常、慢、断、半断（连接正常请求挂）、恢复 |
| 代理 | 有代理、坏代理、需认证代理、企业 TLS 拦截 |
| 重试 | 幂等自动重试生效、非幂等不自动、上限到达呈现与入口 |
| 排队 | 离线操作 → 恢复重放 → 冲突裁决 |
| 时钟 | 本地时钟偏差下的授权与有效期 |

每次验收记录：网络注入方式、界面呈现、重放结果。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出网络依赖清单与每个功能的离线预期档位。一切外呼必须设连接 / 响应 / 总超时；自动重试仅限幂等操作且带退避与上限；非幂等操作必须幂等键或显式用户重试；离线行为按「完整可用 / 只读 / 明确禁用」预定义，缓存呈现带标记；恢复在线触发重查与排队重放，重放冲突以事实源裁决；Go 侧 HTTP 客户端的代理策略显式声明；证书校验不降级；网络等待不得阻塞主线程或界面。平台与企业环境相关行为先验证，未验证标注“待验证”。实现后补弱网 / 断网 / 代理场景的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：网络依赖清单与离线预期（大纲准入条目在二档「网络依赖与离线预期」）。
- **二档**：超时 / 重试矩阵、代理策略声明（主大纲「Go 侧 HTTP 客户端与系统代理/PAC」条目）。
- **三 / 四档**：排队重放、企业环境与按量计费网络验证。
