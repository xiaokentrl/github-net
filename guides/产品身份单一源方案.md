# 产品身份单一源方案：通用规划方案

## 这份方案是做什么的

来源：主大纲一档「产品身份单一源」「macOS Info.plist 合规性」两项，以及《托盘技术方案》（身份映射表）、《默认安装目录规划方案》（目录契约）、《版本号方案》（版本单源）、《签名打包与更新分发技术方案》（签名与公证）里各自散落的身份片段。

改名通常涉及多种值，不能靠全仓库查找替换维护。本方案把这些值收进**一个权威源**，并让桌面项、打包配置、运行时初始化、测试、诊断都从它读取或校验。它管身份，不管版本号数值（→《版本号方案》）、不管目录路径契约（→《默认安装目录规划方案》）、不管图标资源链路（→《托盘技术方案》）、不管签名密钥（→《签名打包与更新分发技术方案》）。

不预设：产品显示名、应用 ID、Bundle ID、桌面文件名、资源路径。示例值只能是占位符，正式方案不得把示例复制成项目事实。

**证据等级**：平台格式规则（`CFBundleIdentifier` 字符集、`{{` 模板残留）来自主大纲二手结论与平台当期文档，落地前按目标平台复核；未核实的标 **待验证**。

## 开始写代码前，先让 AI 回答这些问题

1. 产品有哪些面向用户的名字（含本地化变体）与机器身份？哪些平台需要 Bundle ID、桌面文件 ID、窗口类名、通知类别、Dock 归组键？
2. 身份清单里哪些值必须彼此匹配？哪些只用于平台展示、允许不同？
3. 唯一权威源放在哪（Go 包常量 / 生成文件 / 配置清单）？桌面项、打包配置、运行时、CI 各自如何读取或校验？
4. 构建配置与权威值不一致时，是否有明确失败的校验门（而不是只警告）？
5. `CFBundleIdentifier` 是否只含 `[A-Za-z0-9.-]`？应用显示名是否含空格、与可执行名不同？
6. 从旧模板迁移时，构建产物里是否残留 `{{` 字面量，注册了无意义的文件关联或 scheme？
7. 改显示名是否会影响单实例锁、用户数据目录、升级识别、桌面归组、通知权限（→《单实例与快速启动方案》《默认安装目录规划方案》）？
8. 是否可能迁移稳定 ID？若迁移，旧身份兼容、快捷方式迁移、数据保留、双图标归组的策略是什么？
9. 图标、托盘可访问名称、安装包名是否由权威身份生成或校验（→《托盘技术方案》）？
10. 产物验证：构建完成后从**产物内部**读出实际值（Info.plist / .desktop / PE 资源 / 包名）与权威值对比，而不是只看源码？
11. 单实例唯一 ID 用什么（反向域名或 GUID），与稳定应用 ID 的关系是什么？
12. 本地化显示名的键化管理在哪（→《国际化与输入技术方案》《多语言实现方案》）？

交付给 AI 的设计结果应包含：身份映射表、权威源位置、衍生值生成流程、一致性校验门、改名与迁移流程、产物验证记录。

## 核心纪律

### 一、先分开概念，再建映射

| 身份或名称 | 用途 | 规划时要确认 |
|---|---|---|
| 产品显示名 | 窗口标题、菜单、安装界面、用户可见文字 | 是否本地化；不要拿显示名代替机器身份 |
| 稳定应用 ID | 单实例、桌面环境识别、设置与通知归属 | 格式、生命周期、改名后是否保持稳定 |
| 平台原生身份 | Bundle ID、桌面文件 ID、窗口类名、程序名 | 哪些必须彼此匹配，哪些只用于展示 |
| 托盘可访问名称 | 托盘宿主、辅助功能、菜单标题 | 平台是否展示、长度与本地化 |
| 资源名 | 图标文件名、资源目录名、安装包名 | 是否由构建流程从权威身份生成 |
| 数据目录键 | 配置/数据/缓存/日志根 | 变化会导致「升级后找不到旧数据」 |

**稳定身份集中在单一源**；桌面项、打包配置、运行时初始化和测试从该源读取或校验。改显示名不应意外改变单实例锁、用户数据目录、升级识别或桌面归组。

### 二、衍生值自动检查

- 每个衍生值记录：生成工具、打包位置、运行时加载位置、校验方式。
- 构建配置、安装桌面项与权威值不一致时 **CI 明确失败**；不要只在文档里写「应该一致」。
- 校验门要检查产物内部值，而不是源码目录里有没有那张图片（→《托盘技术方案》的图标资源链路纪律）。
- `CFBundleIdentifier`/`CFBundleExecutable` 的实际值 + 无 `{{` 残留，是 macOS 产物的固定检查项；其他平台同理列固定项。
- 版本号与身份是两套东西：版本号单源注入见《版本号方案》，身份单源注入见本方案，两者都进构建校验门。

### 三、改名与迁移

| 变更 | 是否影响稳定 ID | 必须做的 |
|---|---|---|
| 只改显示名（含本地化） | 否 | 更新键化文案；回归桌面归组与通知归属 |
| 改资源名/图标 | 否 | 检查最终安装包与运行中的应用（→《托盘技术方案》） |
| 改稳定 ID | 是 | 旧身份兼容、快捷方式迁移、数据保留、双图标检查、升级识别演练 |
| 改数据目录键 | 是 | 一次性搬家：新位置没有且旧位置有才搬，原件保留（→《应用状态与持久化技术方案》） |

**迁移演练必须真实执行过**：从旧版本安装 → 覆盖升级 → 检查只有一个 Dock/启动器图标、旧配置仍可读、单实例锁仍生效、托盘唤回仍指向新实例。没有演练记录的迁移方案不算完成。

### 四、与目录、单实例、通知的边界

- 数据目录、缓存目录、日志目录由 `paths` 单源推导（→《默认安装目录规划方案》），身份变更不得静默改变这些路径。
- 单实例唯一 ID 与稳定应用 ID 的关系要写明；二次启动参数路由依赖它（→《单实例与快速启动方案》）。
- 通知类别/权限归属在 macOS 要求有效 Bundle ID 且已签名，身份不一致会表现为「通知不弹」（→《系统能力与平台集成技术方案》）。
- 自定义协议与文件关联的注册值也来自身份源，否则改名后会注册无意义的 scheme（→《外部链接与协议回调安全方案》）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 改名后 Dock 出现两个应用图标 | 显示名、应用 ID、桌面文件身份、窗口类名不一致 | 身份映射表 + 产物级一致性校验门 |
| 升级后设置「丢了」 | 稳定 ID 或数据目录键被改动 | 稳定 ID 不随显示名变；搬家逻辑（新无旧有才搬） |
| macOS 通知/文件关联失效 | Bundle ID 非法或含模板残留 | `CFBundleIdentifier` 正则检查 + 无 `{{` 残留门 |
| 托盘图标与程序图标不一致 | 资源名未从身份源生成 | 资源链路登记 + 安装包实测 |
| 源码里改了、产物里没变 | 只校验源码，未校验构建产物 | 从 Info.plist/.desktop/资源段读实际值 |
| 单实例锁失效开了两个实例 | 唯一实例 ID 与稳定 ID 各写一份 | 单源推导 + 二次启动冒烟 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 一致性 | 权威值 ↔ 桌面项 ↔ 打包配置 ↔ 运行时 ↔ 产物内部值，逐项断言 |
| 格式 | Bundle ID 字符集、桌面文件 ID、含空格的显示名、可执行名不含空格 |
| 迁移 | 旧版安装 → 覆盖升级 → 归组图标数、旧配置可读、单实例、托盘唤回 |
| 平台 | Windows / macOS / Ubuntu 26.04 的桌面项、资源段、Info.plist 实测 |
| 形态 | dev / 打包安装分别验证；浏览器预览不算 |
| 失败 | 故意把配置里一个身份值改错，校验门必须明确失败 |
| 本地化 | 切换语言后显示名变化不影响稳定 ID |

## 给 AI 的实施约束模板

> 先给出身份映射表（显示名/稳定 ID/平台原生身份/托盘名/资源名/数据目录键）、唯一权威源位置、每个衍生值的生成与打包位置、构建期一致性校验门、改名与稳定 ID 迁移策略，再开始写构建配置。**显示名不得代替机器身份；改显示名不得改变单实例锁、数据目录、升级识别与桌面归组；所有衍生值从权威源生成或校验；校验必须读构建产物内部实际值，不一致明确失败；macOS 产物检查 CFBundleIdentifier 字符集与无 `{{` 残留。** 迁移要有从旧版安装覆盖升级的实测记录。任何名称、ID、资源路径由当前项目需求决定，示例值只能是占位符；平台格式规则查不到证据的写「待验证」。实现后给出一致性门、失败用例与未实测平台清单。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 身份映射表、唯一权威源、构建期一致性门（不回答不写业务代码） |
| 二档 | 平台原生身份格式、图标与资源链路、Info.plist 合规性检查 |
| 三档 | 显示名本地化、通知类别归属、托盘可访问名称 |
| 四档 | 产物内部值验证进发布门禁、`{{` 残留检查、迁移演练记录 |
| 五档 | 稳定 ID 迁移可不实施但必须写明触发条件与兼容策略 |
