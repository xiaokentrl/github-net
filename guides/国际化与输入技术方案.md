# 国际化、区域与输入：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把文案键化、RTL / bidi、输入法（IME）、区域格式、语言切换放在一起考虑，避免功能分别做完后才发现：组件库在根节点强制了 LTR、路径和代码在 RTL 布局里被搅乱、受控输入框在打字时丢字或重复、日期被当成字符串存进数据库、切了语言后一半界面没跟上。

它不是某个应用的实现说明，也不预设产品名、框架、组件库或翻译平台。每个项目都应先按目标语言清单和框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「为一种语言写成、后补其他语言」。它们几乎从不来自某一个 bug，而来自一个结构：**格式化、方向、输入这些「展示层关注点」被写进了数据层和逻辑层**。本方案的目标是在立项阶段就把「数据归数据、展示归展示」的边界画出来。

主大纲三档只列准入问题（IME、RTL、区域格式的检查项）；本方案给出完整纪律。Wails3 + Go 的具体落地（一语言一文件、双端零注册、CI 键齐性门禁）见《多语言实现方案》。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标语言和锁定的框架版本，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. **目标语言清单**是什么？是否包含 RTL 语言？是否包含 CJK（输入法必然在场）？
2. **文案键化**：是否全部用户可见文案已键化？翻译资源放哪、怎么打包？缺失键的回退行为是什么，能否在构建期检测？
3. **bidi 混排**：路径、代码、密钥、数字出现在任意语言界面时的隔离策略是什么？哪些内容**永远 LTR**（代码、路径、ID）？
4. **框架与组件库的方向控制**：是否在根节点强制 `dir`？原生菜单、托盘菜单能否镜像（多数不能）？不能镜像时的降级是什么？
5. **IME**：核心输入区是否正确处理组合过程？哪些组件会在组合态被程序性改写（受控重置、格式化拦截）？全局快捷键与组合态的冲突规则是什么？
6. **区域格式**：数字、日期、列表、排序用什么库做区域感知格式化？时区策略是什么（存 UTC、展示本地）？
7. **持久化**：是否一律存规范化值（ISO 8601、原始数字）而非格式化字符串？
8. **语言切换**：运行时可切还是需重启？HTML、原生菜单、托盘、系统通知各层如何联动？哪些层不可达、降级是什么？
9. **本地化资源**的体积与增量更新策略是什么？
10. **测试**：目标语言逐个的 IME、格式、布局测试矩阵在哪？谁验？

交付给 AI 的设计结果应包含：语言清单、键化与回退规则、bidi 隔离清单、IME 兼容纪律、格式化选型、语言切换联动表、测试矩阵。

## 数据归数据、展示归展示（核心纪律）

- **持久化层只存规范化值**：日期存 ISO 8601 或时间戳，数字存原始值，不存任何格式化字符串。格式化字符串进了存储，区域和语言就永远改不动了。
- **格式化只发生在展示层**，且集中到一个格式化模块；组件里手写数字格式化、拼接日期字符串都是违规点。
- **文案全部键化**：字符串字面量进 UI 代码 = 该语言永远无法覆盖；缺失键要有明确回退（键名或源语言）并能被构建检测。
- **排序用区域感知的排序规则**（collation），不用字节序或大小写折叠比较。

## bidi：混排内容的隔离

- 布局方向由语言决定，**内容方向由内容决定**：路径、代码、密钥、ID、数字在 RTL 界面里用隔离手段（隔离元素或双向控制符）保持 LTR，逐类登记成清单。
- 双向控制符有已知的复制 / 搜索副作用，用隔离元素优先于裸控制符——具体取舍在目标组件库中验证。
- 原生层（托盘菜单、系统通知、原生对话框）多数**无法镜像方向**；列入平台差异验证清单，降级（保持系统语言或英文）在立项时选定，不默认「到时候再说」。

## IME：组合态是神圣的

- **组合期间不得程序性改写输入框**：受控组件在组合态被重置或格式化拦截，表现就是丢字、重复、候选窗错位——这是「输入法类 bug」的最大来源。
- 格式化、校验、自动转换统一放在**组合结束之后**；需要实时反馈的用预编辑文本展示，不改值。
- 全局快捷键在组合态的行为逐条定义：放行、拦截还是排队；「打字打到一半快捷键触发」必须不可能发生。
- 目标语言逐个做 IME 冒烟，至少覆盖一种 CJK 输入法的全流程（输入、候选、取消、中英切换）。

## 语言切换的联动

- 切换入口改的是配置（→《应用状态与持久化技术方案》），各层响应方式立项时逐层定：HTML（即时）、原生菜单（可重建则重建，不可则重启生效）、托盘（同前）、系统通知（取当前值）。
- **联动表**逐层填：层 / 是否即时 / 实现方式 / 不可达时的降级。「一半界面没变」几乎都是某一层没进联动表。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| RTL 界面里路径、代码乱序 | 混排内容无隔离 | 永远 LTR 清单 + 隔离手段 |
| 打字丢字、重复、候选错位 | 输入框在组合态被程序性改写 | 组合结束前不改值、不重渲染 |
| 换机器日期显示异常 / 无法换格式 | 存储层存了格式化字符串 | 规范化值入库 + 展示层集中格式化 |
| 切语言后菜单 / 托盘没变 | 该层不在联动表 | 联动表逐层定 + 降级 |
| 快捷键打字时误触发 | 组合态未拦截 | 组合态快捷键规则 |
| 新语言上线即崩 | 缺失键无回退、构建不检测 | 回退规则 + 构建期键完整性检查 |
| 搜索 / 排序「看起来随机」 | 字节序排序、大小写当折叠 | 区域感知 collation |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 语言 | 目标语言逐个：全界面巡检（键缺失、溢出、截断） |
| 输入 | 每个输入区 × 目标 IME：组合、取消、中英混输、快捷键 |
| 方向 | RTL 语言：布局镜像、混排隔离、原生层降级 |
| 格式 | 数字 / 日期 / 排序在不同区域下的展示；切换区域后的存量数据展示 |
| 切换 | 语言切换后逐层核对联动表；重启前后一致 |

每次验收记录：语言、区域、IME、实际输入序列与界面表现。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先确认目标语言清单并给出键化覆盖率。文案全部键化且缺失键有回退、构建可检测；持久化只存规范化值，格式化集中在展示层单一模块；路径、代码、ID 类内容在任何语言下按「永远 LTR」清单隔离；输入组件在 IME 组合态不得被程序性改写，格式化与校验放在组合结束之后；语言切换按联动表逐层实现并写明降级；原生层不可镜像方向时按选定降级执行。不得在组件里手写区域相关格式化或拼接；不得把区域格式写进存储。平台相关行为（菜单镜像、通知语言、组合态行为）先在目标环境验证，未验证标注“待验证”。实现后补目标语言的 IME 与格式回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：目标语言清单（决定是否立项即键化）。
- **二档**：键化与回退、规范化值入库。
- **三档**：IME 纪律、bidi 隔离、联动表（对应主大纲「输入法与预编辑文本」「RTL / bidi」「区域格式」条目）。
