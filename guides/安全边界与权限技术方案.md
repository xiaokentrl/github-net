# 安全边界与权限：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把一条公理推到全部结论：**前端 WebView 是不受信内容，操作系统传进来的一切也是**。覆盖暴露面、CSP 与 DevTools、外部输入消毒、高权限进程隔离、自动化 / Agent 接口、OAuth 回调、敏感数据与更新信任根，避免功能分别做完后才发现：暴露面随功能蔓延成全部后端、关联文件参数被直接拼进路径、高权限操作混在主进程里、令牌进了日志和诊断包。

它不是某个应用的实现说明，也不预设产品名、框架或鉴权库。每个项目都应先按自己的暴露面清单和框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「边界失守」。它们几乎从不来自某一个 bug，而来自一个结构：**边界没有被画出来，于是每个新功能默认把更多东西暴露给更不可信的一侧**。本方案的目标是把边界在立项时画成一页图，并让每次评审对着它检查。

主大纲一档的「渲染器安全边界」「高权限操作隔离」「自定义协议安全」与二档「安全与外部接口」各条，准入问题以主大纲为准；本方案给出完整纪律。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先盘点项目并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。回答不了就不动工。

1. **信任边界一页图**：哪些进程 / 组件可信、哪些不受信（WebView、OS 传入参数、外部进程）？每条跨界通道上有什么校验？
2. **暴露面清单**：暴露给前端的每个方法，标注「只读 / 写 / 管理」和输入校验策略；默认是否最小暴露、按需放开？
3. **绑定模型**：暴露的 struct 是否只是简单数据容器（无 channel、函数、复杂接口、未导出字段）？
4. **CSP**：生产构建是否显式注入（至少 `default-src 'none'` 家族）？开发与生产的差异是什么？是否依赖「默认没有但也没出事」？
5. **DevTools**：生产构建是否显式禁用并进入发布门禁，而不是依赖默认值？
6. **外部输入**：自定义协议、文件关联、deep link 的参数是否只接受结构化 ID？路径规范化与目录前缀校验在哪一层？外部链接打开前有无 scheme 白名单？
7. **高权限操作**：清单是什么（驱动、TUN、系统代理…）？主进程是否始终普通权限运行？高权限拆到什么进程、IPC 如何鉴权（对端校验 / 一次性令牌）？
8. **自动化接口**：开发期的 MCP / Agent 控制接口，生产构建是否零攻击面（不带对应构建标签，且有门禁检查）？
9. **OAuth / SSO 回调**：loopback 还是 deep link？端口冲突、用户拒绝授权的降级路径？`state` 防 CSRF 了吗？系统浏览器回调如何路由到已运行实例？
10. **敏感数据**：令牌、密钥存哪？是否与普通配置分离、权限收紧、排除出日志与崩溃转储（→《应用状态与持久化技术方案》《日志与可诊断性技术方案》）？
11. **Go 侧网络**：更新与 API 调用的 HTTP 客户端代理策略是什么（显式声明遵循或不遵循系统代理）？
12. **更新信任根**：签名公钥是否固定在二进制内，而非从更新源动态获取？

交付给 AI 的设计结果应包含：信任边界图、暴露面清单（逐方法分类）、CSP 与门禁定义、外部输入消毒清单、进程权限图与 IPC 鉴权方式、敏感数据清单、测试矩阵。

## 信任边界一页图（先画图，再写代码）

把系统里每个组件放进三格：**可信（自己）、半可信（本地文件、插件）、不受信（WebView 内容、OS 传入参数、网络）**。每条跨界线写明校验。之后所有评审都对着这张图问一句：**这个新功能有没有把数据或能力递过一条没有校验的边界线？**

两条推论立即成立：

- WebView 里的前端代码「是我们写的」不改变它不受信——它运行在能被注入内容影响的运行环境里，能被注入的内容（页面、脚本、拖放、剪贴板）都是边界外的输入。
- 操作系统递进来的（协议参数、关联文件路径、命令行、deep link）是**攻击者可构造的输入**，不是「系统给的所以可信」。

## 暴露面纪律

- **默认不暴露，按需暴露**：每暴露一个方法都是一次显式决策，登记进清单并分类（只读 / 写 / 管理）。
- **校验在 Go 侧**：前端传来的每个参数都是不可信输入；绑定层给的类型不算校验，取值范围、归属、路径合法性要在 Go 侧再验一次。验证的分层架构（展示 / 边界 / 领域 / 存储）与规则单源见《输入数据验证方案》。
- **绑定模型纯数据**：跨边界的 struct 只是数据容器；复杂类型跨边界既不可靠也扩大攻击面。
- 暴露面只减不增：删除功能时同步删暴露，清单与代码的一致性进 CI。

## 外部输入消毒

- **结构化 ID 优先**：协议与 deep link 回调只接受能对上内部登记表的 ID，不接受任意路径 / URL；「传文件路径」降级为「传登记过的文档 ID」。
- **路径必须规范化后校验**：拒绝穿越、拒绝目录前缀外、拒绝非预期 scheme；规范化在权威层做一次，不做第二次散落实现。
- **外链白名单**：打开任何外部链接前过 scheme 白名单，其余拒绝或转交系统确认。

## 进程与权限隔离

- 主进程**始终普通权限**；需要高权限的操作拆成独立进程，能力最小化到只做那几件事。
- IPC 鉴权落实在连接时：校验对端身份（PID / 路径 / 签名，按平台能力），配一次性令牌；「本地谁都能连的端口」不算鉴权。
- 高权限进程不持有普通业务数据，崩溃 / 被替换不影响主数据。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 前端被注入后能调一切 | 暴露面无分类、无最小化 | 暴露面清单 + 分类注册 + 校验在 Go 侧 |
| 关联文件参数成为攻击入口 | OS 传入直接拼路径 | 结构化 ID + 规范化校验 |
| 页面能加载任意外部脚本 | 无 CSP、依赖默认 | 生产显式注入 CSP + 门禁 |
| 高权限被本地程序冒用 | IPC 无对端校验 | 连接时鉴权 + 一次性令牌 |
| 令牌泄漏 | 与普通配置同路径、进了日志 / 转储 | 分类分离 + 排除清单 |
| 更新被劫持 | 公钥动态获取 | 公钥固定于二进制 |
| 生产被打出 DevTools | 依赖「默认应该关了」 | 显式禁用 + 发布门禁 |
| 自动化接口裸奔上线 | 开发标签带进了生产构建 | 构建门禁检查标签缺失 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 暴露面 | 每方法分类标注核对；越权调用（前端试调管理类）被拒绝 |
| 输入 | 协议 / 关联 / deep link 的恶意用例：穿越、超长、类型混淆、未登记 ID |
| 构建门禁 | 生产构建中 DevTools 关闭、CSP 生效、自动化接口不存在 |
| 提权 | 高权限 IPC 的冒用用例（伪造对端、重放令牌）被拒绝 |
| 回调 | OAuth 端口冲突、用户拒绝、`state` 不匹配、重定向劫持 |
| 泄漏 | 构造含敏感值的操作，审查日志、崩溃转储、诊断包内容 |

每次验收记录：注入方式、实际结果、边界线位置。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出信任边界一页图与暴露面清单。所有暴露方法先分类注册（只读 / 写 / 管理）并在 Go 侧校验输入；绑定模型只含简单数据容器。生产构建显式注入 CSP、显式禁用 DevTools，并作为发布门禁；自动化 / MCP 接口仅限开发构建。外部传入一律结构化 ID 优先，路径必须规范化后做前缀校验，外链过 scheme 白名单。主进程始终普通权限，高权限操作拆独立进程并在连接时鉴权（对端校验 + 一次性令牌）。敏感数据与普通配置分离存储，排除出日志、崩溃转储与诊断包。签名公钥固定于二进制。不得以「前端代码是我们写的」为由跳过校验。实现后补恶意输入与门禁的回归测试，并明确列出未覆盖的攻击面。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。
