# 任务队列：Wails3 + Go 专用方案

## 这份方案是做什么的

《长任务与后台工作技术方案》是纪律母法（取消链、并发互斥、进度协议、退出与崩溃恢复）；本方案是它的**具体实现设计**：一个进程内任务队列系统，回答——任务怎么定义、怎么排队、怎么互斥、怎么去重、怎么重试、前端怎么看得到。

**硬性目标**：全应用所有耗时工作只有**一条进队入口、一种任务状态机、一个前端任务中心**。不出现「某功能自己 `go func` 自己管」——那正是长任务方案要排除的结构（任务发起后与界面解绑）。

先做的分级决策：**内存队列是默认**（桌面单用户，多数任务无需跨重启续跑）；只有声明了「必须跨重启续跑」的任务类型才进**持久化队列**档（任务记录落库，→ 状态方案）。按任务类型选档，写进 kind 注册表，不全局一刀切。

## 核心模型

```go
// internal/tasks/ —— 全库唯一进队入口（→ 后端目录结构方案）
type Queue interface {
    // Submit 幂等：同 Channel+Kind 在途时返回既有任务的句柄，不重复入队
    Submit(kind Kind, payload any, opts ...Opt) (Handle, error)
    Cancel(id TaskID, reason string) error
    Get(id TaskID) (Task, bool)          // 只读
    List(filter TaskFilter) []Task       // 任务中心数据源
}

type Kind struct {          // 类型化注册表：新任务类型 = 注册一次，不写匿名 goroutine
    Name        string                      // "import.library"、"scan.files"
    Run         func(ctx context.Context, t *Task, p Progress) error
    Channel     func(payload any) string    // 互斥锚点："file:123"——同通道串行
    Timeout     time.Duration               // 兜底超时，必有值
    Retry       *RetryPolicy                // nil = 不自动重试；仅幂等任务给
    Durable     bool                        // 是否跨重启续跑（进持久化档）
    Cleanup     func(t *Task)               // 取消/失败后的资源清理
}
```

- **通道互斥**：`Channel` 返回实体锚点（`file:123`、`device:usb-xx`），同通道排队串行、跨通道并行，全局并发上限另设——长任务方案「串行边界」的实现位。
- **去重**：`Channel+Kind` 在途去重是默认行为，连点/重复触发天然安全（与同步层「连点」纪律同源）。
- **取消**：每个任务独立 `ctx`，`Run` 必须在循环与 IO 处检查；`cancelling` 是显式状态，取消后 `Cleanup` 必跑。
- **超时**：`Timeout` 必填（无超时任务是缺陷，→ 长任务方案）；不可取消的外部调用段在 kind 注册时标注。

## 任务状态机

```
queued ──→ running ──→ succeeded
   │          │  ↑心跳/进度
   │          ├──→ cancelling ──→ cancelled
   │          └──→ failed ──(手动重试)──→ queued（新 attempt，保留历史）
   └──(延迟/计划)──→ queued
```

| 规则 | 内容 |
|---|---|
| 终态不可逆 | succeeded / failed / cancelled 后只可复制重提，不可原地改判 |
| attempt 历史 | 重试产生新 attempt，旧 attempt 留痕——失败原因可追溯（→ 可诊断性方案关联 ID） |
| 自动重试 | 仅幂等 kind、仅带 `RetryPolicy`（退避 + 抖动 + 上限）；上限到达给终态与手动入口（→ 网络方案重试纪律） |
| 批量 | 批量 = 父任务 + 子任务；**收口规则**：全部子任务终态后父任务才落定（逐条刷是「批量只同步一半」的根因，→ 同步方案） |
| 部分失败 | 父任务呈现成败边界；失败子任务可单独重试，成功者不重跑 |

## 进度与事件

- 进度经 `Progress` 上报：**节流合并后**发往 `sync/` 枢纽，作为失效信号驱动任务中心刷新——任务队列**不自己刷界面**，与统一落定层同一条路。
- 任务状态本身是**事实**：任务中心是它的读者之一；长段无进度的 kind 必须发心跳，否则「在慢慢跑」与「已经死了」无法区分（→ 长任务方案）。
- 事件频率进性能预算（→ 性能方案事件频率实测）。

## 持久化档（仅 Durable kind）

- 任务记录（kind、payload、状态、attempt 历史）落 `state/` 管的库；启动时：未完任务标 `failed`（原因：应用中断），**不默认自动续跑**——kind 显式声明可续跑且实现了检查点才续。
- 无论如何，启动时**清扫残留**：临时文件、半成品、在途标记（→ 长任务方案崩溃恢复二选一；两样都不做就是幽灵任务）。
- 持久化用现有存储引擎（SQLite 表 + 轮询即可，桌面单用户不引入消息中间件——引入 MQ 属过度设计，需要时重新立项）。

## 退出与生命周期

- 队列挂应用生命周期（`ServiceStartup/ServiceShutdown`）；退出策略（等待 / 取消全部 / 明示丢弃）按档在 kind 注册表配置，关闭时执行并落盘终态（→ 长任务方案退出三选一）。
- 常驻探测类工作不算任务（无终态），挂生命周期 + 可取消上下文，不进队列——队列只收「有终态的工作」。

## 前端：任务中心

- `api/` 暴露 Submit / Cancel / List / Get（绑定分类：Submit、Cancel 是**写**，List、Get 是**只读**→ 安全方案暴露面纪律）。
- `stores/tasks.ts` 是任务状态的镜像（→ 前端结构方案），经 `sync/` 失效刷新；任务中心组件展示：列表、进度、取消、失败原因、重试入口。
- Submit 在组件层的语义：在途禁用或「查看进行中的任务」跳转——去重返回既有句柄时**必须可见**，不许静默吞。

## 验收清单

- [ ] 连点提交 N 次 → 只有一个任务执行（去重可见）
- [ ] 取消贯通：运行中任意时刻取消 → `cancelling` → 资源清理跑过 → `cancelled`
- [ ] 同通道互斥、跨通道并行、全局上限三者验证
- [ ] 每个 kind 的超时兜底生效
- [ ] kill -9 后启动：Durable 任务标记 failed（或按声明续跑），残留清扫跑过
- [ ] 批量部分失败：成败边界呈现、失败者单独重试、成功者不重跑
- [ ] 非幂等任务无自动重试；幂等任务重试带退避与上限
- [ ] 任务完成 → 任务中心与受影响表面在兜底窗口内收敛（非 UI 冒烟可触发任务验证）
- [ ] 退出策略三档各有演练

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 任务被执行两次 | 无在途去重、无幂等键 | Channel+Kind 去重默认开 |
| 点取消停不下来 | `Run` 未检查 ctx、清理缺失 | kind 注册强制取消点审查 + Cleanup 必跑 |
| 重启后任务幽灵复活或永久消失 | Durable 未声明、无启动清扫 | 分档决策 + 启动清扫必做 |
| 进度条抽搐 | 进度未节流、无阶段协议 | 节流 + 心跳（→ 长任务方案） |
| 队列越积越多卡死应用 | 无并发上限、无超时 | 全局上限 + Timeout 必填 |
| 批量一半失败没人知道 | 无父任务收口规则 | 批量收口 + 部分失败呈现 |
| 重试放大副作用 | 非幂等任务自动重试 | RetryPolicy 仅限幂等 kind |
| 任务完成界面没刷 | 任务自己刷界面或没刷 | 一律经 sync 枢纽落定 |
| 同一文件两个导出并行互踩 | 无通道互斥 | Channel 实体锚点 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 在 `internal/tasks/` 实现唯一任务队列：类型化 kind 注册表（Run / Channel 互斥锚点 / Timeout 必填 / Retry 仅幂等 / Durable 分档 / Cleanup），全应用禁止队列外的 `go func` 耗时工作。状态机按本方案六态，终态不可逆，重试留 attempt 历史；批量按父任务收口。进度节流后经 `sync/` 枢纽刷新，任务不自行刷界面；Durable 任务记录落 `state/` 管的库，启动清扫必做，续跑仅限显式声明且带检查点。退出策略按档配置并挂生命周期。前端经 `api/` 暴露 Submit/Cancel/List/Get，去重命中必须可见。实现后跑验收清单，补取消、去重、批量与崩溃恢复的回归测试，并明确列出未覆盖的组合。

方案确认后再改代码；队列行为与框架生命周期细节冲突时，先报告差异再裁决。

- **一档**：长任务清单 → kind 注册表映射；队列分档决策（内存 / Durable）。
