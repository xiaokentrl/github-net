# 状态码与错误码体系：通用方案

## 这份方案是做什么的

错误码的**机制**已有归属：《日志与可诊断性技术方案》定单一源与 parity 门；《输入数据验证方案》定「规则 ID 即错误码」。本方案定**码本身的设计**：码长什么样、怎么分配、怎么防失控、成功路径怎么表示、非错误的「状态枚举」（任务状态、同步状态）怎么治理。

**硬性目标**：每个码可被机器追溯（定义处 / 出现处 / 文案处三处可查）；**码发布即冻结**（永不改义、永不复用）；新码有唯一登记路径——码表增长十年也不失控。

## 码的结构：字符串码优先

```
{domain}.{subject}.{outcome}
例：library.import.file_locked
    settings.save.disk_full
    sync.push.conflict
```

- **domain** 与后端领域清单对齐（→ 后端结构方案 `domains/`）——码的命名空间就是领域，天热防跨域撞码；
- **subject** 具体到事（`import`、`save`、`push`），**outcome** 用受控枚举（`failed / rejected / conflict / timeout / unavailable`）；
- **自描述 + grep 可查**：字符串码在代码、日志、用户截图里都能直接检索，不需要中央数字分配器；
- **数字码仅在与外部系统对接时出现**（HTTP、第三方 API）：由**映射层**单向转换（内部码 → 外部码），映射表登记——外部协议不反向污染内部码表；
- **禁止**：万能码（`error`、`failed` 一步到位）、码内嵌序号或版本号（那是登记表的列，不是码的一部分）。

## 码表登记：新码的唯一出生路径

- **单一定义处**：Go 常量包（→ 后端结构方案，`internal/codes/` 或领域内常量）+ 每码一条登记：**码 / 含义 / 参数 / 文案键 / 引入版本 / 状态（active · deprecated）**；
- **登记自动收集**：CI 校验代码中出现的每个码都已登记、每个已登记码有文案键（与 parity 门同一道闸）——**未登记的码编译/构建期报错**，码表失控（谁顺手加一个）从机制上封死；
- **码发布即冻结**：改义 = 新码 + 旧码标 deprecated（保留映射一个版本周期）；**永不复用**——日志检索与用户报障的「这个码见过」依赖码的恒定；
- **弃用不清除**：历史日志里的码必须永远可查（码表是只增的档案，不是当前的清单）。

## 成功路径的表示（不发明「成功码」）

- Go 绑定返回 `(T, error)`：**成功没有码**——发明 `"success"` 码是噪音，成功由「无错误」表达；
- `error` 结构化为 `{code, params}`（→ 输入验证方案错误协议），前端 `api/` 层统一解包成错误对象（→ 前端结构方案）——**前端不发明码**：它只消费后端码 + 本地 UI 态（非码，不进码表）；
- **部分成功不是码**：批量成败边界是结构（成功清单 + 失败清单，→ 任务队列收口），不塞进单个码。

## 状态枚举（非错误的「码」）

任务状态、同步状态、会话状态、导入阶段……这些**枚举与错误码同纪律、分表管理**：

- 单一源定义（Go 侧枚举 + TS 镜像 + parity 门，同一套工具）；
- **值稳定，扩展只增不改**：新增状态值 = 枚举加值，前端对未知值**前向兼容**（显示兜底文案并上报，不崩、不当成已知值处理）——这是「旧前端遇到新后端」的安全阀（与降级守卫精神一致，→ 状态方案）；
- 枚举值同样登记（含义、引入版本、终态与否）——「这个状态还会变吗」的答案必须可查。

## 双端流转（复用既有链）

```
Go codes/ 常量（+登记表）→ 生成/镜像 TS → parity 门（CI）
       ↓                                    ↓
  日志（码进日志，→ 可诊断性）      errors/ 映射 → i18n 文案（→ 多语言）
```

文案分离纪律不变：**码稳定用于检索，人话随语言走**。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 登记 | 未登记码被 CI 拦截；已登记码缺文案键被拦截 |
| parity | 双端码集一致；码的参数集合一致 |
| 冻结 | 码改义检测（登记表 diff 审查）；弃用码仍可解析文案 |
| 枚举 | 后端新增枚举值 → 旧前端走兜底不崩；前端未知值上报 |
| 检索 | 按码检索日志全命中；码 → 定义处 / 文案处可机器追溯 |
| 外部 | 内外码映射表双向不串（外部码不进内部日志检索） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 码表越长越乱、出现重复码 | 无登记路径、无 CI 拦截 | 唯一出生路径 + 自动收集 |
| 同一错误前后端叫法不同 | 双端手抄无 parity | 常量单源 + parity 门 |
| 日志按码查不全 | 码被改名/复用 | 冻结纪律 + 只增档案 |
| 用户截图里只有 "error" | 万能码 | 结构强制（domain.subject.outcome） |
| 后端加了状态前端白屏 | 枚举无前向兼容 | 未知值兜底 + 上报 |
| 内部码泄漏到外部协议 | 无映射层 | 单向映射表 |
| 文案键和码对不上 | 登记表缺文案键列 | CI 缺键拦截 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出码结构选型（domain.subject.outcome）与登记表设计（码 / 含义 / 参数 / 文案键 / 引入版本 / 状态）。全部码与枚举定义在 Go 侧单一源，镜像 TS + parity 门；CI 拦截未登记码与缺文案键；码发布即冻结，改义走新码 + 弃用映射，永不复用；成功路径不发明码，部分成功用结构不用码；枚举扩展只增不改、前端对未知值前向兼容；与外部系统的码经单向映射层。不得在验证层拼接人话文案（→ 输入验证协议）。实现后补登记收集、parity、冻结与枚举兼容的测试，并明确列出未覆盖的码域。

方案确认后再改代码；码表设计属接口决策，AI 给结构与推演，最终命名由用户裁决。

## 五档定位

- **一档**：码结构选型 + 登记表设计（决定成败的一步，后补极贵）。
- **二档**：codes/ 单源、生成链与 parity 门、CI 拦截就位。
- **持续**：码表随领域增长；弃用档案与枚举兼容随版本维护。
